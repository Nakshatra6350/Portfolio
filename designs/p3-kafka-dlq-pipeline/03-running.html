Running, testing & exercises

Bring the stack up, follow one order through all five stages of the pipeline, then break it four different ways on purpose and watch each mechanism catch its own failure. Every command here runs against the real project; every observation has a place to look and a value to expect.

How to use this page

Reading the code tells you what the pipeline is supposed to do. The only way to know it does is to make it fail. Each section below has the same shape: a command that breaks something, the exact place to look, and the value that proves the mechanism engaged. If a number does not match, that is the interesting part — the troubleshooting table in code/README.md maps every symptom to its cause.

Bring the stack up

Infrastructure runs in Docker; the two Spring Boot services run on the host so you can attach a debugger and watch the retry ladder in your own console. That split is deliberate and it is also the first thing that bites people, because the broker advertises two different addresses and the one you need depends on which side of the container boundary you are calling from.

first session, in orderbash
make up                        # docker compose up -d --wait
make connector                 # register the Debezium outbox connector, then print its status
make build                     # mvn -T1C clean package -DskipTests (also builds the DLQ inspector jar)

# two more terminals, left running:
make run-consumer              # mvn -pl consumer -am spring-boot:run   on :38082
make run-producer              # mvn -pl producer -am spring-boot:run   on :38081

--wait is what makes this reproducible: docker compose blocks until every service with a healthcheck reports healthy, so make connector cannot fire at a Connect worker that is still starting its REST server. Without it you get an intermittent Connection refused that looks like a Debezium problem and is not.

The broker has no volume, and that is intentional

Mounting a named volume over /var/lib/kafka/data on the apache/kafka image lands you in a root-vs-appuser ownership fight. Broker state here is disposable; make reset (docker compose down -v) wipes the database volume and the topics together and gives you a clean first run. PostgreSQL does have a volume, which is why the consumer database is created only on the first boot of an empty data directory.

Register the Debezium connector

Nothing flows until the connector exists. Registering it is what creates the logical replication slot outbox_slot and the publication outbox_publication inside ordersdb — the connector is not a poller, it is a WAL reader, and those two objects are its subscription.

register, then verifybash
curl -X POST -H 'Content-Type: application/json' \
     --data @connectors/outbox-connector.json http://localhost:38083/connectors

curl -sS http://localhost:38083/connectors/outbox-connector/status
# expect "state":"RUNNING" for BOTH the connector and tasks[0].
# A RUNNING connector with a FAILED task publishes nothing and looks healthy
# in every dashboard that only reads the top-level field.

# what it created in postgres:
docker exec p3-postgres psql -U postgres -d ordersdb \
  -c "SELECT slot_name, plugin, active, confirmed_flush_lsn FROM pg_replication_slots;"
connectors/outbox-connector.json — the four lines that decide the wire formatjson
"transforms.outbox.route.by.field": "aggregate_type",
"transforms.outbox.route.topic.replacement": "${routedByValue}.events",
"transforms.outbox.table.expand.json.payload": "true",
"transforms.outbox.table.fields.additional.placement":
    "event_type:header:eventType,trace_id:header:traceId,id:header:eventId,aggregate_type:header:aggregateType"

The topic name is data, not configuration: aggregate_type = "orders" plus that replacement string produces orders.events. table.expand.json.payload is the line that stops your jsonb payload arriving as a JSON-encoded string — the single most common "why does my consumer see escaped quotes" complaint.

Deleting the connector does not delete the slot — and an idle slot pins WAL forever

make connector-delete removes the connector; outbox_slot survives. From that moment PostgreSQL cannot recycle any WAL segment newer than the slot's confirmed_flush_lsn, because it must assume a consumer will come back for it. Keep writing orders and pg_wal grows without bound until the volume fills and the database refuses writes. This is the classic CDC outage and it does not announce itself.

-- the number to alert on, in bytes:
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS retained
FROM pg_replication_slots;

-- and the cleanup you must not forget:
SELECT pg_drop_replication_slot('outbox_slot');

Trace one order through all five stages

One curl, five places to look. The eventId minted inside the producer's transaction is the same string at every stage — that is the thread you follow, and it is also the reason replay is safe later.

stage 1 — place an order and look at the outboxbash
curl -X POST -H 'Content-Type: application/json' \
     -d '{"customerId":"CUST-001","amountCents":4999,"status":"CREATED"}' \
     http://localhost:38081/api/orders

docker exec p3-postgres psql -U postgres -d ordersdb -c \
  "SELECT id, aggregate_type, aggregate_id, event_type, created_at
     FROM outbox ORDER BY created_at DESC LIMIT 10;"

The two rows come from two save calls under one annotation. The producer module's pom.xml has no Kafka dependency at all — it cannot dual-write, which is a stronger guarantee than a code review.

OrderService#createOrder — the whole point of the projectjava
// ---------------------------------------------------------------
// THE ONE TRANSACTION. Two INSERTs, one COMMIT, one durability
// decision. Nothing between these two lines may talk to a broker,
// an HTTP endpoint, or anything else that can fail independently.
// ---------------------------------------------------------------
orderRepository.save(order);
outboxEventRepository.save(outboxEvent);

For stage 3, open kafka-ui and select orders.events. The record's key is the order id (from aggregate_id), its value is the payload column expanded into a JSON object, and its headers carry eventId, eventType, traceId and aggregateType. Nothing in the producer chose a topic name.

stages 4 and 5 — the effect, and the ledger that makes it repeatablebash
docker exec p3-postgres psql -U postgres -d consumerdb -c \
  "SELECT order_id, customer_id, amount_cents, status, apply_count, updated_at
     FROM order_projection ORDER BY updated_at DESC LIMIT 10;"

docker exec p3-postgres psql -U postgres -d consumerdb -c \
  "SELECT count(*) AS processed_messages FROM processed_message;"

# apply_count = 1 is the assertion. 2 would mean the idempotency guard failed;
# 0 with a projection row present is impossible, because the row is only ever
# written by the same statement that sets the counter.

Break it on purpose

Four failure classes, four different paths through the topology. The status field on the order is the control channel: two reserved values drive the consumer into a retryable and a fatal failure without stubbing a downstream service.

A retryable failure walks the ladder

drive it, then watch the topics appearbash
make fail-retryable
# == curl ... -d '{"customerId":"CUST-RETRY","amountCents":4999,
#                  "status":"SIMULATE_RETRYABLE_FAILURE"}'

docker exec p3-kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka:19092 --list | sort
# orders.events
# orders.events-dlt
# orders.events-retry-5000        <- created lazily, on first use
# orders.events-retry-30000
# orders.events-retry-180000

The topic names carry their backoff because the listener uses TopicSuffixingStrategy.SUFFIX_WITH_DELAY_VALUE. That is not cosmetic: it means kafka-topics.sh --list is the documentation of the ladder, and a tier that silently collapsed into another one would be visible as a missing topic.

application.yml — where 5s/30s/180s comes fromyaml
app:
  retry:
    # attempts counts the FIRST delivery as attempt 1, so 4 attempts means the
    # main topic plus three retry topics, then the DLT.
    attempts: 4
    initial-delay-ms: 5000
    multiplier: 6.0
    max-delay-ms: 300000

While the record is on the ladder, query processed_message: it is empty. The marker insert and the business effect share one transaction, so a failed attempt leaves no trace at all. That is the property that makes redelivery correct rather than merely tolerated.

Two tiers clamped to the same delay become one topic

The suffix is the delay, so if max-delay-ms clamps attempt 3 and attempt 4 to the same value, both resolve to the same topic name and Spring's default reuse strategy folds them into a single shared topic. You then get four attempts across three tiers and the ladder you drew on the whiteboard does not exist. With 5000 × 6.0 the ladder reaches 180000 and never touches the 300000 ceiling — check that arithmetic every time you change a multiplier. Setting app.retry.multiplier=7.75 is the exercise that puts the third tier exactly on the cap.

A fatal failure skips it

the exclude list, in the annotationjava
@RetryableTopic(
        attempts = "${app.retry.attempts}",
        backoff = @Backoff(
                delayExpression = "${app.retry.initial-delay-ms}",
                multiplierExpression = "${app.retry.multiplier}",
                maxDelayExpression = "${app.retry.max-delay-ms}"),
        topicSuffixingStrategy = TopicSuffixingStrategy.SUFFIX_WITH_DELAY_VALUE,
        dltStrategy = DltStrategy.FAIL_ON_ERROR,
        exclude = { NonRetryableException.class, DeserializationException.class },
        traversingCauses = "true",
        kafkaTemplate = "retryKafkaTemplate",
        listenerContainerFactory = "kafkaListenerContainerFactory")

traversingCauses = "true" is what makes the exclusion work at all. A DeserializationException arrives wrapped in a ListenerExecutionFailedException; a classifier that looked only at the thrown type would see the wrapper, decide it was retryable, and spend 3.5 minutes proving that bytes which are not JSON now are still not JSON later. Run make fail-fatal and confirm no -retry- topic is touched.

A poison pill that does not stop the partition

publish bytes that are not JSON, straight past the producerbash
echo 'poison-key:{"eventId":"not-a-uuid", broken json <<<' | \
  docker exec -i p3-kafka /opt/kafka/bin/kafka-console-producer.sh \
    --bootstrap-server kafka:19092 --topic orders.events \
    --property "parse.key=true" --property "key.separator=:"

Without ErrorHandlingDeserializer this is a permanent outage. The exception is thrown inside KafkaConsumer.poll() — before any listener, error handler or offset commit exists — so the container catches it, logs, and polls the same offset again, forever. One malformed byte, one dead partition, and the only fix is a manual offset seek.

KafkaConfig — the wrapper that turns a poll-time crash into a routable recordjava
JsonDeserializer<OrderEvent> jsonDeserializer =
        new JsonDeserializer<>(OrderEvent.class, objectMapper, false);
jsonDeserializer.addTrustedPackages("com.acme.consumer.model");

return new DefaultKafkaConsumerFactory<>(
        props,
        new StringDeserializer(),
        new ErrorHandlingDeserializer<>(jsonDeserializer));

Now the value deserialises to null, the exception is stashed in a header, the record reaches the container, and the error handler routes it like any other failure. Verify two things: the DLT holds exactly one record whose bytes equal what you published, and a normal order placed afterwards still lands in the projection.

A poison pill never appears in dlq_record

make dlq-table will not show it, and that is not a bug. The DLT's own listener container deserialises with the same JsonDeserializer that already rejected the bytes once, so @DltHandler is never invoked for it — with DltStrategy.FAIL_ON_ERROR the framework logs and moves on rather than republishing to the DLT in a loop. The record is in the topic, byte for byte. Read it with make dlq-describe, which is exactly why the inspector reads byte[] and never deserialises anything.

A duplicate that only lands once

Republish an event that has already been applied — a replay, a Debezium re-emit after a connector restart, or literally the same curl against the DLQ inspector. The effect must not repeat.

IdempotentProcessor#process — marker and effect, one transactionjava
int inserted = jdbcTemplate.update(INSERT_MARKER, /* ... ON CONFLICT (event_id) DO NOTHING */);

if (inserted == 0) {
    // The unique constraint on processed_message.event_id did its job. Note that we return
    // normally rather than throwing: a duplicate is a success, not an error. Throwing here
    // would send perfectly healthy redeliveries to the DLT.
    log.info("Duplicate event {} for order {} from {}-{}@{} - effect already applied, skipping",
            event.eventId(), event.orderId(), topic, partition, offset);
    return false;
}

The assertion is apply_count. The projection upsert increments it on every application, so "was this applied twice?" is a SQL question with a numeric answer: 1 means the guard held, 2 means it did not, 0 means nothing was consumed at all. The dedupe key is the producer-assigned eventId — not the offset, which changes the moment a record is forwarded to a retry topic, and not a payload hash, which collides with legitimately identical events.

Stop the consumer, produce, restart

build a backlog, then watch it drainbash
# 1. Ctrl-C the `make run-consumer` terminal.
# 2. Place ten orders. They all commit - the producer has no Kafka client to be
#    blocked by, so the outbox grows and the pipeline is simply behind.
for i in $(seq 1 10); do make order AMOUNT=$((1000 + i)); done

# 3. Lag, per partition, from outside the application:
docker exec p3-kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server kafka:19092 --describe --group order-consumer

# 4. Restart the consumer. It resumes from its COMMITTED offsets, not from the
#    beginning, and LAG returns to 0 within a poll or two.

The same experiment works one level further out: docker compose stop kafka, place ten orders, confirm they all commit and the outbox grows, then docker compose start kafka and watch Debezium drain the backlog from the WAL. That is the property a dual write cannot give you — the broker being down is a latency problem here, not a data-loss problem.

auto-offset-reset: earliest is only safe because of the ledger

It applies when the group has no committed offset — a fresh group, or one whose offsets aged out of __consumer_offsets (broker default retention is 7 days of group inactivity). At that point the consumer replays the entire topic. With processed_message in place that is a no-op storm; without it, it is every order reapplied. Choosing earliest without an idempotent consumer is choosing to reprocess history the first time a group goes idle over a long weekend.

The CLI you will actually use

These run inside the broker container, where the scripts live at /opt/kafka/bin. The bootstrap address there is kafka:19092 — the internal listener. It cannot be the host one: PLAINTEXT_HOST advertises localhost:39092, and a client running inside the broker would bootstrap fine and then be redirected to a port nothing in that container is listening on. Same trap as before, mirrored.

Lag on a retry topic means something different

A retry-topic partition is paused, not slow: its container holds the assignment and deliberately does not poll until the backoff elapses. Non-zero lag on orders.events-retry-180000 for up to three minutes is the design working. Lag on orders.events is the number that means what you think it means. Alerting on both with the same threshold produces a pager that cries wolf every time one order fails.

Triage and replay

The inspector is a plain kafka-clients fat jar — no Spring context, no datasource, ~15 MB — because a tool you reach for during an incident should start in under a second and have nothing unrelated to Kafka that can fail.

the triage loopbash
java -jar tools/target/dlq-inspector.jar list --bootstrap localhost:39092 \
     --dlt-topic orders.events-dlt
# one line per record + a breakdown by exception class

java -jar tools/target/dlq-inspector.jar list --exception NonRetryable --since 2h
java -jar tools/target/dlq-inspector.jar describe --partition 0 --offset 3
# every header decoded, the payload pretty-printed, the full stack trace

java -jar tools/target/dlq-inspector.jar replay --exception RetryableException
# DRY RUN - prints exactly what would be sent, sends nothing

java -jar tools/target/dlq-inspector.jar replay --exception RetryableException --execute

Two design choices in the tool are worth copying. It assigns partitions manually and never commits an offset, so running it cannot disturb the application's own DLT consumer and running it twice shows the same records. And replay is dry by default — replaying a bad batch onto a production topic is a very expensive way to learn the flag ordering.

kafka_dlt-original-topic names the LAST hop, not the first

Each forward along the ladder overwrites that header, so a record that walked all three tiers reports orders.events-retry-180000. Replaying naively onto that value puts the record back on a retry topic, where the retry container picks it up immediately (the backoff header was stripped) and the main topic's consumer semantics are skipped entirely. The tool strips the suffix to recover the real origin:

/** Removes a trailing {@code -retry-<delay>} (optionally {@code -<index>}) suffix. */
static String stripRetrySuffix(String topic) {
    return topic.replaceFirst("-retry-\\d+(-\\d+)?$", "");
}

A replayed record starts a fresh life: every kafka_dlt-, retry_topic- and x-dlq- header is dropped, or the next failure's diagnostics would describe the previous incident. Application headers such as traceId survive, plus one x-replayed-from-dlt breadcrumb. The DLT keeps the originals — replay never deletes.

Fix the cause before you press --execute

Replaying into an unfixed consumer just refills the DLT, and each pass adds another x-replayed-from-dlt header to records that are already hard to read. The one case where replaying immediately is correct is when the failure was genuinely transient and the ladder simply ran out of tiers before the downstream recovered — which is what the x-dlq-classification header (RETRIES_EXHAUSTED / NON_RETRYABLE / DESERIALIZATION) exists to tell you without parsing stack traces.

Running the tests

make test is mvn verify. The consumer's integration tests start real Kafka and PostgreSQL containers through Testcontainers, publish real records and assert on real topics — Docker must be running, and the first run pulls apache/kafka:4.0.0.

AbstractIntegrationTest — the ladder compressed to millisecondsjava
@SpringBootTest(
        classes = ConsumerApplication.class,
        properties = {
                "app.retry.attempts=4",
                "app.retry.initial-delay-ms=100",
                "app.retry.multiplier=3.0",
                "app.retry.max-delay-ms=60000",
                "spring.kafka.consumer.group-id=order-consumer-it",
                ...
        })
// Topic names follow the delays, so under these overrides the ladder is
// orders.events-retry-100 / -retry-300 / -retry-900. The multiplier and max
// delay are chosen so no two tiers clamp to the same value, which would make
// Spring fold them into a single shared topic.

Four attempts, three retry topics, one DLT — the topology is identical and only the clock changes, which is exactly what you want from a test of routing behaviour. The tests then assert the two things a compressed clock cannot fake: the tiers were visited in ascending timestamp order, and reaching tier three took at least 100 + 300 ms, proving the backoff was applied rather than skipped.

The sentinel trick — how the idempotency tests avoid sleeps

Naively you publish the duplicate, sleep, and hope. Instead every test publishes a sentinel event on the same Kafka key after the records under test. Same key means same partition, and a partition is consumed strictly in order, so the moment the sentinel's row appears in processed_message the earlier records are guaranteed to have been consumed and committed. The assertion then runs against a settled system with no sleeps and no flakiness. This generalises: order on a partition is a synchronisation primitive you already have.

Exercises

Each one changes real behaviour. Verify with the tests or the CLI rather than by reading — if you cannot state the observable difference before you start, the exercise is not finished when the code compiles.

  1. Add exactly-once with Kafka transactions. Wrap the consume–process–produce step in a transactional producer (transactional.id, sendOffsetsToTransaction) so the projection write and the offset commit land atomically. Then write down what you still have not solved: Debezium's leg into Kafka is unchanged, and the database write is in a different resource manager from the offsets. Conclusion to reach on your own: Kafka transactions remove one duplicate source, not the need for the ledger.
  2. Add a schema registry with Avro. Replace the JsonConverter in the connector with AvroConverter and the consumer's JsonDeserializer with the Avro equivalent, both pointed at a registry container. Done when a producer-side field rename is rejected at registration time instead of surfacing as a NonRetryableException in your DLT an hour later.
  3. Alert on consumer lag. Export kafka_consumergroup_lag and page on sustained lag against orders.events only. Explain in the alert's runbook why the same threshold on orders.events-retry-180000 would fire on every single failed order.
  4. Implement the inbox pattern. Today the consumer applies the effect inline. Instead, write the raw event into an inbox table in the same transaction as the marker and process it from a separate worker. Compare: what does this buy when the business effect is slow or calls a third party, and what does it cost in end-to-end latency and in one more table to operate?
  5. Trace the whole pipeline. The traceId is already generated in OrderService and carried as a Kafka header by the SMT. Wire OpenTelemetry so one trace spans the HTTP request, the Debezium relay, the consumer, and every retry hop. The hard part is that the CDC leg has no in-process continuation — you must reconstruct the parent from the header, and decide whether a 180-second retry wait belongs in the same trace at all.
  6. Partition the outbox. Convert outbox to a PARTITION BY RANGE (created_at) table with daily partitions, so retention becomes DROP PARTITION instead of the DELETE in OrderService#purgeOldOutboxRows. Confirm Debezium still streams it, then explain why dropping a partition is cheap for autovacuum and a bulk DELETE is not.
  7. Handle a schema change in the source table. Add a V2 migration renaming outbox.aggregate_id to entity_id without touching the connector. Watch connector-status go to FAILED, read the SMT's error, and fix table.field.event.key. This is the coupling the outbox pattern really has, and it is invisible until you break it.
  8. Delete the idempotency guard. Comment out the zero-rows-inserted early return. IdempotencyTest#duplicateEventIsAppliedOnce must fail with apply_count = 2. Put it back.
  9. Move the marker out of the transaction. Write it from a method annotated @Transactional(propagation = REQUIRES_NEW) before the effect, then publish a retryable failure. The record walks the ladder, but the marker is already committed, so every retry is silently skipped and the event is lost. This is the single most common idempotency bug in production systems.
  10. Make retries blocking. Remove @RetryableTopic and give the DefaultErrorHandler a FixedBackOff(30_000L, 4L). Publish one failing order and ten good ones on the same partition, and time how long the good ones take. Then compute what happens when the backoff exceeds max.poll.interval.ms.
  11. Remove the byte-passthrough serializer. Swap PayloadOrRawBytesSerializer for a plain JsonSerializer and run the poison pill test. Inspect what actually lands in the DLT, and note that the corruption is silent.
  12. Add a second aggregate. Emit aggregate_type = "shipments" from a new endpoint. A shipments.events topic appears with no connector change at all — routing is data, not configuration. Now decide whether that is a feature or a way to create production topics by typo.

What to take away

  1. A single broker advertises two addresses and the correct one depends on which side of the container boundary you are on: kafka:19092 for containers, localhost:39092 for host JVMs (the broker's 9092 published on the host as 39092). The failure happens on the metadata hop, not the connect, which is why the error message never says "wrong listener".
  2. Deleting a Debezium connector leaves its replication slot behind, and an inactive slot pins every WAL segment after confirmed_flush_lsn until the disk fills. Alert on pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn), and drop slots deliberately.
  3. Follow the eventId, not the offset. It is minted inside the producer's transaction, travels as an outbox primary key, a Kafka header, a payload field and a processed_message row — which is why replayed and re-emitted records are recognisable as duplicates and why apply_count is a one-query correctness check.
  4. The exclude list plus traversingCauses = "true" is the difference between a fatal defect surfacing in milliseconds and an operator learning about it 3.5 minutes later. Retrying a message that cannot be parsed is pure waste; retrying a timeout is the entire point.
  5. A poison pill reaches the DLT but never reaches @DltHandler, so it is absent from dlq_record by design — the DLT container cannot deserialise it either. Any DLQ workflow that reads only your archive table will silently miss exactly the failures you most need to see; the byte-level inspector is not a nicety.
  6. kafka_dlt-original-topic is the last hop, not the first. Strip the -retry-<delay> suffix before replaying, strip the framework headers so the next failure describes itself, and keep replay dry-run by default.
  7. Lag on the main topic means the consumer is behind; lag on a retry topic means a partition is deliberately paused mid-backoff. They are different signals and one threshold for both makes the alert useless.
