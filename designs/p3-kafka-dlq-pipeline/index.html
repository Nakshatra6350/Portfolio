Resilient Kafka Pipeline: Outbox, CDC & DLQ

An order service that writes its business row and its event row in one local PostgreSQL transaction, Debezium relaying that outbox to Kafka by reading the write-ahead log, and a consumer that applies each event once, classifies its failures, walks a ladder of non-blocking retry topics, and parks what it cannot handle in a dead letter topic carrying enough context to actually diagnose and replay it. Every mechanism in the repository exists because a specific failure mode makes the naive version wrong.

The one hard problem this project exists to teach

You cannot atomically change a database and publish a message. They are two independent commit points with no coordinator between them, and there is no ordering of the two that is correct.

Database first, broker second: the process dies after COMMIT and the event is gone forever — an order that exists and that nothing downstream will ever hear about. Broker first, database second: the insert hits a constraint and rolls back, and downstream systems ship and invoice an order that does not exist. Wrap send() in a retry loop and you have duplicates instead, with no dedup key you control, and the process can still die mid-loop. XA would solve it; Kafka does not implement XA.

The transactional outbox does not coordinate the two commits — it deletes one of them. The event becomes a row in the same database, written by the same transaction as the business change, and publishing becomes an at-least-once delivery problem for a CDC connector rather than a correctness problem for the service.

That is the trade you are actually learning, because it produces the rest of the project: once delivery is at-least-once, every effect downstream must be idempotent, every failure must be classified as retryable or not, retries must not block the partition they are on, and whatever survives all of that has to land somewhere a human can query, understand and replay. The outbox is one file. The consequences are the other twenty.

What you will build

Three Maven modules and a Compose stack. The producer on :38081 exposes POST /api/orders and does exactly one interesting thing: inserts into orders and into outbox inside a single @Transactional method. Its pom.xml has no Kafka dependency at all — it is structurally incapable of dual-writing.

Debezium 3.1 in Kafka Connect tails the outbox through a pgoutput logical replication slot and applies the EventRouter SMT, which turns aggregate_type into the topic name, aggregate_id into the record key and the payload jsonb column into the record value. Nothing in the producer chose a topic. The consumer on :38082 deserialises defensively, applies each event under an idempotency ledger, and routes failures down a 5s → 30s → 180s ladder of delay topics before dead-lettering them. A CLI reads the dead letter topic at byte level and replays it, dry-run by default.

Kafka 4 broker, 3.8 client — on purpose

The broker image is apache/kafka:4.0.0, but kafka-clients stays at the version Spring Boot 3.4.1 manages — 3.8.1, which you can confirm with mvn help:evaluate -Dexpression=kafka.version. Kafka’s client/broker protocol is bidirectionally compatible and Spring Kafka 3.3.1 is certified against the 3.8 clients it ships with; forcing 4.0 clients into the reactor compiles fine and can then fail at runtime on APIs Kafka 4 removed. Debezium 3.1 is used because it is the first line built against Kafka 4.

Quick start

JDK 17 (exactly — no Java 21 syntax is used), Maven 3.9+, and Docker with Compose v2 and --wait. Roughly 4 GB of free memory for the containers. Host ports used: 35432 postgres, 38080 kafka-ui, 38081 producer, 38082 consumer, 38083 Connect, 39092 Kafka. Inside the Compose network the containers still talk to postgres:5432, connect:8083 and kafka:19092 — only the published host side moves, so this project can run alongside the other projects and a natively installed database.

bring the pipeline upbash
cd 10-projects/p3-kafka-dlq-pipeline/code

# 1. infrastructure. --wait blocks until every healthcheck passes.
make up

# 2. register the Debezium connector -- this creates the replication slot
#    and the publication, so it must come after postgres is healthy.
make connector
make connector-status      # expect state RUNNING for both connector and task

# 3. build all three modules (the DLQ inspector fat jar comes out of this too)
make build
two more terminals, then trafficbash
make run-consumer          # :38082 -- leave it running, watch the retry decisions
make run-producer          # :38081 -- leave it running

make order                 # a normal order, end to end
make outbox                # the row Debezium will pick up
make projection            # it landed in the consumer's read model, apply_count = 1
the three failure paths, and triagebash
make fail-retryable        # walks 5s -> 30s -> 180s, then dead-letters (~3.5 min)
make fail-fatal            # NonRetryableException: straight to the DLT, no retry topic touched
make poison                # malformed bytes published directly to orders.events
make topics                # the retry tiers appear, named after their delay in ms

make dlq-list              # summary and breakdown by exception class
make dlq-describe          # every header, the payload, the stack trace
make replay                # DRY RUN -- shows what would be sent, sends nothing
make replay-execute        # actually republish to the resolved original topic
tests, and the same thing without makebash
make test                  # mvn verify -- Testcontainers, so Docker must be running

docker compose up -d --wait
curl -X POST -H 'Content-Type: application/json' \
     --data @connectors/outbox-connector.json http://localhost:38083/connectors
mvn clean package -DskipTests
mvn -pl consumer -am spring-boot:run
mvn -pl producer -am spring-boot:run
curl -X POST -H 'Content-Type: application/json' \
     -d '{"customerId":"CUST-001","amountCents":4999,"status":"CREATED"}' \
     http://localhost:38081/api/orders
The retry ladder takes real wall-clock time

make fail-retryable does not produce a dead letter you can inspect straight away. The delays are 5s, 30s and 180s, so the record reaches orders.events-dlt roughly three and a half minutes later — and while it waits, the consumer keeps processing the main topic normally, which is the entire point. Running make dlq-list immediately and seeing nothing means the ladder is working, not that it is broken. The integration tests override the tiers to 100ms/300ms/900ms so the topology is unchanged and only the clock is compressed; make fail-fatal and make poison reach the DLT within milliseconds because neither one touches a retry topic.
