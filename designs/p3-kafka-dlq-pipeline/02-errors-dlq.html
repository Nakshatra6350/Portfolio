Retries, DLQ & poison pills

The consumer half of the project, read as a series of forced choices: why one bad message can stop a partition forever, why classifying every failure as retryable wedges the consumer and classifying everything as fatal loses data, what the tiered retry topics cost you in ordering, and why a try/catch in the listener body cannot see a deserialisation failure at all.

The mental model for the whole consumer

A Kafka partition is a single cursor, not a queue you can take items out of. There is no "ack this one, nack that one" — there is one committed offset per partition per group, and it can only move forwards. Every error-handling mechanism in this project exists because of that one fact. You cannot skip a message without abandoning it, and you cannot hold a message without holding everything behind it. So the only workable answer is to move the failure somewhere else — to a retry topic, or to the DLT — and let the cursor advance. Error handling here is a routing problem, not a try/catch problem.

One bad message blocks its partition

Start with the failure the naive consumer has. The listener throws, the container catches, the offset is not committed, and the next poll() returns the same record. There is nothing wrong with that loop — it is exactly what at-least-once delivery means. The problem is that the partition has 50 other orders behind that record and none of them can be delivered until the cursor moves.

Classification, and why the two easy answers are both wrong

Before you can route a failure you have to say what kind it is, and there are only two useful kinds. Treating everything as retryable means a message with a missing eventId occupies the ladder for three and a half minutes and then reaches the DLT anyway — you paid the full latency to learn nothing, and if the defect is systematic you have just multiplied your broker traffic by four. Treating everything as fatal means one 503 from a downstream service dead-letters a perfectly good order that would have succeeded on the next attempt. Both defaults are data loss or wasted time dressed as a policy.

The project makes the decision explicit with two exception types, and the javadoc on each one is the test you apply at the throw site.

consumer/error/RetryableException.java — the question to askjava
/**
 * A failure that a later attempt could plausibly succeed at.
 *
 * <p>Throw this for transient infrastructure conditions: a downstream HTTP call timed out, a
 * connection pool was exhausted, a row was locked, a rate limit was hit, a dependency returned 503.
 * The defining question is <em>"would the identical message, replayed in five minutes, have a real
 * chance of working?"</em> If yes, it is retryable.
 */
public class RetryableException extends RuntimeException { ... }
consumer/error/NonRetryableException.java — the short circuitjava
/**
 * A failure that no amount of retrying will fix.
 *
 * <p>Throw this for defects in the message or in the business rules applied to it: a required field
 * is missing, an enum value is unknown, a referenced entity can never exist, the amount is
 * negative, a schema version is unsupported. Replaying such a message in five minutes produces the
 * same exception, so the retry ladder would only burn broker storage and delay the operator's
 * discovery of a real bug.
 */
public class NonRetryableException extends RuntimeException { ... }

The classification is applied in exactly one place — the annotation's exclude list — and everything not named there is retryable by default. That default is the right way round: a new exception type you forgot to classify gets retried and then dead-lettered with full diagnostics, rather than being silently discarded.

The classifier must walk the cause chain, or it never fires

Your NonRetryableException does not arrive at the classifier naked. Spring wraps it in a ListenerExecutionFailedException; a DeserializationException arrives wrapped too, and itself wraps the underlying Jackson error. A classifier that looks only at e.getClass() sees the wrapper and routes every fatal defect onto the retry ladder. That is what traversingCauses = "true" is for, and it is why the DLT's own triage label is computed by walking down from the top rather than jumping to the root cause:

private static String classify(Throwable exception) {
    for (Throwable current = exception; current != null; current = current.getCause()) {
        if (current instanceof DeserializationException) {
            return "DESERIALIZATION";
        }
        if (current instanceof NonRetryableException) {
            return "NON_RETRYABLE";
        }
        if (current.getCause() == current) {
            break;                       // self-referential cause: stop, do not spin
        }
    }
    return "RETRIES_EXHAUSTED";
}

Inspecting only the deepest cause would classify every poison pill as a generic Jackson parse failure and lose the distinction the operator actually needs.

Blocking versus non-blocking retries

The blocking version is one line of configuration and it is what most services ship with: a DefaultErrorHandler holding a BackOff. The consumer thread sleeps between attempts. That thread owns the partition, so the sleep is a stall for every other order on it, and once the total sleep approaches max.poll.interval.ms the broker declares the consumer dead and rebalances — into a loop, because the new owner starts the same sleep.

This project uses @RetryableTopic instead, and deliberately configures the fallback handler to do no in-memory retry at all so the two mechanisms cannot compound:

consumer/config/KafkaConfig.java — the non-@RetryableTopic fallbackjava
/**
 * <p>{@code FixedBackOff(0, 0)} means "no in-memory retry at all": recover immediately. In-memory
 * retry blocks the consumer thread and therefore the whole partition, which is exactly the
 * property the retry topics were introduced to avoid. Retrying in two places at once just
 * multiplies the delays.
 */
@Bean
public DefaultErrorHandler defaultErrorHandler(DeadLetterPublishingRecoverer recoverer) {
    DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, new FixedBackOff(0L, 0L));
    handler.addNotRetryableExceptions(NonRetryableException.class);
    handler.setAckAfterHandle(true);
    handler.setLogLevel(org.springframework.kafka.KafkaException.Level.WARN);
    return handler;
}

The ordering trade, stated out loud

From OrderEventListener's own javadoc: if orders A1 and A2 share a key and A1 fails, A2 is processed while A1 is parked on orders.events-retry-5000. When A1 eventually succeeds it is applied after A2. For a projection of independent facts that is fine and the idempotency ledger keeps replays safe. For a state machine it is corruption: "order shipped" applied before "order paid" is not a delay, it is wrong data. When strict per-key ordering matters you must either block the partition and accept the stall, or park the whole key — stop consuming it, buffer subsequent events, resume in order once the failure clears. Non-blocking retries are the right default; picking them without knowing which case you are in is how "impossible" ordering bugs get written.

Two tiers clamped to the same delay collapse into one topic

Because the suffix is the delay, a ladder whose later tiers both hit max-delay-ms produces two tiers with the same name, and Spring's default reuse strategy folds them into a single topic. You asked for five attempts and got four, silently. With initial-delay-ms=5000, multiplier=6.0 and a 300 s ceiling the third tier lands on 180 s and never reaches the cap, so nothing clamps. Change the multiplier to 7.75 and the third tier sits exactly on 300000; add a fourth and it collides. Check the topic list after any change to these three numbers — the count of retry topics is the only reliable confirmation of how many attempts you actually have.

max.poll.interval.ms is what the ladder is really budgeted against

A retry-topic partition is paused, not polled, for the whole backoff. If the longest tier exceeds max.poll.interval.ms the broker evicts the consumer mid-wait and the group rebalances continuously — the symptom is a consumer that never processes anything and a log full of "Attempt to heartbeat failed since group is rebalancing". This project sets max.poll.interval.ms: 900000 against a longest tier of 180 000 ms, a 5× margin. The check is per-tier, not on the total, but leave real room: the interval also has to cover the processing time of a full max-poll-records: 50 batch.

The dead letter record

A DLT record has one job: to let somebody who was not on call reconstruct the incident six weeks later, and then put the message back. That means diagnostics in headers and the payload byte-identical to what failed. Anything that rewrites the payload — a re-serialisation, a "cleanup", a schema upgrade — destroys the only artefact that proves what went wrong.

consumer/config/KafkaConfig.java — enriching what Spring cannot knowjava

Each forward overwrites it. A record that walked the whole ladder reports orders.events-retry-180000 — so a replay tool that trusts the header republishes onto a retry topic. That technically works (the retry container picks it up immediately, since the backoff header was stripped) but it skips the main topic's consumer-group semantics and it is thoroughly misleading in an incident. The inspector recovers the true origin with a regex:

/** Removes a trailing {@code -retry-<delay>} (optionally {@code -<index>}) suffix. */
static String stripRetrySuffix(String topic) {
    return topic.replaceFirst("-retry-\\d+(-\\d+)?$", "");
}
Header values are opaque bytes, and length is not the discriminator

There is no type system here, and the obvious decoder — switch on value.length — is wrong. Three producers touch a DLT record and they write numbers three different ways. Spring's DeadLetterPublishingRecoverer writes kafka_dlt-original-partition as a fixed-width 4-byte int and -offset/-timestamp as fixed-width 8-byte longs, and the retry infrastructure writes retry_topic-attempts as a 4-byte int. But retry_topic-original-timestamp and retry_topic-backoff-timestamp come from BigInteger#toByteArray(), which is variable width: an epoch-milli needs only 41 bits, so those headers arrive six bytes long, not eight. And this project's own x-dlq-* headers are decimal text, so an attempt count of 4 is one byte whose raw value is 52 — the ASCII code, not the number.

So the decoder reads decimal text first — a run of ASCII digits is unambiguous, because every binary encoding above starts with a magnitude byte far below '0' for any plausible count or timestamp — and otherwise hands the bytes to BigInteger, which reads two's-complement big-endian at any width and so covers the fixed-width 4- and 8-byte cases as a subset of the variable-width one:

private static long decodeNumericHeader(byte[] value, long defaultValue) {
    if (value == null || value.length == 0) {
        return defaultValue;
    }
    if (isDecimalText(value)) {
        try {
            return Long.parseLong(new String(value, StandardCharsets.UTF_8).trim());
        } catch (NumberFormatException ignored) {
            // Not text after all; fall through to the binary decode.
        }
    }
    if (value.length <= Long.BYTES) {
        return new java.math.BigInteger(value).longValue();
    }
    return defaultValue;
}

readIntHeader and readLongHeader are one-line wrappers over that. Matching on value.length == Long.BYTES instead would miss retry_topic-original-timestamp completely and silently return the default, which is exactly how a record that spent 3.5 minutes on the ladder gets archived as a fresh failure. The same decode is repeated verbatim in DlqInspector, which has no Spring dependency, and in AbstractIntegrationTest, so the tests cannot pass on a decode the application would get wrong.

Deserialisation failures, and why your try/catch cannot see them

This is the mechanism most people meet the hard way. Deserialisation does not happen in your listener. It happens inside KafkaConsumer.poll(), while the client is turning the fetch response into ConsumerRecord objects — before any container code, any error handler, any offset commit, and certainly before your method body. A try/catch around the listener is code that never runs. The container catches the exception from poll(), logs it, and polls the same offset again. Forever.

consumer/config/KafkaConfig.java — the poison pill defence, wiredjava
JsonDeserializer<OrderEvent> jsonDeserializer =
        new JsonDeserializer<>(OrderEvent.class, objectMapper, false);
// The producer is Debezium, not Spring, so there are no __TypeId__ headers to honour and
// nothing to strip. Target type comes from the constructor above.
jsonDeserializer.addTrustedPackages("com.acme.consumer.model");

return new DefaultKafkaConsumerFactory<>(
        props,
        new StringDeserializer(),
        new ErrorHandlingDeserializer<>(jsonDeserializer));

The second half of the defence is on the way out. When a poison pill is forwarded, the value being published is the original byte[] recovered from the DeserializationException — not an OrderEvent. A plain JsonSerializer would base64-encode those bytes into a JSON string, and the DLT would hold a mangled copy of the one thing you need to look at.

consumer/config/KafkaConfig.java — bytes in, bytes outjava
static final class PayloadOrRawBytesSerializer implements Serializer<Object> {
    @Override
    public byte[] serialize(String topic, Object data) {
        if (data == null) {
            return null;
        }
        if (data instanceof byte[] bytes) {
            return byteArraySerializer.serialize(topic, bytes);
        }
        if (data instanceof String string) {
            return stringSerializer.serialize(topic, string);
        }
        try {
            return objectMapper.writeValueAsBytes(data);
        } catch (Exception e) {
            // Failing to serialise a record on its way to the DLT would lose the failure
            // itself. Degrade to a readable marker instead of throwing.
            log.error("Could not serialise {} for topic {}; writing a diagnostic stub instead",
                    data.getClass().getName(), topic, e);
            return ("{\"serializationError\":\"" + e.getClass().getName()
                    + "\",\"type\":\"" + data.getClass().getName() + "\"}")
                    .getBytes(StandardCharsets.UTF_8);
        }
    }
}

The @DltHandler never sees a poison pill

The DLT container deserialises with the same JsonDeserializer that already rejected those bytes once, so it fails again. DltStrategy.FAIL_ON_ERROR logs and moves on, which is the safe outcome — the alternative, ALWAYS_RETRY_ON_ERROR, republishes the record to the DLT forever and you discover it as an unbounded topic. The consequence is that dlq_record has no row for a poison pill: the archive covers what could be parsed. Reading the raw bytes is what DlqInspector describe is for, and its best-effort printer says so explicitly — "<-- not valid JSON (this is the poison pill)".

The idempotent consumer

Every mechanism above is at-least-once. Debezium re-emits an outbox row after a connector restart whose offsets were not flushed; the consumer processes a record and dies before committing; a rebalance revokes a partition between processing and commit. None of those can be engineered away, so the consumer is built to make duplicates harmless instead. The guard is one insert with a unique constraint, in the same transaction as the effect.

consumer/service/IdempotentProcessor.java — the guardjava
@Transactional(propagation = Propagation.REQUIRED, isolation = Isolation.READ_COMMITTED)
public boolean process(OrderEvent event, String topic, int partition, long offset,
                       String consumerGroup) {

    validate(event);

    int inserted = jdbcTemplate.update(INSERT_MARKER,
            event.eventId(), topic, partition, offset, consumerGroup,
            new Timestamp(System.currentTimeMillis()));

    if (inserted == 0) {
        // The unique constraint on processed_message.event_id did its job. Note that we return
        // normally rather than throwing: a duplicate is a success, not an error. Throwing here
        // would send perfectly healthy redeliveries to the DLT.
        log.info("Duplicate event {} for order {} from {}-{}@{} - effect already applied, skipping",
                event.eventId(), event.orderId(), topic, partition, offset);
        return false;
    }

    // ---------------------------------------------------------------
    // The business effect. Still inside the same transaction as the
    // marker above, so the two commit or roll back as one.
    // ---------------------------------------------------------------
    simulateFailureIfRequested(event);
    applyToProjection(event);
    ...
}

READ_COMMITTED is deliberate and sufficient: two concurrent deliveries of the same event race on the processed_message primary key, and the loser either sees zero affected rows or blocks until the winner commits and then sees zero. Higher isolation buys nothing except serialisation failures.

Replay: the workflow and its safeguards

The DLT is not an archive you read; it is a queue you eventually drain. Replay is the drain, and it is the most dangerous operation in the whole pipeline — a mistyped filter republishes four thousand records onto a production topic. DlqInspector is built around that risk.

Replay is only safe because the consumer is idempotent

A replayed record is a duplicate by construction. If it had already been applied before the failure — say the effect committed and the DLT record came from a later, unrelated hop — the processed_message ledger rejects it and apply_count does not move. If it had not, it is applied normally. Without the ledger, "replay the DLT" and "double-charge every customer in it" are the same command. The correct order of operations is always: fix the cause, deploy, dry run, read the plan, then --execute.

Monitoring: three signals, and what each one means

The DLT is a metric, not just a topic. Three numbers cover almost every real incident, and they answer different questions — you need all three.

triage queries against the archive tablesql
-- What is failing, and is it one thing or many?
SELECT exception_class, count(*) AS n, max(dead_lettered_at) AS latest
FROM dlq_record
WHERE dead_lettered_at > now() - interval '1 hour'
GROUP BY exception_class
ORDER BY n DESC;

-- Fatal on sight, or exhausted the ladder? The gap is the whole diagnosis.
SELECT attempt_count,
       count(*),
       avg(dead_lettered_at - first_failure_at) AS avg_time_failing
FROM dlq_record
GROUP BY attempt_count
ORDER BY attempt_count;

-- Is anybody draining the DLT?
SELECT now() - min(dead_lettered_at) AS oldest_untriaged, count(*) AS backlog
FROM dlq_record;
Retention asymmetry is deliberate

orders.events keeps 7 days; orders.events-dlt keeps 30, with cleanup.policy=delete. A DLT that expires before anyone triages it is a deleted incident report. The asymmetry also means you can still replay a record whose original has aged out of the main topic — the DLT carries the payload, so publishing it back does not depend on the source still existing.

What to take away

  1. A partition is one cursor. You cannot skip or hold a single message, so every error-handling design reduces to where do I move the failure — a retry topic, the DLT, or nowhere, in which case the partition stalls.
  2. Classification is the only decision that matters, and it has exactly one right question: would the identical bytes, replayed in five minutes, have a real chance of working? Retryable by default is the safe polarity — an unclassified exception should be retried and dead-lettered loudly, not discarded.
  3. The classifier must traverse causes. NonRetryableException arrives wrapped in ListenerExecutionFailedException, and DeserializationException wraps the Jackson error underneath it — a check on e.getClass() matches neither.
  4. Non-blocking retries buy a partition that never stalls and cost per-key ordering for the failing key. That is a data-model decision, not a config decision: fine for a projection of independent facts, corruption for a state machine.
  5. Naming retry topics after their delay makes the ladder readable from kafka-topics.sh --list, and it makes a clamped tier visible as a collision instead of a silently missing attempt. Budget the longest single tier against max.poll.interval.ms — here 180 s against 900 s.
  6. Deserialisation happens inside poll(), so no try/catch in your listener can ever see it. ErrorHandlingDeserializer converts an unroutable exception into a routable record; the forwarding serializer must then pass byte[] through untouched, or the DLT holds a mangled copy of the evidence.
  7. The idempotency marker and the business effect must share one transaction. Committing the marker separately is the single most common bug in this pattern: the effect fails, the retry is skipped as a duplicate, and the event is lost while every metric reports success.
  8. Replay is dry by default, strips framework headers, recovers the true origin topic from the -retry-<delay> suffix, and never deletes. Alert on the retry rate, not just the DLT depth — it moves 3.5 minutes earlier.
