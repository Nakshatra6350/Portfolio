The dual-write problem & outbox

Why save() then send() has no safe ordering, why XA is not available to you on Kafka, and how one extra INSERT plus PostgreSQL's write-ahead log turns publishing from a correctness problem for your service into a retry problem for a connector.

Java 17 Spring Boot 3.4.1 Kafka 4 PostgreSQL 16 Debezium outbox & CDC
The mental model that matters

A dual write is not "two things that might fail" — it is two independent commit points with no coordinator between them. Nothing you write inside your service can fix that, because the fix has to be a shared durability decision and there is only one storage engine you can enlist. So the outbox pattern does not coordinate the second commit; it deletes it. The event becomes a row in the same database, written by the same transaction, and a separate process later turns rows into records. Delivery then has exactly the property delivery is allowed to have: it can be retried forever, because the truth is already durable.

Two commit points, no coordinator

The version everybody writes first is two lines long, and it is documented in this project's own source as the thing the design exists to avoid:

the broken shape, from OrderService's class javadocjava
orderRepository.save(order);        // (1) commits
kafkaTemplate.send("orders", evt);  // (2) may or may not happen

Swapping the two lines does not help, and neither does wrapping the second one in a retry loop. Each ordering fails differently, and each failure is worse than "an error the caller sees" — they are all silent divergence between two systems that each believe they are correct.

"We wrapped it in @Transactional and it's fine now"

Putting kafkaTemplate.send() inside a Spring transaction does nothing for atomicity by default: the send is executed immediately and the broker knows nothing about your database transaction. Registering it as an afterCommit callback (the TransactionSynchronization trick, or an @TransactionalEventListener(phase = AFTER_COMMIT)) is strictly better — it removes the "phantom event for a rolled-back order" case — but it is exactly the "DB first, Kafka second" row above. The process can be killed in the microsecond between COMMIT returning and the callback running, and that event is gone with no record anywhere that it was ever owed.

The candidates, and why four of them lose

ApproachHow it would workVerdict
XA / two-phase commitA transaction manager prepares both resources, then commits bothNot available. Kafka exposes no XA resource adapter. Kafka transactions are Kafka-internal — they scope producer writes and consumer offset commits on the same cluster, and cannot enlist a JDBC connection. Even where XA exists it buys a blocking coordinator, in-doubt transactions that hold locks until an operator resolves them, heuristic outcomes, and latency measured in extra round trips per write.

Listen to yourselfThe service publishes the command/event, then consumes its own topic and writes the row from the consumerRejected here. It is genuinely atomic — there is only one commit point — but it makes Kafka the system of record and the database a projection. The HTTP caller gets 201 before the row exists, so read-your-writes breaks; you cannot enforce a uniqueness or CHECK constraint at accept time, only discover the violation later on a topic you cannot reject from; and your write path is now down whenever the broker is down. One INSERT, no read-back, no marker column, no extra load on the primary, and sub-second latency. Pays for it with an operational dependency (Kafka Connect) and a replication slot you must monitor.
Kafka transactions solve a different problem

enable.idempotence + transactional.id gives you exactly-once consume–transform–produce within Kafka: reading from topic A, writing to topic B and committing the offset atomically. That is real and useful, and this project's consumer sets enable.idempotence: true on its forwarding producer for the ordering guarantee it brings. It does not and cannot make a PostgreSQL COMMIT atomic with a Kafka send().

The outbox table is a public contract

The outbox is not a generic "events" table. Every column name in it is named again in the connector configuration, which means the DDL is an interface with an external consumer, not an implementation detail you can refactor.

Renaming an outbox column kills the connector, not the service

Rename aggregate_id to entity_id in a V2 migration and your producer keeps returning 201, your tests keep passing, and orders keep committing. Debezium keeps streaming too — it is the SMT that throws, and with errors.tolerance=none the task dies. The pipeline goes silent while the service looks perfectly healthy. This is the coupling the pattern really has, and it is why the migration file carries that comment. Monitor GET /connectors/outbox-connector/status, and alert on outbox rows written in the last five minutes (the producer exposes /api/orders/outbox/recent-count for exactly this) against records produced to orders.events.

The one transaction

Everything above exists so that this method can be boring. Two saves, one @Transactional, no I/O of any kind between them:

producer · OrderService#createOrder — the whole point of the projectjava
@Transactional(propagation = Propagation.REQUIRED)
public Order createOrder(String customerId, long amountCents, String status, String traceId) {
    Order order = Order.place(customerId, amountCents, status);

    UUID eventId = UUID.randomUUID();
    String effectiveTraceId = (traceId == null || traceId.isBlank())
            ? UUID.randomUUID().toString().replace("-", "").substring(0, 32)
            : traceId;

    OrderCreatedPayload payload = new OrderCreatedPayload(
            eventId, order.getId(), order.getCustomerId(),
            order.getAmountCents(), order.getStatus(), order.getCreatedAt());

    String payloadJson = serialise(payload);

    OutboxEvent outboxEvent = OutboxEvent.of(
            eventId, aggregateType, order.getId().toString(),
            eventTypeCreated, payloadJson, effectiveTraceId);

    // ---------------------------------------------------------------
    // THE ONE TRANSACTION. Two INSERTs, one COMMIT, one durability
    // decision. Nothing between these two lines may talk to a broker,
    // an HTTP endpoint, or anything else that can fail independently.
    // ---------------------------------------------------------------
    orderRepository.save(order);
    outboxEventRepository.save(outboxEvent);

    return order;
}

Three details in there are load-bearing. The order id is a client-generated UUID from Order.place(), not a database sequence — the outbox row must reference it before either INSERT is flushed, and application-assigned identifiers remove the "flush to get the id" dance entirely. The eventId is generated here, inside the transaction, and written in two places: as the outbox primary key and inside the serialised payload. And serialisation happens inside the transaction on purpose:

a failure to serialise must roll the order backjava
private String serialise(OrderCreatedPayload payload) {
    try {
        return objectMapper.writeValueAsString(payload);
    } catch (JsonProcessingException e) {
        // Thrown inside the transaction, so the order insert rolls back with it. An order whose
        // event cannot be serialised must not exist.
        throw new IllegalStateException("Could not serialise outbox payload for order "
                + payload.orderId(), e);
    }
}

Relay: polling publisher versus CDC

With the write side settled, the only remaining question is who turns rows into records. Both answers are at-least-once; they differ in cost and in what they do to your primary.

The retention purge can delete an event that was never published

The outbox is a queue, not an audit log; left alone it grows without bound and every autovacuum pass gets more expensive. But the DELETE is just another WAL entry — it does not bring back the INSERT once the slot has advanced past it, and if the connector has been down long enough that the WAL segment holding the insert is gone, the event is lost permanently with no trace. The project sets app.outbox.retention: 7d with a 0 */15 * * * * cron precisely so the cutoff sits far beyond any plausible connector lag. Pick your retention from your worst observed connector outage, not from disk pressure.

PostgreSQL logical decoding, from the bottom up

Debezium is not magic and it is not a trigger. PostgreSQL's write-ahead log is a physical redo log — block images and byte offsets, useless to anything but a recovery process. Logical decoding is the mechanism that reassembles those records into logical row changes, and it needs three things configured before it will work at all.

docker-compose.yml · the postgres command lineyaml
    # wal_level=logical is the whole reason Debezium can work. Without it
    # Postgres does not write enough information into the WAL to reconstruct
    # row images, and the replication slot will refuse to be created.
    command:
      - postgres
      - -c
      - wal_level=logical
      - -c
      - max_replication_slots=10
      - -c
      - max_wal_senders=10
      - -c
      - wal_sender_timeout=0
SettingWhat it doesIf you get it wrong
wal_level=logicalAdds the extra information (notably the old tuple for the configured replica identity) that lets a decoding plugin reconstruct row changesSlot creation fails outright. Requires a restart — it is not a SIGHUP parameter, so this is a planned maintenance window on an existing cluster.
max_replication_slotsUpper bound on concurrent slots (default 10 in PG 16)New connectors fail to start once you have accumulated abandoned slots
max_wal_sendersUpper bound on concurrent walsender processesConnector cannot open a replication connection; physical standbys compete for the same budget
wal_sender_timeout=0Disables the idle-sender timeout (default 60 s)On a low-traffic outbox the sender is dropped and reconnects in a loop. Fine to disable in a demo; in production prefer a heartbeat over an infinite timeout.

Why pgoutput

pgoutput has shipped in the PostgreSQL core since 10, because it is the plugin native logical replication itself uses. That is the entire argument: no CREATE EXTENSION, no .so to install on every replica, and it works on managed PostgreSQL (RDS, Cloud SQL, Azure) where you cannot install anything. The historical alternatives — decoderbufs (Protobuf, from the Debezium project) and wal2json — both require a server-side extension and buy you nothing here, since Debezium converts to Connect records immediately either way.

pgoutput decodes only tables that belong to a publication, which is why the connector names one and asks to have it created:

publication.autocreate.mode=filtered means "create a publication covering exactly the tables in table.include.list, and nothing else". The default, all_tables, publishes your whole database and decodes every change in it — enormous waste when you care about one insert-only table. The cost of filtered is a privilege: only the table owner can add it to a publication, which is why this stack connects as postgres and why the init script spells out what production should do instead.

snapshot.mode, and why this one is no_data

On first start a Debezium connector has no offset, so it must decide what "the beginning" means. The default initial takes a consistent snapshot of every included table with SELECT * and emits a synthetic r (read) event per row before switching to streaming. For a table you are replicating that is exactly right. For an outbox it is a disaster: every row still in the table is an event that was already delivered, so a snapshot republishes the last seven days of your event stream to production consumers. no_data establishes the slot's starting LSN and streams from there without reading a single row — the correct semantics for a queue whose rows are historical by definition.

snapshot.modeBehaviour on first startUse for an outbox?
initial (default)Snapshot all included tables, then streamNo — re-emits every undeleted event
no_dataCapture schema, skip the data, stream from nowYes — what this project uses
neverStream only; no schema capture passOnly if you are certain the schema is already known
alwaysSnapshot on every connector startNever. Full replay on each restart.

skipped.operations and the purge

The retention job DELETEs outbox rows, and a delete is a WAL record like any other. Without skipped.operations=u,d,t, every purge cycle would push a delete event for every purged row through the SMT and onto orders.events — and with tombstones.on.delete at its default of true, a null-valued tombstone record after each one. Fifteen minutes of quiet, then a burst of thousands of records your consumer has to recognise and discard. u,d,t means updates, deletes and truncates are dropped in the connector before they ever reach the transform.

An abandoned replication slot pins WAL until the disk fills

A logical slot guarantees the server keeps every WAL segment from the slot's restart_lsn onwards, because that is the promise that makes the consumer restartable. If nothing reads the slot, that promise is unbounded. Delete the connector and keep taking orders and pg_wal grows forever — the database does not slow down, does not warn you, and then stops accepting writes when the volume is full. The Makefile says this out loud because the failure is so quiet:

$ make connector-delete
deleted
note: the replication slot 'outbox_slot' still exists in postgres.
      an abandoned slot pins WAL forever - drop it with:
      make psql, then SELECT pg_drop_replication_slot('outbox_slot');

Alert on it directly. This is the one query every team running CDC should have on a dashboard:

SELECT slot_name,
       active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
  FROM pg_replication_slots;

-- active = false on a slot you still want is an outage in progress.
-- retained_wal climbing without bound is an outage you have not noticed yet.
-- PG 13+: set max_slot_wal_keep_size so the server invalidates a runaway slot
-- instead of running out of disk. That converts a silent outage into a loud one.
A busy database and an idle outbox is the sneakiest version of the same bug

The slot's restart_lsn only advances when the connector flushes an offset, and it only has an offset to flush when it emits something. If ordersdb is busy with other traffic while the outbox table is quiet, the connector decodes and discards everything and never advances — so WAL accumulates on a slot that is perfectly healthy and perfectly active. That is what heartbeat.interval.ms: 10000 is for: it makes the connector emit a heartbeat and flush its position every 10 s regardless of whether the captured table changed.

The outbox event router SMT

Debezium's raw output is a change envelope: before, after, source, op, ts_ms, keyed by the table's primary key. Publishing that to your consumers would leak the outbox's physical shape into your event contract. The EventRouter single-message transform unwraps it and rebuilds the record from the columns you nominate.

Without table.expand.json.payload your event arrives as a string

The payload column is jsonb, but to the connector it is just a text value. Left alone, the SMT places that text into the record value and the JsonConverter serialises it as a JSON-encoded string: your consumer receives "{\"eventId\":\"...\",\"orderId\":\"...\"}" and Jackson refuses it, or worse, quietly binds nothing. "transforms.outbox.table.expand.json.payload": "true" parses the column and emits a real object. It is one line, and its absence is the single most common way this pattern is mis-wired — it is listed in the project's own troubleshooting table.

Why eventId is in the header and the body

From OrderCreatedPayload: "headers can be stripped by a badly configured converter or an intermediate proxy, and the consumer's idempotency key must never depend on transport metadata. The body is the contract." The header exists so a router or a filter can read it cheaply; the body field exists because correctness depends on it.

The whole path, end to end

Ordering, and the aggregate_id-as-key decision

Kafka orders records within a partition and offers nothing across partitions. The producer here does not choose partitions — the SMT sets the key from aggregate_id and the default partitioner hashes it (murmur2(key) % numPartitions). That single line of configuration is what turns "3 partitions of unordered events" into "per-order ordering with 3× the parallelism".

producer · the schema comment that states the guaranteesql
-- `aggregate_id` becomes the Kafka message key, which is what gives you
-- per-aggregate ordering: every event for one order lands on one partition and
-- is therefore consumed in write order.
Key choiceOrdering you getParallelismWhen it is right
aggregate_id — this projectTotal order per aggregateUp to numPartitions consumersAlmost always. Invariants are per-aggregate by definition.
event_id (or null → round-robin)NoneMaximumOnly for genuinely independent facts: metrics, logs, clicks
customer_idTotal order per customer, coarser than per orderLower, and hot customers create hot partitionsWhen invariants span a customer's orders (credit limits, balances)
Constant / single partitionTotal order over everythingOne consumer threadOnly when the whole stream is a single state machine and the volume is small
Adding partitions silently rewrites the mapping

The partition is murmur2(key) % numPartitions. Change the partition count from 3 to 6 and roughly half of all keys move — including keys with events already sitting on the old partition. For a window equal to your consumer lag, two partitions hold events for the same aggregate and are consumed concurrently, which is precisely the ordering violation the key was chosen to prevent. Kafka will not warn you. Size the partition count for peak consumer parallelism up front, and treat an increase on a keyed topic as a migration, not a config tweak.

The relay is ordered because tasks.max = 1, and it cannot be otherwise

A PostgreSQL connector reads one replication slot; it does not shard. That is a throughput ceiling — one connector task publishing every event for a database — and it is also the reason the stream that reaches the partitioner is in commit order. If you outgrow it the answer is another database, not another task.

Where the guarantee stops

Be able to state the residual weakness out loud: this pipeline is at-least-once, not exactly-once. Debezium can re-emit a row after a connector restart whose offsets were not flushed — OFFSET_FLUSH_INTERVAL_MS: 1000 in the Compose file bounds that window at roughly one second of records. Nothing in the outbox pattern removes duplicates; it removes loss. Deduplication is the consumer's job, and it is why every event carries a stable identifier generated inside the producer's transaction:

consumer · the other half of the contractsql
-- One row per event this consumer has *committed* the effects of. `event_id` is
-- the primary key, which gives us the unique constraint the whole mechanism
-- hangs on.
CREATE TABLE processed_message (
    event_id       UUID         PRIMARY KEY,
    topic          VARCHAR(255) NOT NULL,
    partition_no   INTEGER      NOT NULL,
    record_offset  BIGINT       NOT NULL,
    consumer_group VARCHAR(255) NOT NULL,
    processed_at   TIMESTAMPTZ  NOT NULL DEFAULT now()
);

Note that the ledger lives in consumerdb, a different database from the producer's ordersdb. That separation is deliberate: if both services shared one database you could make the consumer's effect part of the producer's transaction and learn nothing about the realistic distributed case. The next page picks up from here — what happens when the consumer's effect fails, how to tell a transient failure from a permanent one, and why blocking retries destroy a partition.

What to take away

  1. A dual write has no safe ordering because it has two commit points and no coordinator. DB-then-Kafka loses events on a crash; Kafka-then-DB creates phantom state; a retry loop converts loss into duplicates you have no key to dedupe on. An afterCommit callback narrows the window to microseconds without closing it.
  2. XA is not an option because Kafka exposes no XA resource adapter — Kafka transactions are Kafka-internal and cannot enlist a JDBC connection. The outbox does not coordinate the second commit, it deletes it: the event becomes a row written by the same transaction.
  3. The strongest expression of the pattern is a missing dependency. The producer module has no kafka-clients on its classpath, so it cannot dual-write even by accident, and orders keep committing with the broker completely down.
  4. CDC beats a polling publisher on write amplification (one INSERT, no mark-as-published UPDATE), on latency (no poll-interval floor) and on load (no queries against your primary) — at the cost of a Connect cluster and a replication slot you must monitor.
  5. Logical decoding needs wal_level=logical (a restart, not a reload), slots and walsender budget, and a publication. Use pgoutput because it is in-core and therefore works on managed PostgreSQL; use publication.autocreate.mode=filtered so you decode one table instead of the whole database; use snapshot.mode=no_data because an initial snapshot of an outbox republishes your entire event history.
  6. An unread replication slot pins WAL until the disk fills, silently. Alert on pg_replication_slots.active and on pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn), set max_slot_wal_keep_size, and use heartbeat.interval.ms so a busy database with a quiet outbox still advances the slot.
  7. The EventRouter SMT makes routing data: aggregate_type picks the topic, aggregate_id becomes the key and therefore the ordering granularity, and table.expand.json.payload=true is what stops your payload arriving as a JSON-encoded string. Keying by the aggregate buys per-aggregate order with N-way parallelism — and changing the partition count later silently breaks it.
