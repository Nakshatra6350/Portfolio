CRDTs & the convergence problem

Why two people typing at the same position cannot be reconciled by timestamps, what algebraic property makes delivery order irrelevant, and how src/crdt/rga.js buys that property with one character identifier, one predecessor reference, one total order and a very large pile of tombstones.

Node 22 WebSocket Redis 8 crdt

The problem: two carets, one position

Two browser tabs hold the same document. Neither holds a lock, neither asks permission, and each applies its own keystroke to the screen before the network sees it — that optimism is the entire user-visible reason for the architecture. The moment both users touch the same region, you have two divergent histories and no authority to arbitrate between them.

The first instinct is a timestamp: last write wins. It does not survive contact with a text buffer, because the unit of a text edit is not a document, it is a position, and a position is not something you can overwrite. Discard one of two concurrent edits and you have not resolved a conflict, you have deleted a character the user watched themselves type.

The second instinct is to ship the edit as an index — insert "X" at 1. That is worse, because it fails silently. An index is only meaningful relative to a document state, and by the time the op arrives the receiver's document is no longer in that state.

Operational transformation is the classic fix: keep sending indexes, but transform each incoming op against every concurrent op you already applied, so its index is rewritten into your frame of reference. It works, and Google Docs runs on it. The cost is that the transformation functions must satisfy two properties — TP1 and TP2 — and TP2 is the one that ruins weekends: for three concurrent ops the transformed results must be independent of the order in which you transform. Published OT algorithms have shipped with TP2 violations for years before anyone found them, and most production OT systems dodge the problem entirely by routing every op through a central server that imposes a total order, which reintroduces exactly the single point of coordination we are trying to remove.

Why convergence is a lattice property

A CRDT replaces "resolve the conflict" with "make the conflict impossible to observe". The requirement is stated algebraically. If every replica's state is an element of a set with a merge operation ⊔, and that merge is commutative, associative and idempotent, then the merge is a join-semilattice, and any two replicas that have absorbed the same set of updates hold the same state — regardless of the order they arrived in, how many times each arrived, or how they were grouped into batches.

Those three laws map exactly onto the three things the network does to you. Reordering is commutativity. Batching — one instance delivering a run of ops that another delivers one-by-one — is associativity. Redelivery, which happens constantly here because an op can reach you over the pub/sub bus and in an op-log replay and from a client resending after a reconnect, is idempotence. Satisfy all three and you can stop reasoning about delivery entirely.

The mental model that matters

A CRDT does not make ordering unnecessary; it makes agreement on an ordering unnecessary. The document order in this project is fixed by compareIds, a pure function every replica evaluates independently and always agrees on. The network is demoted from "the thing that decides what the document says" to "a best-effort delivery mechanism for a set of facts". That is why src/crdt/rga.js has no imports and the browser loads the same file the server runs: convergence is a property of one function, and two hand-written copies of that function is how it gets broken.

test('two replicas converge when concurrent inserts are applied in opposite orders', () => {
  const a = new RGA('a');
  const b = new RGA('b');

  // Both start empty and both type at position 0, without seeing each other.
  const opsA = a.insertAt(0, 'hello');
  const opsB = b.insertAt(0, 'world');

  assert.equal(a.toString(), 'hello');
  assert.equal(b.toString(), 'world');

  // Now they exchange - in opposite orders, which is the whole point.
  a.apply(opsB);
  b.apply(opsA);

  assert.equal(a.toString(), b.toString(), 'replicas must converge');
  // Pinned so a change to the comparator cannot silently change document order:
  // site "b" wins the counter tie, so "world" sorts ahead of "hello".
  assert.equal(a.toString(), 'worldhello');
});

Sequences are the hard CRDT

Counters and sets are easy because their elements have no relationship to each other. A grow-only counter merges by taking the per-replica maximum; a grow-only set merges by union. Both are trivially commutative, associative and idempotent, and neither has to answer the question a text document lives or dies by: where does this element go?

The textbook approach is to give each character a dense, totally ordered identifier: a position value from a space where, between any two positions, another position always exists. Then inserting between 0.3 and 0.4 is just picking 0.35, merging is a set union of (position, character) pairs, and the document is the sorted order. That is Logoot and LSEQ, and the density requirement is what makes it painful in practice: identifiers are variable-length paths, an adversarial or merely unlucky editing pattern (repeatedly typing at the same spot) makes them grow without bound, and a 3 KB document can end up carrying 60 KB of identifiers.

RGA takes the other route. It never invents a position between two things. It says "immediately after this specific character", names it by an identifier that never changes, and resolves the remaining ambiguity — several ops naming the same predecessor — with a total order over identifiers. The identifier space does not have to be dense, only unique and totally ordered, and a (siteId, counter) pair gives you both in 16 bytes.

RGA: identity, predecessor, tombstone

the entire wire format, from the READMEjson
{ "type": "ins", "id": { "s": "alice", "c": 7 }, "after": { "s": "bob", "c": 3 }, "ch": "x" }
{ "type": "del", "id": { "s": "alice", "c": 7 } }

Three decisions are packed into those two lines, and each one is load-bearing.

An identifier, not an index. c is a Lamport counter, raised to at least any value the replica has ever observed, so "later" always means "numerically larger". s is the site id — the browser tab, or the server instance. The pair is unique by construction, and it is immutable: the character keeps it for the life of the document, through snapshots, reconnects and process restarts.

The insert names its predecessor. after is an id, not a number. It means one unambiguous thing on every replica forever, whereas "index 5" means whatever that replica happens to hold right now.

The delete does not delete. It flips a boolean on a node that stays in the list — a tombstone. That is what makes delete commute with everything: it never moves a node, and a node that never moves cannot invalidate someone else's after reference.

the identifier and its total order — src/crdt/rga.jsjs
/** Stable string key for an id. Used for every Map/Set lookup in this file. */
export function idKey(id) {
  return id.s + ':' + id.c;
}

/**
 * Total order over ids. Returns > 0 when `a` should sit BEFORE `b` in the
 * document, < 0 when after, 0 only when they are the same id.
 *
 * Higher Lamport counter first, ties broken by site id descending. Two things
 * matter here and both are easy to get wrong:
 *
 *   - It must be TOTAL. If the comparator can return 0 for two different ids,
 *     the scan below becomes order-dependent and the replicas diverge. Since
 *     (counter, siteId) pairs are unique by construction, comparing both fields
 *     gives a total order.
 *   - It must be the same everywhere. Any tie-break works (ascending site id
 *     would be just as correct) as long as every replica picks the same one.
 */
export function compareIds(a, b) {
  if (a.c !== b.c) return a.c - b.c;
  if (a.s === b.s) return 0;
  return a.s < b.s ? -1 : 1;
}
A colon in a site id silently aliases two different characters

idKey joins with ':', so site a counter 1:2 and site a:1 counter 2 would produce the same map key — and the second character to arrive would be swallowed as a duplicate. The constructor refuses the input rather than letting it become a data-corruption bug six hours later:

if (siteId.includes(':')) {
  // idKey() joins with ':', so a colon in a siteId would make two different
  // ids collide on the same key. Cheap invariant, nasty bug if violated.
  throw new TypeError('siteId must not contain ":"');
}

The same reasoning is why src/config.js validates INSTANCE_ID against /^[A-Za-z0-9_.-]{1,32}$/: the instance id becomes part of the server's site id (srv-${config.instanceId}), so a colon in a Kubernetes pod name would reach the comparator.

The integration scan, and the tie-break

Placing a remote insert is four lines. Resolve the anchor; walk forward past every node that "wins" the comparator; splice in. Because compareIds is a strict total order over ids that are unique by construction, every replica walks exactly the same distance and stops in exactly the same place, no matter which order the surrounding nodes arrived in.

#integrateInsert — the whole CRDT is these linesjs
this.#observe(op.id);

const key = idKey(op.id);
// Idempotence: the same op can arrive twice (bus + op-log replay, or a
// client that resent after a reconnect). Seeing it again is a no-op.
if (this.#index.has(key) || this.#redirect.has(key)) return false;

const anchor = this.#resolveAnchor(op.after);
if (anchor === undefined) {
  // Causally not ready: we have not seen the predecessor yet. Park it.
  this.#pend(idKey(op.after), op);
  return false;
}

// ---- the integration scan -------------------------------------------
// Walk forward from the anchor while the next node "wins" the comparator.
// Because compareIds is a total order over ids, every replica walks the
// same distance and stops at the same place, no matter what order the
// nodes arrived in.
let prev = anchor;
while (prev.next !== null && compareIds(prev.next.id, op.id) > 0) {
  prev = prev.next;
}

const node = { id: op.id, ch: op.ch, deleted: false, next: prev.next };
prev.next = node;
this.#index.set(key, node);
this.#visible++;
return true;
A comparator that returns 0 for two different ids diverges — rarely, and forever

Drop the site-id tie-break so compareIds compares counters only, and the test suite still passes most single-replica tests. It breaks exactly when two sites mint the same counter, which is precisely the concurrent-edit case you shipped the CRDT for. The scan then stops in different places on different replicas and the documents drift apart with no error anywhere. That is why rga.test.js asserts the order-theoretic laws directly rather than trusting a few examples:

// totality: only identical ids may compare equal. If two DIFFERENT ids
// ever compared equal, the integration scan would stop at different
// places on different replicas and the whole CRDT would fall apart.
if (idKey(x) !== idKey(y)) assert.notEqual(xy, 0, `${idKey(x)} and ${idKey(y)} must be ordered`);
A local insert never actually scans

insertAt mints an id with the largest counter this replica has ever seen, so the while loop's first comparison already fails and the character lands exactly where the caret is. Local editing is O(1) per character after the index walk; the scan cost only appears for genuinely concurrent remote inserts.

for (let i = 0; i < text.length; i++) {
  const op = { type: 'ins', id: this.#nextId(), after: anchor.id, ch: text[i] };
  // A locally minted id always has the largest counter this replica has
  // seen, so the integration scan stops immediately and the character lands
  // exactly where the user put it. We still route through applyOp so there
  // is exactly one code path that mutates the list.
  this.applyOp(op);
  anchor = this.#index.get(idKey(op.id));
  ops.push(op);
}

Causal buffering: why delivery order stops mattering

Commutativity says nothing about an op whose anchor has not arrived. ins after=bob:3 is unplaceable on a replica that has never seen bob:3 — not wrong, just not yet resolvable. The fix is local and cheap: park it, keyed by the id it is waiting for, and replay it the instant that id appears. The network gets to reorder freely; causality is reconstructed on the receiving side.

park and drain — src/crdt/rga.jsjs
#pend(key, op) {
  if (this.#pendingCount >= this.#maxPending) {
    // BOUNDED on purpose. A peer that streams inserts referencing ids it
    // never sends would otherwise grow this map until the process dies.
    // Dropping is safe: the op log replay on the next sync re-delivers.
    this.#pendingDropped++;
    return;
  }
  const list = this.#pending.get(key);
  if (list === undefined) this.#pending.set(key, [op]);
  else list.push(op);
  this.#pendingCount++;
}

/** Replay ops that were waiting on `key`, and anything they in turn unblock. */
#drain(key) {
  const queue = [key];
  while (queue.length > 0) {
    const current = queue.pop();
    const waiting = this.#pending.get(current);
    if (waiting === undefined) continue;
    this.#pending.delete(current);
    this.#pendingCount -= waiting.length;
    for (const op of waiting) {
      const applied = op.type === 'ins' ? this.#integrateInsert(op) : this.#integrateDelete(op);
      if (applied && op.type === 'ins') queue.push(idKey(op.id));
    }
  }
}

The drain is an explicit work queue rather than recursion for a concrete reason: a whole word delivered in reverse is a chain of n parked ops, and the arrival of the first character unblocks all of them in one cascade. At 4 kB of pasted text that recursion would be 4,000 frames deep. The test pins the cascade behaviour exactly.

the reverse-delivery testjs

assert.equal(r.pendingCount, 0);

Deletes need buffering too, and forgetting it looks like a haunting

It is easy to buffer inserts and drop a delete whose target is unknown — "there is nothing to delete, so nothing to do". Wrong: the insert may still be in flight. Discard the delete and the character arrives moments later and stays forever, on that replica only. Users report it as text coming back from the dead after a reconnect, which is a spectacularly unpleasant bug to reproduce.

const node = this.#index.get(key);
if (node === undefined) {
  // Delete arrived before the insert it refers to. Park it: this is the
  // half of causal buffering people forget, and it shows up as characters
  // that "come back from the dead" after a reconnect.
  this.#pend(key, op);
  return false;
}
The pending buffer is bounded, and that is only safe because of the op log

Once maxPending (default 10,000) is reached, further parked ops are counted in pendingDropped and thrown away. On its own that would be data loss. It is safe here purely because every op is also durably in the Redis Stream: the next sync/welcome re-delivers it. Remove the op log and this bound becomes a bug. Watch pendingDropped in /healthz — a non-zero value means either an abusive peer or a genuinely broken causal chain upstream.

Tombstones, and the price of never forgetting

Type 100,000 characters, delete all of them, and the empty document still costs 100,000 nodes: memory, snapshot bytes, and an O(n) walk for every index lookup in #nodeBeforeVisibleIndex. In a long-lived document tombstones routinely outnumber live characters, which is why Document.stats() exposes tombstoneRatio on /healthz — it is the number that tells you when a document needs resetting.

You cannot simply drop them. Removal is only safe once a delete is causally stable: every replica has seen it, so no future op can name the removed character as its anchor. Proving that requires version vectors exchanged between replicas plus knowledge of the full membership set — neither of which a system built from anonymous, reconnecting browser tabs has cheaply.

gc() — collection with anchor inheritancejs
gc(isStable) {
  if (typeof isStable !== 'function') throw new TypeError('gc requires an isStable(node) predicate');
  let collected = 0;
  let prev = this.#head;
  let node = this.#head.next;
  while (node !== null) {
    if (node.deleted && isStable(node)) {
      const key = idKey(node.id);
      prev.next = node.next;
      this.#index.delete(key);
      // Anchor inheritance: anything that pointed at this node now points at
      // its surviving predecessor (null == the head sentinel).
      this.#redirect.set(key, prev.id === null ? null : prev.id);
      this.#tombstones--;
      collected++;
      node = prev.next;
      continue;
    }
    prev = node;
    node = node.next;
  }
  return collected;
}
and the resolver that makes redirects work — #resolveAnchorjs
#resolveAnchor(after) {
  if (after === null || after === undefined) return this.#head;
  let cursor = after;
  for (let hops = 0; hops < 1_000_000; hops++) {
    const key = idKey(cursor);
    const node = this.#index.get(key);
    if (node !== undefined) return node;
    if (!this.#redirect.has(key)) return undefined; // never seen it
    const next = this.#redirect.get(key); // collected: follow the redirect
    if (next === null) return this.#head;
    cursor = next;
  }
  throw new Error('redirect chain did not terminate');
}
Every replica must run gc() with the SAME predicate

Collection is the one operation in this CRDT that is not safe to do independently. If replica A collects tombstone a:3 and replica B does not, a late insert anchored on a:3 is placed after a:3's predecessor on A and after a:3 itself on B — and if a live character sits between them, the two replicas place the new character on opposite sides of it. Convergence is gone, and the fuzz test will not catch it because gc() is never called automatically. Nothing in the server calls it; it is there so you can see what a correct collection scheme has to prove.

The three real answers to tombstone growth
  1. Never collect. Bound the damage with snapshots plus periodic document resets. That is this project's default, and for documents with a bounded lifetime it is the right trade.
  2. Collect under a coordinator that can prove every session has acknowledged a sequence number — what gc() models. You already have the acknowledgement machinery here: the op log's sequence number and each client's since.
  3. Change the data model. Block-wise CRDTs store a run of characters in one node, so a deleted paragraph costs one tombstone rather than 400. This is what Yjs does, and it is the biggest single constant-factor win available.
Snapshots keep tombstones, and drop the after links

snapshot() writes [siteId, counter, char, deletedFlag] per node in document order. The predecessor links are dead weight once the order is materialised — restore rebuilds in O(n) with no comparator at all. Tombstones are written, because a future op may still name one as its anchor; #pending is not, because parked ops are by definition ops that were never applied and the op log will re-deliver them.

What RGA gives up, and what Yjs and Automerge do instead

Convergence is not the same as intention preservation. RGA's scan walks a flat list rather than a tree of siblings, and the consequence has a name: interleaving. Two users typing whole words at the same position concurrently can end up with their characters interleaved rather than each word kept whole. Every replica agrees on the interleaved result — it converges perfectly — it is simply not what either user meant.

Why write RGA rather than depend on Yjs

For production you should almost certainly use Yjs: it is block-wise, binary-encoded, battle tested, and roughly an order of magnitude leaner per character. The reason this project implements RGA in 565 readable lines is that Yjs's efficiency is achieved by making the interesting parts — the comparator, the scan, the tombstone policy — invisible. Once you have written the comparator and watched the fuzz test fail when you weaken it, the library stops being magic and becomes a set of engineering trades you can evaluate.

The system around the CRDT

The CRDT solves merge. It solves nothing else — not durability, not "what did I miss while my laptop was asleep", not "Alice is on instance A and Bob is on instance B". Those are the backplane's job, and the separation between the two is the design's spine.

submitOps — the ordering IS the design (src/doc/registry.js)js
async submitOps(docId, ops, clientId) {
  const doc = await load(docId);

  // 1. Durable first. This also allocates the sequence number.
  const seq = await oplog.append(docId, { ops, clientId });

  // 2. Local state.
  const applied = doc.applyOps(ops);
  doc.advanceTo(seq);
  metrics.inc('collab_ops_applied_total', applied.length);
  metrics.inc('collab_ops_duplicate_total', ops.length - applied.length);

  // 3. Sockets on this instance (the author gets an ack instead of an echo:
  //    it already applied these ops optimistically).
  broadcastLocal(docId, opsMessage({ docId, seq, ops, clientId }), clientId);

  // 4. Every other instance. Note we send the full batch, not just what
  //    changed here - another instance may be missing exactly the ops we
  //    deduplicated.
  await bus.publish(docId, { type: 'ops', docId, seq, ops, clientId });

  // 5. Snapshot cadence, off the critical path.
  this.maybeSnapshot(docId).catch((err) => log.error('snapshot failed', { docId, err }));

  return { seq, applied: applied.length };
}
seq is not causality — do not order CRDT ops by it

The sequence number answers "how much of the op log have I consumed", nothing more. It exists so a reconnecting client can say "I last saw 4210" and be sent exactly what it missed. The CRDT answers "what does the document say" and does not care about order at all. Conflating them is the classic mistake in this architecture: if you sorted ops by seq before applying them, you would have rebuilt a total-order broadcast and thrown away the reason for the CRDT.

advanceTo(seq) {
  if (!Number.isInteger(seq) || seq < 0) throw new TypeError(`seq must be a non-negative integer, got ${seq}`);
  if (seq > this.seq) this.seq = seq;
  return this.seq;
}

Note it never moves backwards. A gap fill reads the log directly and can interleave with live pub/sub delivery, so entries genuinely arrive out of order — and rewinding the watermark would make this instance serve a stale delta to a client that is ahead of it.

Because ops commute, the failure modes of the backplane degrade gently. Redis pub/sub is fire-and-forget and will drop messages during a subscriber blip; the receiving instance notices the sequence gap, reads the missing entries straight out of the Stream, and applies them. Applying the newer op first and repairing afterwards is not a problem: it is exactly the reordering the CRDT was chosen to absorb.

The fuzz test, and why it is the only test that would catch a comparator regression

Three replicas each start from a shared seed, edit in isolation for 40 random steps, and pool every op they produced. Twenty-five different shuffles of that pool are replayed into fresh replicas; all twenty-five must produce byte-identical text and leave nothing parked. The PRNG is seeded so a failure is reproducible from its seed rather than being a flaky CI ticket.

const outputs = new Set();
for (let i = 0; i < 25; i++) {
  const replica = replayInto(`fuzz-${i}`, shuffled(pool, rnd));
  assert.equal(replica.pendingCount, 0, `run ${i} left ops unintegrated`);
  outputs.add(replica.toString());
}

assert.equal(outputs.size, 1, `divergence across shuffles: ${[...outputs].map((s) => JSON.stringify(s)).join(' | ')}`);

Collapsing every run into a Set and asserting size === 1 is the whole trick: you are not asserting a particular document, you are asserting that there is only one. That assertion survives any change to the tie-break direction, which a pinned string would not.

What to take away

  1. An index is a statement about one replica's current state, so it cannot be shipped. RGA replaces it with an immutable {s, c} identifier plus an after reference, which means the same thing on every replica forever.
  2. Convergence is the join-semilattice property — commutative, associative, idempotent merge. Those three laws are exactly reordering, re-batching and redelivery, which is why the CRDT lets you stop reasoning about the network.
  3. Everything rests on compareIds being a strict total order. A comparator that returns 0 for two different ids diverges only when two sites pick the same counter — i.e. only under genuine concurrency — and it does so silently. Assert the order-theoretic laws, not examples.
  4. Commutativity does not cover causality. An op whose anchor has not arrived must be parked and replayed, and that includes deletes — dropping an early delete is how characters come back from the dead after a reconnect.
  5. Tombstones are the rent you pay for commuting deletes, and they are unbounded. Collection is only sound when a delete is causally stable and every replica collects the identical set; watch tombstoneRatio in /healthz and prefer block-wise storage (Yjs) if you need it to actually scale.
  6. RGA converges but does not preserve intention: concurrent word-level typing at one position interleaves. YATA and Fugue buy intention preservation with extra per-item origin bookkeeping; know which property you actually need.
  7. The CRDT solves merge and nothing else. Durability, catch-up and cross-instance fanout are the op log's, the sequence watermark's and the bus's jobs — and seq is a log position, never a causal order. Sort ops by it and you have rebuilt the coordinator you removed.
