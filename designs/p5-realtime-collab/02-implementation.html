The realtime layer

The CRDT is the easy half. This is the other: the validator between a socket and the merge algorithm, the heartbeat that tells a dead connection from an idle one, the bounded queue that stops one slow phone eating the heap, and the Redis backplane that makes two processes behave like one document.

The mental model that matters

A WebSocket is a long-lived resource held on behalf of someone you cannot trust and cannot see. Requests end; connections do not. Each mechanism below answers one question: is this frame safe to act on? (protocol), is the peer there? (heartbeat), is it keeping up? (backpressure), what did the other instances see? (Redis, whose guarantees are weaker than they look).

The wire protocol

One JSON object per text frame, tagged with t. The rule src/transport/protocol.js enforces: nothing from a socket reaches the CRDT unchecked. The RGA integrator assumes id.s is a string and ch one character, so {c: "banana"} must be rejected at the door, not inside a linked-list walk where the failure is a corrupted document instead of an error message.

Two rules follow. Every list has a bound — ops, ids, names, the whole frame — because an unbounded field on a public socket is a denial of service waiting to happen. And validation returns a value rather than throwing: a bad frame costs one error message and one counter, not a stack unwind.

size is checked before anything is parsedjs
function byteLength(raw) {
  if (typeof raw === 'string') return Buffer.byteLength(raw, 'utf8');
  if (raw instanceof ArrayBuffer) return raw.byteLength;
  if (ArrayBuffer.isView(raw)) return raw.byteLength;
  if (Array.isArray(raw)) return raw.reduce((sum, chunk) => sum + byteLength(chunk), 0);
  return 0;
}

String.length is not a size limit

String length counts UTF-16 code units; the wire carries UTF-8. 400 copies of あ are 400 characters and 1,200 bytes, so a naive check turns a 64 KiB cap into 192 KiB — worse for four-byte emoji. Measure with Buffer.byteLength(raw, 'utf8').

test('the size limit counts BYTES, not characters', () => {
  const payload = JSON.stringify({ t: 'presence', docId: 'd', cursor: null, pad: 'あ'.repeat(400) });
  assert.ok(payload.length < 1024, 'under the limit if you count characters');

Heartbeat, and the zombie connection

A dead TCP connection is indistinguishable from an idle one. Both send nothing. When a lid closes, when wifi switches to cellular, when a NAT box drops an idle mapping, no FIN and no RST arrives, and SO_KEEPALIVE waits two hours before probing. The socket sits in readyState === OPEN forever, holding a Connection, a presence entry and a broadcast slot.

The fix is to make the peer prove liveness on your schedule. Ping/pong is a protocol-level control frame, which is why it beats an application-level {t:'ping'}: every conforming client answers automatically, so no client code ships.

the whole heartbeatjs
const heartbeat = setInterval(() => {
  for (const conn of connections) {
    if (!conn.alive) {
      // No pong since the previous tick: the peer is gone even though the
      // socket still looks open. terminate() skips the close handshake, which
      // is the point - there is nobody there to complete it.
      conn.log.info('terminating unresponsive connection', { docId: conn.docId });
      conn.ws.terminate();
      continue;
    }
    conn.alive = false;
    try {
      conn.ws.ping();
    } catch (err) {
      conn.log.warn('ping failed', { err });
    }
    // Opportunistically drain anything left over from a backpressure episode.
    conn.flush();
  }
}, config.heartbeatIntervalMs);
heartbeat.unref?.();

Backpressure: the failure mode that eats the heap

ws.send() never blocks and never fails on a slow peer: if the peer stops reading, the data piles up in ws.bufferedAmount, in your process memory, with no signal to check. Thirty typists produce ~150 ops frames per second at ~150 bytes, so a client that stops reading for five minutes holds 6.6 MB — two hundred of them, 1.3 GB. The symptom is an OOM kill.

the three methods that implement the diagramjs
#write(payload) {
  if (this.ws.readyState !== WebSocket.OPEN) return false;

  // Once anything is queued, EVERYTHING must queue - otherwise a later
  // message would overtake an earlier one and the client would see ops out of
  // order. Ordering is not optional even though the CRDT tolerates reorder:
  // the sequence numbers would go backwards.
  if (this.queue.length > 0 || this.ws.bufferedAmount > this.config.maxBufferedBytes) {
    return this.#enqueue(payload);
  }
  this.ws.send(payload);
  this.metrics.inc('collab_messages_out_total');
  return true;
}

#enqueue(payload) {
  if (this.queue.length >= this.config.maxOutboundQueue) {
    // The client is hopelessly behind. Everything it is missing is in the op
    // log, so closing costs it one resync and costs us nothing.
    this.metrics.inc('collab_backpressure_disconnects_total');
    this.log.warn('outbound queue overflow, disconnecting slow client', {
      queued: this.queue.length,
      bufferedAmount: this.ws.bufferedAmount,
      docId: this.docId,
      clientId: this.clientId,
    });
    this.close(CLOSE.BACKPRESSURE, 'too slow');
    return false;
  }
  this.queue.push(payload);
  this.metrics.inc('collab_backpressure_queued_total');
  this.metrics.add('collab_outbound_queued', 1);
  this.#scheduleDrain();
  return true;
}

/** Move as much of the queue into the socket as its buffer will accept. */
flush() {
  if (this.closed || this.ws.readyState !== WebSocket.OPEN) return;
  while (this.queue.length > 0 && this.ws.bufferedAmount <= this.config.maxBufferedBytes) {
    const payload = this.queue.shift();
    this.metrics.add('collab_outbound_queued', -1);
    this.ws.send(payload);
    this.metrics.inc('collab_messages_out_total');
  }
  if (this.queue.length > 0) this.#scheduleDrain();
}

Note the two metrics.add('collab_outbound_queued', ±1) calls. That one is a gauge, not a counter: #enqueue raises it and flush() lowers it, so the value at scrape time is how many frames are sitting in queues across every connection right now. Pair it with the collab_backpressure_queued_total counter next to it — the counter says how often you hit backpressure, the gauge says whether you are still in it.

Once anything is queued, everything must queue

"Queue only when the buffer is full" reorders the stream: a frame written directly while three sit in the queue arrives first. Ops commute, so the CRDT survives it; the client's lastSeq watermark does not, because it takes Math.max and now believes it has seen 118 when it never received 116. The this.queue.length > 0 || half of the condition prevents that.

Alternatives, and why they lose here

Drop the oldest frames: fine for cursors, wrong for ops — the client cannot detect a hole in a sequence range. Coalesce into a snapshot: correct but expensive for a client that may never read again. await the send: blocking the broadcast loop on one slow socket punishes 29 healthy ones. Only closing bills the client that caused it.

The Redis backplane

Alice is on instance A, Bob on instance B. Instance A knows Alice's socket and nothing else. Without a backplane the system looks healthy and silently splits into two documents: the worst class of distributed bug, because there is no error anywhere. Pub/sub is the fix, with two sharp edges.

Edge one: pub/sub echoes to the publisher

Redis delivers to every subscriber, including the publisher. The originating instance already applied and broadcast that message locally, so it must drop its own echo, or every op is applied twice and every client receives it twice. The envelope carries the instance id, and config.js refuses to boot with a malformed one.

redisBus.js — the filter is one line, and it is load-bearingjs
await subscriber.subscribe(channelFor(docId), (raw) => {
  let envelope;
  try {
    envelope = JSON.parse(raw);
  } catch (err) {
    log.error('unparseable bus message', { docId, err });
    return;
  }
  // Drop our own echo - see SELF-FILTERING above.
  if (envelope.instanceId === config.instanceId) return;
  metrics.inc('collab_bus_received_total');
  const current = handlers.get(docId);
  if (current === undefined) return; // unsubscribed while in flight
  try {
    current(envelope);
  } catch (err) {
    // A throwing handler must not take down the shared subscriber
    // connection: one bad document would stop fanout for every document.
    log.error('bus handler threw', { docId, err });
  }
});
Why a second Redis connection

A connection in subscriber mode accepts almost nothing else — you cannot XADD on it — so sharing one client deadlocks the first append after the first subscribe. src/index.js uses redis for commands plus redis.duplicate() for SUBSCRIBE, and /healthz reports both.

Edge two: pub/sub has no delivery guarantee at all

Fire and forget. If a subscriber is disconnected for 200 ms — a failover, a blip, a paused event loop — those messages are gone, queued nowhere, with nothing to tell you. So the Stream is the durable record, every envelope carries the sequence it assigned, and a receiver that spots a hole reads it back.

The watermark is what makes a dropped op permanent

Without gap repair the CRDT does not crash; it is missing a character. The fatal line is doc.advanceTo(envelope.seq): the watermark jumps past the hole, so no later sync ever asks for those ops and the document is wrong forever. Not "we occasionally drop an edit" but "we permanently corrupt documents in proportion to Redis flappiness".

Sequence numbers, and the race the Lua script closes

The Stream could assign its own <millis>-<n> ids, but a client would then have to echo back an opaque two-part token. Instead INCR allocates a monotonic integer used as the stream id, so "everything after 4210" is XRANGE key (4210-0 + COUNT n — O(log n), and trim-proof. The cost is a race.

oplog.js — INCR and XADD in one atomic scriptlua
-- KEYS[1] = sequence counter, KEYS[2] = stream
-- ARGV[1] = approximate MAXLEN, ARGV[2] = JSON payload
local seq = redis.call('INCR', KEYS[1])
if seq == 1 then
  -- Reconciliation: the counter is volatile-looking state while the stream is
  -- durable. If the counter was lost (flushed, expired, restored from an older
  -- dump) but the stream survived, restarting at 1 would make XADD fail
  -- forever with "equal or smaller ID". Resume above the last stream id.
  local last = redis.call('XREVRANGE', KEYS[2], '+', '-', 'COUNT', 1)
  if last and last[1] then
    local lastSeq = tonumber(string.match(last[1][1], '^(%d+)')) or 0
    if lastSeq >= seq then
      seq = lastSeq + 1
      redis.call('SET', KEYS[1], tostring(seq))
    end
  end
end
redis.call('XADD', KEYS[2], 'MAXLEN', '~', ARGV[1], tostring(seq) .. '-0', 'p', ARGV[2])
return seq

Two instances appending at once both INCR — getting 11 and 12 — then both XADD. If B's (12) lands first, A's (11) is rejected: stream ids must strictly increase. Redis runs scripts to completion without interleaving, so ids are allocated and used in the same order. A retry loop around XADD * loses the one-id-per-entry property clients depend on.

registry.submitOps — the ordering IS the designjs
async submitOps(docId, ops, clientId) {
  const doc = await load(docId);

  // 1. Durable first. This also allocates the sequence number.
  const seq = await oplog.append(docId, { ops, clientId });

  // 2. Local state.
  const applied = doc.applyOps(ops);
  doc.advanceTo(seq);
  metrics.inc('collab_ops_applied_total', applied.length);
  metrics.inc('collab_ops_duplicate_total', ops.length - applied.length);

  // 3. Sockets on this instance (the author gets an ack instead of an echo:
  //    it already applied these ops optimistically).
  broadcastLocal(docId, opsMessage({ docId, seq, ops, clientId }), clientId);

  // 4. Every other instance. Note we send the full batch, not just what
  //    changed here - another instance may be missing exactly the ops we
  //    deduplicated.
  await bus.publish(docId, { type: 'ops', docId, seq, ops, clientId });

  // 5. Snapshot cadence, off the critical path.
  this.maybeSnapshot(docId).catch((err) => log.error('snapshot failed', { docId, err }));

  return { seq, applied: applied.length };
}
Swap steps 1 and 4 and every test still passes

Publishing before appending is faster and looks harmless. Kill the process between the two and the edit exists in every other browser but not in the log; reload from Redis and it is gone. This presents weeks later as "the document was fine until someone restarted the server", with no way to reconstruct what happened.

Catch-up: delta or snapshot

The client keeps one number, lastSeq, and sends it as since on every join. One decision covers two failures: a client away for four hours wants one 40 KB snapshot, not 90,000 ops, and a client whose position has been trimmed out of the log cannot be served a delta at all, however small the gap looks.

registry.catchUpjs
async catchUp(docId, since) {
  const doc = await load(docId);

  if (Number.isInteger(since) && since >= 0 && doc.seq - since <= config.maxReplayOps) {
    const entries = await oplog.range(docId, since, config.maxReplayOps);
    const contiguous = entries.length === 0 || entries[0].seq === since + 1;
    if (contiguous) {
      const ops = [];
      for (const logEntry of entries) ops.push(...logEntry.ops);
      metrics.inc('collab_sync_delta_total');
      return {
        mode: 'delta',
        // Never claim a higher watermark than the ops we are actually
        // sending: if COUNT capped the page, the client must ask again.
        seq: entries.length > 0 ? entries.at(-1).seq : doc.seq,
        ops,
      };
    }
    log.debug('delta impossible, log was trimmed past the client position', { docId, since });
  }

  metrics.inc('collab_sync_snapshot_total');
  const snap = doc.snapshot();
  return { mode: 'snapshot', seq: snap.seq, snapshot: snap.state, text: snap.text };
}

Presence: heartbeats, TTL and the sweeper

One Redis hash per document, clientId → JSON record — a hash because each entry carries a payload (name, colour, cursor) that changes far more often than membership. Joining is trivial; leaving is the hard part, for the same reason the heartbeat exists. Every record carries a timestamp the pong refreshes, and each instance sweeps its own documents.

presence.js — the sweep, and HDEL as the arbiterjs
async sweep(docIds) {
  const cutoff = Date.now() - config.presenceTtlMs;
  let expired = 0;
  for (const docId of docIds) {
    const k = redisKeys(config.keyPrefix, docId);
    ...
    for (const [clientId, json] of Object.entries(raw)) {
      let entry;
      try { entry = JSON.parse(json); } catch { entry = { ts: 0 }; }
      if (entry.ts > cutoff) continue;
      // Atomic claim: exactly one instance gets removed === 1.
      const removed = await redis.hDel(k.presence, clientId);
      if (removed === 1) {
        expired++;
        metrics.inc('collab_presence_expired_total');
        log.info('expired stale presence', { docId, clientId, ageMs: Date.now() - entry.ts });
        await fanout(docId, 'leave', { clientId, instanceId: entry.instanceId ?? null });
      }
    }
  }
  metrics.inc('collab_presence_sweeps_total');
  return expired;
}

Every instance sweeps, so two can call the same entry stale in the same instant. HDEL returns the number of fields it removed, and only the instance that gets 1 broadcasts the leave — "who may announce this?" as an atomic compare-and-set, with no lock and no leader election.

Why not HEXPIRE, which Redis 8 certainly has

Per-field TTLs (Redis 7.4+) would delete this whole function, and are deliberately unused: when Redis removes a field, nobody is left to broadcast the leave, and every client keeps rendering a cursor for someone who left ten minutes ago. The sweep has to be observable. A hash-level EXPIRE at four TTLs still guards against leaked keys.

A heartbeat is not news

presence.heartbeat() writes the record and does not fan out; update() does both. Get it wrong and 300 clients heartbeating every 15 s produce 300 pub/sub messages fanned out to 300 sockets each — 6,000 frames per second saying "still here", which is exactly the traffic that triggers the backpressure path above.

Graceful shutdown

Signals become an AbortController rather than doing the work inside the handler — Node's answer to signal.NotifyContext — with a second-signal escape hatch so an operator whose shutdown has wedged gets their terminal back. Then four steps, in an order where reversing any two loses data or hangs.

index.js — stop new work, finish in-flight work, release resourcesjs
async function close() {
  if (closed) return;
  closed = true;
  const started = Date.now();

  // Order matters: stop new work, then finish in-flight work, then release
  // resources. Reversing any two of these loses data or hangs.
  await wsServer.close(); // 1. hang up sockets with 1001 "going away"
  await new Promise((resolve) => server.close(resolve)); // 2. stop accepting
  presence.stopSweeper();
  await registry.closeAll(); // 3. final snapshots, unsubscribe
  await bus.close();
  await Promise.allSettled([redis.quit(), subscriber.quit()]); // 4. drain and close
  logger.info('shutdown complete', { ms: Date.now() - started });
}

Draining means closing sockets with 1001 GOING_AWAY rather than dropping them. The client reads the code, waits with jittered backoff and rejoins with since, so a deploy costs each user one delta replay instead of a lost paragraph. Jitter is not decoration: without it every client reconnects in lockstep and knocks over the instance that just came up.

wsServer.close(), and the client side of the same contractjs
// server: refuse new sockets, then hang up the existing ones
async close() {
  shuttingDown = true;
  clearInterval(heartbeat);
  for (const conn of connections) conn.close(CLOSE.GOING_AWAY, 'server shutting down');
  await new Promise((resolve) => wss.close(() => resolve()));
}

// client/client.js: 'close' is the only place reconnection is handled
ws.addEventListener('close', (event) => {
  state.connected = false;
  state.ws = null;
  if (state.closing) return;
  state.reconnects++;
  // Exponential backoff with jitter. Without jitter, every client kicked off
  // by a deploy reconnects in lockstep and knocks the new instance over.
  const wait = Math.min(RECONNECT_MAX_MS, state.backoff) * (0.5 + Math.random());
  state.backoff = Math.min(RECONNECT_MAX_MS, state.backoff * 2);
  setTimeout(connect, wait);
});
The forced-exit timer is not optional either

SHUTDOWN_GRACE_MS (10 s) arms a setTimeout calling process.exit(1). If a Redis command never resolves, close() awaits forever and Kubernetes SIGKILLs you anyway, losing the snapshots you were writing. Failing fast leaves a log line saying which step hung.

The test that proves it

Every unit test here can pass while the system is broken in the only way that matters, because that failure lives in the wiring.   assert.equal(docB.text, converged, 'instance B server-side document');
});

Note the shape of the convergence assertion: not a specific string, but that both replicas agree and all three inserts survived. An exact expected result would encode one interleaving and turn every timing change into a red test. The environment is driven deliberately too (MAX_REPLAY_OPS: '8', SNAPSHOT_EVERY_OPS: '5') so snapshot, delta and sweeper all fire in seconds.

The server-side half is polled before it is asserted, and that is not belt-and-braces. Two clients agreeing only says both clients have everything; it says nothing about when each instance finished applying what it consumed from the bus. Asserting docA.text the instant the clients match races that, and an intermittent red here is indistinguishable from a real convergence bug — the most expensive kind of flake. So the test waits on the cheap synchronous registry.stats() view until both instances report the converged length, then loads the documents and compares the text exactly.

The zombie test: presence left behind by a crashed instance

The one leave path with nobody to notice it: an instance SIGKILLed, its clients left in the presence hash.

await cleanup.hSet(presenceKey, 'zombie', JSON.stringify({
  clientId: 'zombie', name: 'Zombie', color: '#000000', cursor: null,
  instanceId: 'instance-that-died',
  ts: Date.now() - 60_000, // far older than PRESENCE_TTL_MS
}));

await waitFor(async () => {
  const roster = await cleanup.hGetAll(presenceKey);
  return roster.zombie === undefined;
}, 'the sweeper to remove the zombie entry', 15_000);

const expiredAfter = a.metrics.get('collab_presence_expired_total') + b.metrics.get('collab_presence_expired_total');
assert.ok(expiredAfter > expiredBefore, 'exactly one instance claimed and counted the expiry');
assert.equal(expiredAfter - expiredBefore, 1, 'and only one - HDEL is the arbiter, so there is no double report');

> expiredBefore proves the sweeper works, === 1 that arbitration does: two instances both broadcasting pass the first and fail the second.

What to take away

  1. A dead TCP connection and an idle one are identical from userspace. A protocol-level ping with a two-tick liveness flag is the only thing separating them.
  2. ws.send() never blocks and never fails on a slow peer, so an unmonitored bufferedAmount is an unbounded memory leak. Bound it — 1 MiB buffered, 256 frames queued, then close with 4002.
  3. Once anything is queued, everything must queue: bypassing it reorders the stream, and the client's Math.max watermark then permanently hides what it skipped.
  4. Redis pub/sub delivers to the publisher too, and to nobody at all if a subscriber blinks. The instance-id filter fixes the first, gap repair against the Stream the second. Fanout gives speed, the log gives truth.
  5. Append to the durable log before publishing and before applying. Reversing it passes every test and loses edits on the one crash that happens in between.
  6. Reconnect on a single integer: delta when the log contains everything after it contiguously, snapshot otherwise — and never acknowledge a sequence higher than the ops you sent.
  7. Presence expiry must be observable: HEXPIRE removes the field with nobody left to broadcast the leave. Sweep it yourself and let HDEL elect the announcer.
