Running, testing & exercises

Start the stack, watch two browser tabs converge character by character, then split them across two server instances so the Redis backplane is the only thing holding the document together. After that: read the op log with redis-cli, run the convergence property test, load it until the event loop bends, and break Redis, the network and an instance on purpose — each failure has a distinct signature in the metrics.

Two tabs, one instance: see it converge

Open http://localhost:58080 twice. Each tab mints its own client id into sessionStorage, and that id is also its CRDT site id — so the two tabs are genuinely two replicas, not one shared editor with two views. Type in both at the same time, ideally in the same region of the text. Characters interleave; nothing is lost; the sidebar's characters and tombstones counters move independently.

The reason this works without a round trip is in the client's input handler. The textarea gives you a whole new value, not a keystroke, so the client recovers the change with a prefix/suffix scan and turns it into CRDT ops that it applies locally first.

client/client.js — a textarea change becomes opsjs
el.editor.addEventListener('input', () => {
  const before = state.rga.toString();
  const after = el.editor.value;
  const change = diffText(before, after);
  if (change.removed === 0 && change.inserted.length === 0) return;

  const ops = [];
  // Delete first, then insert at the same index: a replacement is exactly that
  // pair, and doing it in the other order would shift the delete range.
  if (change.removed > 0) ops.push(...state.rga.deleteAt(change.start, change.removed));
  if (change.inserted.length > 0) ops.push(...state.rga.insertAt(change.start, change.inserted));

  sendOps(ops);
  renderStats();
  scheduleCursor();
});
Do not duplicate the tab — open a new one

Chrome and Firefox copy sessionStorage into a duplicated tab. Both copies then read the same collab.clientId, so two independent RGA replicas share a site id and their Lamport clocks advance separately. Both mint {s:"c-abc", c:6} for different characters, and integration — which is correctly idempotent on id — discards the second as already-applied. Characters silently vanish and it looks like a CRDT bug. Open a fresh tab (or a private window) instead. The same hazard is why config.js refuses an INSTANCE_ID containing :: site ids are joined into map keys as `${siteId}:${counter}`.

Delete a paragraph and watch length fall while tombstones rises by the same amount — nothing is ever removed from the list.

Two instances: prove the backplane

The single-instance demo proves the CRDT. It proves nothing about the architecture, because both tabs are talking to the same in-memory Document. Put one tab on :58080 and the other on :58081 and every character now has to travel through Redis.

Confirm the traffic really crossed the boundary rather than taking a local shortcut. The server field in each tab's sidebar shows the instance id it is attached to, and the metric that only moves on the receiving side is collab_bus_received_total:

That ops_duplicate_total 0 on app1 is the interesting assertion. Redis pub/sub delivers to the publisher as well, so without self-filtering app1 would apply its own five ops a second time and count five duplicates. The filter is one line:

src/backplane/redisBus.jsjs
// Drop our own echo - see SELF-FILTERING above.
if (envelope.instanceId === config.instanceId) return;
metrics.inc('collab_bus_received_total');
Two instances sharing an INSTANCE_ID is a silent split-brain

Self-filtering is by instance id, so if you export INSTANCE_ID in a shell profile or an .env and start both servers from it, each one drops the other's messages as its own echo. Both processes look perfectly healthy: sockets connect, edits apply locally, /healthz is ok, and collab_bus_published_total climbs. Only collab_bus_received_total stays pinned at zero on both, and the two tabs hold different documents forever. make dev / make dev2 set dev-a and dev-b precisely so you cannot trip this by accident; if you start the servers by hand, leave INSTANCE_ID unset and let config.js generate inst-<8 hex>.

Kill the network and watch it resync

Pull one tab's connection and keep typing in the other. The dropped tab reconnects with exponential backoff plus jitter, sends join with since: lastSeq, and the server decides between two answers. The sidebar's sync mode field shows which one it got.

src/doc/registry.js — the delta/snapshot decisionjs
if (Number.isInteger(since) && since >= 0 && doc.seq - since <= config.maxReplayOps) {
  const entries = await oplog.range(docId, since, config.maxReplayOps);
  const contiguous = entries.length === 0 || entries[0].seq === since + 1;
  if (contiguous) {
    const ops = [];
    for (const logEntry of entries) ops.push(...logEntry.ops);
    metrics.inc('collab_sync_delta_total');
    return {
      mode: 'delta',
      // Never claim a higher watermark than the ops we are actually
      // sending: if COUNT capped the page, the client must ask again.
      seq: entries.length > 0 ? entries.at(-1).seq : doc.seq,
      ops,
    };
  }
  log.debug('delta impossible, log was trimmed past the client position', { docId, since });
}

To force a snapshot instead of a delta, restart the tab with MAX_REPLAY_OPS lowered (the integration test uses 8), or simply type more than 2000 op-log entries while one tab is away.

"simulate network drop" does not simulate a network drop

The button's own comment claims "no close frame, no leave message", but the handler calls state.ws.close(4009, 'simulated drop') — and the browser's WebSocket.close() performs a proper closing handshake. The server sees ws.on('close'), runs presence.leave() immediately, and the other tab's roster updates within milliseconds. What the button genuinely exercises is the reconnect path (backoff, join with since, delta replay), which is most of what you want.

To exercise the sweeper you need a socket that dies without a close frame. Use DevTools → Network → Offline, or docker network disconnect p5-realtime-collab_default p5-app2. Then nothing announces the departure and the ghost user lingers for up to PRESENCE_TTL_MS (45 s) plus one PRESENCE_SWEEP_INTERVAL_MS (10 s) — and collab_presence_expired_total ticks on exactly one instance, because HDEL's return value is the arbiter.

The sequence allocator and the stream are written together by a Lua script, and the reason is worth reading in full because it is the one place a naive implementation loses data:

src/backplane/oplog.js — APPEND_SCRIPTlua
-- KEYS[1] = sequence counter, KEYS[2] = stream
-- ARGV[1] = approximate MAXLEN, ARGV[2] = JSON payload
local seq = redis.call('INCR', KEYS[1])
if seq == 1 then
  -- Reconciliation: the counter is volatile-looking state while the stream is
  -- durable. If the counter was lost (flushed, expired, restored from an older
  -- dump) but the stream survived, restarting at 1 would make XADD fail
  -- forever with "equal or smaller ID". Resume above the last stream id.
  local last = redis.call('XREVRANGE', KEYS[2], '+', '-', 'COUNT', 1)
  if last and last[1] then
    local lastSeq = tonumber(string.match(last[1][1], '^(%d+)')) or 0
    if lastSeq >= seq then
      seq = lastSeq + 1
      redis.call('SET', KEYS[1], tostring(seq))
    end
  end
end
redis.call('XADD', KEYS[2], 'MAXLEN', '~', ARGV[1], tostring(seq) .. '-0', 'p', ARGV[2])
return seq
Why INCR and XADD cannot be two round trips

Two instances appending at the same instant both INCR — getting 11 and 12 — and then both XADD. If 12 lands first, the XADD for 11 is rejected: stream ids must strictly increase. One user's keystroke disappears, with an error nobody is watching for. Redis runs a script to completion without interleaving, so wrapping the pair makes allocation order and use order identical. Verify it yourself: type in both tabs simultaneously and check that XLEN equals GET :seq exactly.

The central assertion is a property test, not an example test. It builds one pool of ops from three replicas editing offline, then replays that pool into 25 fresh replicas in 25 different random orders and demands a single distinct output:

src/crdt/rga.test.js — the convergence propertyjs
const outputs = new Set();
for (let i = 0; i < 25; i++) {
  const replica = replayInto(`fuzz-${i}`, shuffled(pool, rnd));
  assert.equal(replica.pendingCount, 0, `run ${i} left ops unintegrated`);
  outputs.add(replica.toString());
}

assert.equal(outputs.size, 1, `divergence across shuffles: ${[...outputs].map((s) => JSON.stringify(s)).join(' | ')}`);

The PRNG is mulberry32 seeded with a constant, so a failure is reproducible from its seed rather than being a flake you re-run until it passes. pendingCount === 0 matters as much as the text comparison: a replica can produce the right string while quietly holding ops it never managed to integrate, and that divergence surfaces hours later when the next op arrives.

A green integration run may have tested nothing

test/integration.test.js probes Redis at import time and sets skip if it cannot reach it — deliberately, because a red test that only means "you have no Redis today" trains people to ignore red tests. The cost is that make test passes with a smile on a machine where the backplane was never exercised. Read the summary line: # skipped 1 next to # pass is the tell. In CI, assert that the count is zero, or gate the job on a Redis service container.

Load it until it bends

The interesting property of this workload is that fanout is quadratic in participants: N clients each typing R characters per second produce N × (N−1) × R outbound frames per second. 200 clients at 2 cps is 24,000 inbound ops per minute and roughly 80,000 outbound frames per second. That number, not CPU per op, is what decides how many people can share one document.

bench/load.js — N sockets speaking the real protocoljs
import { WebSocket } from 'ws';
import { monitorEventLoopDelay } from 'node:perf_hooks';
import { RGA } from '../src/crdt/rga.js';   // the SAME merge code the server runs

const URL = process.env.WS_URL ?? 'ws://localhost:58080/ws';
const CLIENTS = Number(process.env.CLIENTS ?? 200);
const CPS = Number(process.env.CPS ?? 2);
const SECONDS = Number(process.env.SECONDS ?? 60);

const lag = monitorEventLoopDelay({ resolution: 10 });
lag.enable();
let acked = 0, received = 0;

function spawn(i) {
  const clientId = `load-${i}`;              // also the CRDT site id: must be unique
  const rga = new RGA(clientId);
  const ws = new WebSocket(URL);
  ws.on('open', () => ws.send(JSON.stringify({ t: 'join', docId: 'load', clientId, since: null })));
  ws.on('message', (raw) => {
    const msg = JSON.parse(raw.toString());
    if (msg.t === 'welcome') {
      if (msg.mode === 'snapshot') rga.restore(msg.snapshot);
      else rga.apply(msg.ops ?? []);
      // Stagger the start: 200 clients typing on the same timer tick is a
      // thundering herd, not a workload.
      setTimeout(() => setInterval(() => {
        const ops = rga.insertAt(rga.length, 'x');
        ws.send(JSON.stringify({ t: 'op', docId: 'load', ops }));
      }, 1000 / CPS), Math.random() * 1000);
    } else if (msg.t === 'ops') { rga.apply(msg.ops); received++; }
    else if (msg.t === 'ack') { acked++; }
  });
  ws.on('error', (err) => console.error(clientId, err.message));
}

for (let i = 0; i < CLIENTS; i++) setTimeout(() => spawn(i), i * 10);  // 100 conn/s ramp

setTimeout(() => {
  console.log(JSON.stringify({
    clients: CLIENTS, acked, received,
    generatorLoopMeanMs: +(lag.mean / 1e6).toFixed(2),
    generatorLoopP99Ms: +(lag.percentile(99) / 1e6).toFixed(2),
  }));
  process.exit(0);
}, SECONDS * 1000);

The load generator is single-threaded too

Every simulated client in bench/load.js holds a full RGA and applies every other client's ops, so the generator does N × the CRDT work the server does. Past a few hundred sockets it saturates before the server does and you end up measuring your own harness. That is what generatorLoopP99Ms is for: if it is worse than the server's, throw the run away. Split across processes (CLIENTS=250 × 4 terminals) or run the generator on another machine.

A Redis outage silently forks the typing client

While Redis is paused, registry.submitOps rejects at the oplog.append call, the socket handler replies {t:'error', code:'internal'} — and that is the end of it. The client already applied those ops optimistically and has no retry queue: it never re-sends them, and its lastSeq never advanced past them, so a later reconnect asks for a delta that does not contain them either. That tab now holds characters no other replica will ever see, indefinitely, until something forces a snapshot resync and quietly discards them.

This is not a bug in the CRDT — it is the missing durable send queue on the client, and fixing it properly is exercise 7. Until then, treat collab_redis_errors_total as a data-loss alarm, not a warning.

The restart test is the one that proves the storage layer

docker compose restart app1 is worth running with /healthz open on both ports. The dying instance writes a final snapshot in unload(), its clients reconnect (some to app2), and when a document is next opened on app1 it is rebuilt from snapshot + XRANGE tail with no memory of the old process. The integration test asserts exactly this with a third instance that has never seen the document: assert.equal(doc.text, alice.text, 'reconstructed from Redis only').

Exercises

Roughly in order of difficulty. Each has a test you can write first, and several will make you change the CRDT — run make test-unit after every step, because rga.test.js is the only thing standing between you and a document that diverges under load three weeks from now.

  1. Rich-text attributes. Add a third op type, {type:'fmt', id, key, value}, that attaches a mark to an existing character. Attributes are a last-writer-wins register per (id, key): store the Lamport counter of the op that set it and ignore anything older. Extend protocol.js to validate it and the snapshot format to carry it — note that snapshot() currently serialises a node as [s, c, ch, deleted], so you are changing the on-disk format and need a v: 2 branch in restore().
  2. Tombstone garbage collection, for real. rga.gc(isStable) exists and is tested, but nothing calls it, because nothing can prove stability. Build the proof: have each client report its lastSeq in its presence record, take the minimum across the presence hash, and collect tombstones from ops below that watermark. The trap is the warning in rga.js — every replica must run gc with the same predicate, so the watermark has to come from Redis, not from each instance's local view. Measure tombstoneRatio and snapshot HSTRLEN before and after.
  3. Undo/redo. Keep a per-client stack of the ops that client originated. Undo of an insert is a delete of the same id; undo of a delete needs a resurrect op, which means deleted stops being a monotonic boolean and becomes a LWW flag with a counter. Decide and document what undo means when someone else has edited inside your range — that decision, not the data structure, is the hard part.
  4. Awareness: id-anchored selection ranges. Presence carries {index, length} today, which drifts the moment someone edits above you. Change it to {anchor: <id>, head: <id>} and resolve ids to indices at render time. Tombstones make this work: an anchor on a deleted character still resolves. Then render the peer cursors as overlays instead of the @12 text in the sidebar.
  5. Document permissions. Add a signed token to the join frame and reject unauthorised documents. The subtlety is placement: the check must run before registry.attach, and handleOp's WRONG_DOC guard is what stops a client subscribing to a document by sending an op for it. Add read-only participants and confirm they still receive presence and ops but get an error on submit.
  6. Snapshots in Postgres. Redis is a cache with a volume attached; a document you care about belongs in a database. Keep the op log and pub/sub in Redis, move snapshot.js behind a table (doc_id, seq, state jsonb, ts) with the guarded write as INSERT … ON CONFLICT (doc_id) DO UPDATE … WHERE excluded.seq > snapshots.seq. Compare the round-trip cost with the Lua version and decide whether the write belongs on the critical path at all.
  7. An offline queue in the client. Fixes the data loss above. Buffer every op the client generates in an unacked list; drop entries when the matching ack arrives; on reconnect, re-send the buffer after the welcome. Idempotent integration makes the resend safe — identical ids are deduplicated. Persist the buffer to IndexedDB so a browser crash does not lose it, and handle the case where the welcome was a snapshot that already contains some of the buffered ops.
  8. Swap RGA for Yjs and measure. Keep the transport, the op log and the presence layer; replace the CRDT with Y.Text and ship binary updates instead of JSON ops. Then measure the three numbers that matter: bytes on the wire for a 10,000-character paste, snapshot size after deleting a 400-character paragraph (one tombstone versus 400), and time to load a 100,000-op document. Yjs's block-wise representation is exactly the escape from the tombstone problem described at the bottom of rga.js.
  9. Reliable fanout. Replace the pub/sub channel with a Redis Stream consumer group per instance, so an instance disconnected for a second replays instead of relying on gap repair. Measure the added latency per op, then decide honestly whether gap repair was the better trade — it usually is, and knowing why is the point.
  10. End-to-end encryption. Encrypt ch and the attribute values client-side; leave ids, after and type in the clear so the server can still order and integrate. Work out what the server can still infer (document length, edit positions, typing cadence, who is in the room) and what breaks: the server can no longer produce a text field in the snapshot, and any server-side search or export is gone.
  11. Scale-test to 10,000 connections. Raise the fd limit (ulimit -n 65535), spread clients over many documents rather than one, and run several server instances behind a load balancer with sticky sessions off — the backplane makes stickiness unnecessary, which is worth proving. Find where it actually breaks: it will be per-connection memory (ws allocates a receiver buffer per socket, and perMessageDeflate is off for exactly this reason) or the fanout loop in broadcastLocal, which re-encodes JSON once per recipient.
  12. Prove the backpressure path with a test. Write an integration test with a client that completes the WebSocket handshake and then never reads from its TCP socket, while a second client types thousands of characters. Assert the slow one is closed with 4002 and the fast one is untouched. Setting MAX_OUTBOUND_QUEUE=8 in the test env makes it run in milliseconds; a stock ws client is useless here because it always drains.

What to take away

  1. Two tabs on one port test the CRDT; two tabs on two ports test the architecture. Until collab_bus_received_total is non-zero on the instance that did not originate the edit, you have not exercised the backplane at all.
  2. Self-filtering is by INSTANCE_ID, so two instances sharing one is a silent split-brain: healthy logs, healthy /healthz, two permanently different documents. Leave the variable unset and let config.js generate one.
  3. The client persists exactly one number across a disconnect — lastSeq. Delta versus snapshot is a server decision made from that number plus entries[0].seq === since + 1; the contiguity check is a correctness guard, not an optimisation, because a trimmed log would otherwise produce a delta that skips characters.
  4. XLEN should equal GET :seq on an untrimmed document. If it does not, a sequence number was allocated and never used — which is precisely the INCR/XADD race the Lua script exists to close.
  5. The integration test skips without Redis rather than failing. A green make test proves nothing about fanout, presence or catch-up unless the summary says # skipped 0.
  6. Fanout is quadratic in participants, not linear, and broadcastLocal re-encodes per recipient. Load-test with the server's own event-loop delay exposed as a gauge — and register the gauge in metrics.js first, or metrics.set() throws unknown metric.
  7. A Redis outage does not stop the editor; it forks it. Ops typed during the outage are applied locally, rejected by the server, never retried, and never recovered — the client has no durable send queue. That is the single largest hole in this design and exercise 7 is the fix.
