Distributed Job Scheduler & Workflow Engine

A horizontally scalable scheduler in which every instance is identical — each one schedules, each one executes, and there is no control-plane tier and no coordination service. It runs one-off jobs, six-field cron jobs and DAG workflows across N processes with at-least-once delivery, leases, backoff with full jitter, a DEAD_LETTER terminus and an idempotency ledger. The teaching point is that all of the coordination is six SQL statements and the transaction boundaries around them.

Java 17 Spring Boot 3.4.1 PostgreSQL 16 Redis 8 Project 1
The one hard problem

N identical processes must agree on who runs what, without talking to each other. That is the entire project. Every other feature — cron, DAGs, retries, the REST API — exists to put pressure on that one question from a different angle.

It decomposes into two kinds of mutual exclusion, and they are not the same problem:

  1. Exclusion over rows. Two workers poll the same queue in the same millisecond and must not both take execution #4171. Solved by SELECT … FOR UPDATE SKIP LOCKED plus an UPDATE to RUNNING in one transaction: the row lock holds the line until COMMIT, and after COMMIT the status column holds it.
  2. Exclusion over time. Both instances tick their cron loop every second and exactly one occurrence row must be created per schedule slot. Solved by pg_try_advisory_xact_lock inside @Transactional — transaction-scoped, so COMMIT releases it, an exception path cannot leak it, and a SIGKILLed JVM does not wedge the cluster.

The answer this project commits to is put both in PostgreSQL. Not because a database is the elegant place for a queue, but because the alternative — a lock service that can disagree with the database about who owns a row — is precisely the failure mode a scheduler exists to avoid. Redis is present, and deliberately not on the correctness path: it holds one sorted set of live node ids so the stats endpoint can list peers, its health indicator is disabled so a Redis outage cannot pull an instance out of a load balancer, and you can delete it entirely without changing a single guarantee.

What you will build

One Spring Boot application, run twice. Each process starts five @Scheduled loops and a REST controller; there are no roles, no membership protocol and no leader between ticks. An instance is a peer that happens to hold some row locks right now.

The status machine

Six statuses, and every transition below is a single UPDATE guarded by the status it is moving out of.

ExecutionStatus — every edge is one guarded UPDATEtext
PENDING ──claim──> RUNNING ──success──> SUCCEEDED
   ^                  │
   │                  ├── retryable failure, attempt < max ──> PENDING (run_at += backoff)
   │                  ├── retryable failure, attempt >= max ─> DEAD_LETTER
   │                  ├── NonRetryableException ─────────────> FAILED

BLOCKED ── all parents SUCCEEDED for this scheduled_for ──> PENDING
BLOCKED ── an ancestor reached FAILED/DEAD_LETTER/CANCELLED ──> CANCELLED

The mechanisms

Each row is a mechanism in the code, the concept it is a concrete instance of, and where that concept was taught in isolation. Reading the module page next to the source is the point of the project.

MechanismWhere it livesConcept it demonstratesModule
Exclusive claim JobExecutionRepository.selectDueForUpdate → markRunning FOR UPDATE SKIP LOCKED as a queue: FOR UPDATE buys correctness, SKIP LOCKED buys throughput. Delete each in turn and see which assertion fails. Postgres concurrency patterns, SQL locking
Partial claim index idx_job_execution_claim in V1__schema.sql Why (status, run_at) WHERE status = 'PENDING' and not (run_at) — the index that keeps a queue fast as terminal history accumulates. Index design
Leader election per tick AdvisoryLock + CronTicker.tick pg_try_advisory_xact_lock: transaction-scoped so a pool cannot strand it, non-blocking so losers do nothing rather than queue. Coordination
Lease + heartbeat + reclaim WorkerLoop.heartbeat, OrphanSweeper.sweep Failure detection is a timestamp comparison, not a protocol. 30s lease / 5s heartbeat = six missed beats before reclaim; a reclaim costs an attempt so a worker-killing job dead-letters instead of looping. Failure models
Backoff with full jitter RetryPolicy cap = min(maxDelay, base × 2^attempt), then delay = uniform(0, cap). The row goes back to PENDING with a future run_at — never a sleeping thread holding a lease. Resilience patterns
Idempotency ledger processed_execution + WorkerLoop.completeSuccess At-least-once delivery turned into effectively-once at the handler: a deterministic key jobId@ISO-instant, written in the same transaction as the status. The schema comment is honest about which duplicate this closes and which it does not. Idempotency
DAG eligibility DagResolver NOT EXISTS (… NOT EXISTS …) — relational division, SQL's way to say for all parents. Set-based, so two resolvers racing produce the same result. Advanced joins
Cycle rejection JobDependencyRepository.wouldCreateCycle Recursive CTE reachability at create time, because a cycle in the graph is a deadlock you cannot detect at runtime — every row just sits BLOCKED forever. Recursive CTEs
Transaction boundaries ExecutionClaimer.claim (REQUIRES_NEW), CronTicker The proxy rules that decide whether @Transactional exists at all: a self-invocation silently bypasses the proxy, which here would silently disable the advisory lock and let every instance win. AOP & proxies, Transactions
Scheduled loops five @Scheduled methods, spring.task.scheduling.pool.size The default scheduling pool is one thread: five loops on one thread means a slow sweep delays every tick. Sizing it is not optional. Caching & scheduling
Backpressure WorkerLoop.pollOnce, bounded pool with AbortPolicy Claim min(batchSize, free slots), never more: a claimed row is RUNNING with a ticking lease whether or not a thread is on it. AbortPolicy over CallerRunsPolicy so the poll loop is never the thing that blocks. Executors & futures
Redis kept off the path scheduler:nodes sorted set, health indicator disabled The counter-example: why the lease is not a Redis lock. Two systems that can disagree about who owns a row is the exact failure this design avoids. Redis distributed locks
Error contract GlobalExceptionHandler RFC 7807 ProblemDetail with field-level bean-validation detail, so a bad cron expression fails at create time rather than never firing. Web MVC
Migrations & real-database tests V1__schema.sql, AbstractPostgresIT Flyway on startup; Testcontainers runs a singleton postgres:16-alpine, because SKIP LOCKED and advisory locks cannot be asserted against H2. Migrations, Spring testing
The most instructive bug in the project

Remove the backpressure — claim claimBatchSize unconditionally instead of min(batchSize, free slots) — and nothing appears to break. Then queue a few hundred jobs with {"sleepMs": 20000}. Rows go RUNNING, sit in the local queue past their 30s lease, get reclaimed by the peer, and run twice. The mechanism failure is three hops away from the line you changed, which is exactly why it is worth reproducing on purpose. Exercise 7 in Running, testing & exercises walks it.

Why a diamond and not a chain

DagEligibilityTest is built on a four-node diamond on purpose. A linear chain passes even if the eligibility rule is the broken any parent succeeded; only a fan-in distinguishes all from any. Pick the topology that can fail.

Quick start

JDK 17 exactly, Maven 3.9+, and a running Docker daemon with Compose v2 (docker compose, not docker-compose). Ports 15432, 16379, 18080 and 18081 must be free. Images pulled: postgres:16-alpine, redis:8-alpine.

single instance — the normal development loopbash
cd 10-projects/p1-job-scheduler/code

make up      # postgres + redis, waits for both healthchecks
make run     # one instance on :18080; Flyway applies V1__schema.sql on startup

# in another shell
make seed    # a 10s cron job, a flaky job, and a 4-node diamond DAG
curl -s localhost:18080/api/jobs | jq
curl -s localhost:18080/api/executions/stats | jq
make status  # execution counts grouped by status, straight from psql
two instances — what the project is actually aboutbash
make up-cluster   # postgres + redis + scheduler-a :18080 + scheduler-b :18081
make logs         # watch both instances interleave

# SKIP LOCKED partitions the queue cleanly: no row is ever claimed twice
make psql
  SELECT claimed_by, status, count(*) FROM job_execution GROUP BY 1,2 ORDER BY 1,2;

# the cron job fires once per occurrence although BOTH instances tick every second
  SELECT scheduled_for, count(*) FROM job_execution
   WHERE job_id = (SELECT id FROM job WHERE name='heartbeat-every-10s')
   GROUP BY 1 HAVING count(*) > 1;        -- always empty

# ask each instance what it thinks it is doing
curl -s localhost:18080/api/executions/stats | jq '{nodeId, liveNodes, inFlightOnThisNode}'
curl -s localhost:18081/api/executions/stats | jq '{nodeId, liveNodes, inFlightOnThisNode}'

# kill one mid-flight: SIGKILL, no handover, leases simply stop being renewed
docker kill p1-scheduler-a
make logs-db      # within ~30s: "reclaimed execution … -> PENDING (attempt 1/3)"
tests and the rest of the targetsbash
make test     # mvn test; Testcontainers starts its OWN postgres:16-alpine
make build    # fat jar, tests skipped -> target/job-scheduler.jar
make down     # stop, keep volumes
make clean    # stop, delete volumes, mvn clean
make help     # list every target

# no make on Windows? every target is deliberately a one-liner:
docker compose up -d --wait postgres redis
mvn -B spring-boot:run
mvn -B test
The tests disable all five loops

AbstractPostgresIT switches every @Scheduled loop off and the tests call claim(), sweep(), tick() and pollOnce() directly. That is the difference between asserting on a mechanism and asserting on whether a timer happened to fire — the second kind of test is the one that goes flaky on a loaded CI box and then gets deleted. The suite needs a Docker daemon but never touches the Compose stack's database.
