Running, testing & exercises

The exact commands to bring the cluster up, submit work and watch it execute — then three deliberate failures (a SIGKILLed worker, a handler that never succeeds, a dead database) with the log lines and SQL that prove the recovery machinery works. Ends with twelve exercises that each break one mechanism on purpose.

Prerequisites and what the stack costs

Everything below assumes you already have Docker, a JDK and Maven. The versions are not negotiable in one place and flexible in another — the JDK matters, the rest does not.

Two local instances silently share one node id

application.yml sets node-id: ${HOSTNAME:${random.uuid}}. Inside a container HOSTNAME is the container id, so the two compose instances are distinct. On your laptop HOSTNAME is your laptop, so two local mvn spring-boot:run processes both call themselves my-laptop — and the heartbeat statement is scoped by claimed_by = :workerId, which means each process happily renews the other's leases for work it is not doing. The orphan sweeper then never fires, and a genuinely dead instance leaks its rows forever. Run the second local instance with -Dspring-boot.run.arguments=--scheduler.node-id=local-b --server.port=18081, or just use make up-cluster.

Submitting a job and watching it execute

make seed creates six jobs in one go: a ten-second cron job, a job that fails its first three attempts, and a four-node diamond DAG. Here is the cron one on its own, because the response shows the two fields worth understanding.

handler is echoed back even though it is not a column — it is derived from the reserved handler key in the payload, and "which handler will actually run?" is the first question you ask when a job misbehaves. maxAttempts: 3 is the default applied in CreateJobRequest.withDefaults(), not a database default reflected back.

Spring cron has six fields, and the five-field form is rejected

"*/10 * * * *" gets you a 400 with a message naming all six fields. That is deliberate: JobController.validateCron calls CronExpression.isValidExpression at create time rather than at tick time, so a typo is an error the author sees immediately instead of a job that looks scheduled and silently never fires. Note also that a five-field expression is not invalid in every cron dialect — it just means something completely different, which is the worse failure.

Ten seconds later, nothing has run — but six rows exist. That surprises people, so it is worth seeing:

make psql, then look at the queuesql
SELECT status, count(*), min(run_at), max(run_at)
  FROM job_execution
 WHERE job_id = (SELECT id FROM job WHERE name = 'heartbeat-every-10s')
 GROUP BY status;

  status   | count |            min             |            max
-----------+-------+----------------------------+----------------------------
 PENDING   |     5 | 2026-09-02 10:15:40+00     | 2026-09-02 10:16:20+00
 SUCCEEDED |     1 | 2026-09-02 10:15:30+00     | 2026-09-02 10:15:30+00

scheduler.cron.horizon is 60 s, so each tick materialises every occurrence falling inside the next minute, bounded by max-occurrences-per-tick: 16. The rows are created early and simply are not claimable until run_at <= now(). That is the whole reason the claim predicate has two terms rather than one, and it is why a schedule edit takes up to a horizon to take effect — already-materialised occurrences are deliberately left alone by PATCH /api/jobs/{id}.

trigger a run of the DAG root — the whole closure is created at oncebash
ROOT=$(curl -s localhost:18080/api/jobs | jq -r '.[] | select(.name=="dag-extract") | .id')
curl -sS -X POST localhost:18080/api/jobs/$ROOT/trigger | jq '{scheduledFor, createdCount}'

202 rather than 200 is not pedantry: the response is emitted long before any handler runs. createdCount: 4 is the diamond — dag-extract PENDING plus three BLOCKED steps, all sharing that one scheduledFor. Six fractional digits, because ExecutionMaterializer.normalize truncates to microseconds to match timestamptz; a nanosecond-precision instant would produce an idempotency key that no longer matches the value the database stored.

lagMillis is the number to watch and to alert on. It is the gap between the logical occurrence and the first attempt's start — started_at is written once, with COALESCE(started_at, :now), and a retry never clears it — so for a DAG leaf it is mostly upstream execution time, and for a cron job it is pure scheduling delay. It stays comparable across a row that succeeded first time and a row that took three attempts, which is the whole point: growing lag with a flat failure count means the cluster is under-provisioned, while failures show up in status instead. Note what is missing from that response: claimedBy, claimedAt and heartbeatAt are all absent, because JobExecution.releaseClaim() nulls them on completion and Jackson is configured to omit nulls.

countsByStatus in the same response is cluster-wide, because it comes from a table both instances share; everything else is per-instance. That asymmetry is the point of the endpoint. 143 versus 128 is what SKIP LOCKED fairness looks like — roughly even, never exactly even, because each poll takes the first batch of rows nobody else holds, and the batch is min(claimBatchSize, free slots). availableCapacity is 8 in a container (SCHEDULER_WORKER_THREADS: "4", and capacity() = threads * 2).

claimed_by is NULL for everything except in-flight rows

The obvious query — SELECT claimed_by, status, count(*) FROM job_execution GROUP BY 1,2; — will show you (NULL, SUCCEEDED, 271) and nothing else, and you will conclude the claim is broken. It is not: every terminal transition calls releaseClaim(), which nulls claimed_by, claimed_at and heartbeat_at. It has to — the job_execution_running_is_owned CHECK constraint permits an owner only on RUNNING rows. So that query only ever shows live work; run it in a watch loop while a backlog drains, or read the per-node counters from /api/executions/stats for the historical split.

watch -n 0.5 "docker compose exec -T postgres psql -U scheduler -d scheduler -c \
  \"SELECT claimed_by, count(*) FROM job_execution WHERE status='RUNNING' GROUP BY 1;\""

The cron job is the leader-election test. Both instances tick every second; exactly one wins pg_try_advisory_xact_lock per tick, and the loser discovers it lost in microseconds and does nothing. The proof is that no occurrence is ever duplicated:

this query is always emptysql
SELECT scheduled_for, count(*)
  FROM job_execution
 WHERE job_id = (SELECT id FROM job WHERE name = 'heartbeat-every-10s')
 GROUP BY 1
HAVING count(*) > 1;

-- And the lock itself is essentially never observable, because it is
-- transaction-scoped and a tick takes a couple of milliseconds:
SELECT locktype, objid, granted FROM pg_locks WHERE locktype = 'advisory';
The unique constraint is the belt; the lock is the braces

Delete the advisory lock entirely and you still get no duplicate runs — ON CONFLICT (idempotency_key) DO NOTHING in insertIfAbsent catches it, because ExecutionMaterializer.idempotencyKey is a pure function of (jobId, scheduledFor). What you lose is efficiency and signal: every instance burns a transaction per job per tick, and the losers log constraint churn forever. Electing one materialiser makes the tick cost O(1) per cluster instead of O(instances).

Breaking it on purpose

1. Kill a worker mid-execution

give it something slow to hold, then SIGKILL the processbash
SLOW=$(curl -sS -X POST localhost:18080/api/jobs -H 'Content-Type: application/json' \
  -d '{"name":"slow","type":"ONE_OFF","payload":{"handler":"logging","sleepMs":120000}}' | jq -r .id)
curl -sS -X POST localhost:18080/api/jobs/$SLOW/trigger > /dev/null

# wait until a row is RUNNING, then:
docker kill p1-scheduler-a        # SIGKILL - no @PreDestroy, no handover
make logs                         # watch scheduler-b
what scheduler-b prints, ~30–40s after the killtext
c.a.scheduler.worker.OrphanSweeper : reclaimed execution 8c1e4a91-... of job 'slow' from
                                     'scheduler-a' -> PENDING (attempt 1/3)
c.a.scheduler.worker.OrphanSweeper : orphan sweep reclaimed 1 execution(s)
c.a.s.worker.handlers.LoggingHandler : [job-worker-2] job='slow' attempt=1 ...

Note attempt 1/3. The sweeper deliberately routes through RetryPolicy.recordFailure rather than issuing a bare UPDATE … SET status = 'PENDING':

OrphanSweeper.sweep — the loop that charges the attemptjava
for (JobExecution row : rows) {
    String previousOwner = row.getClaimedBy();
    Instant lastBeat = row.getHeartbeatAt();
    String message = "lease expired: owner '" + previousOwner + "' last heartbeat at "
            + lastBeat + ", lease timeout " + props.worker().leaseTimeout();

    retryPolicy.recordFailure(row, message, now, true);

    log.warn("reclaimed execution {} of job '{}' from '{}' -> {} (attempt {}/{})",
            row.getId(), row.getJob().getName(), previousOwner, row.getStatus(),
            row.getAttempt(), row.getJob().getMaxAttempts());
}

A job whose handler reliably wedges the JVM would otherwise be reclaimed and re-run forever — an infinite loop that looks like healthy throughput on every dashboard. Charging an attempt means it eventually dead-letters and becomes visible. The reclaim also inherits the jittered backoff, so a dead instance holding 200 rows does not return all 200 to PENDING at the same instant and immediately flatten its surviving peers.

docker stop shows you nothing — that is the wrong verb

docker stop sends SIGTERM, which runs WorkerLoop's @PreDestroy: the pool drains for up to shutdown-grace: 20s, then releaseToPending hands the still-running rows straight back — no attempt charged, no 30-second wait, and the log says released 1 in-flight execution(s) back to PENDING on shutdown. That is the rolling-deploy path and it is correct, but it exercises none of the recovery machinery. Use docker kill when you want to see the sweeper.

DOOMED=$(curl -sS -X POST localhost:18080/api/jobs -H 'Content-Type: application/json' \

watch -n 1 "curl -s localhost:18080/api/jobs/$DOOMED/executions | jq -c '.[] | {status, attempt, runAt, error}'"

# ...and afterwards, the other kind of failure:
curl -sS -X PATCH localhost:18080/api/jobs/$DOOMED -H 'Content-Type: application/json' \
  -d '{"payload":{"handler":"logging","failFatally":true}}'
curl -sS -X POST localhost:18080/api/jobs/$DOOMED/trigger > /dev/null
# -> status FAILED, attempt 1, no backoff, no further attempts consumed.
three attempts, then the terminustext
execution 1f0c... of job 'doomed' failed (attempt 1/3): IllegalStateException: simulated
    retryable failure on attempt 0 of job 'doomed' -> PENDING
execution 1f0c... of job 'doomed' failed (attempt 2/3): IllegalStateException: simulated
    retryable failure on attempt 1 of job 'doomed' -> PENDING
execution 1f0c... of job 'doomed' failed (attempt 3/3): IllegalStateException: simulated
    retryable failure on attempt 2 of job 'doomed' -> DEAD_LETTER

Three executions, not four. attempt counts attempts that have already finished and failed, so it is 0 on the first run; after the third failure it is 3, 3 >= 3 holds, and the row is dead-lettered. That off-by-one is the classic bug in every retry implementation, and it is worth watching the backoff too — the gaps between those three lines will be roughly 0–2 s and 0–4 s, not exactly 2 s and 4 s:

RetryPolicy.capFor — doubling, not shiftingjava
public Duration capFor(int attempt) {
    long base = Math.max(1L, props.retry().baseDelay().toMillis());
    long max = Math.max(base, props.retry().maxDelay().toMillis());

    long cap = base;
    for (int i = 0; i < attempt && cap < max; i++) {
        cap = cap * 2;
    }
    if (cap > max || cap <= 0) {
        cap = max;
    }
    return Duration.ofMillis(cap);
}

The delay itself is uniform(0, cap) — full jitter. Plain exponential backoff does not spread load, it synchronises it: 500 jobs that fail in the same second all retry at exactly base × 2 seconds later, delivering the downstream dependency the same simultaneous spike that knocked it over, in lockstep, forever. The loop rather than base << attempt matters too: Java masks the shift distance to the low six bits, so 1L << 64 is 1, and attempt 64 of a job would suddenly get a one-millisecond backoff.

That distinction between NonRetryableException and everything else is the difference between a queue that drains and one that spends its capacity re-running work that was doomed the first time. A missing handler bean takes the same route — WorkerLoop.run fails terminally rather than burning three attempts, because retrying will not conjure a bean into existence.

3. Stop the database

the whole coordination substrate, gonebash
docker compose stop postgres
make logs                       # then, 30 seconds later:
docker compose start postgres
what you see — and how long between each linetext
c.a.scheduler.worker.WorkerLoop   : worker poll failed
    org.springframework.jdbc.CannotGetJdbcConnectionException: Failed to obtain JDBC Connection
    Caused by: java.sql.SQLTransientConnectionException: scheduler-pool - Connection is not available,
               request timed out after 10001ms
c.a.scheduler.worker.WorkerLoop   : heartbeat failed
c.a.scheduler.scheduler.CronTicker: cron tick failed
c.a.scheduler.worker.OrphanSweeper: orphan sweep failed

The back-off here is emergent rather than designed, and it is worth understanding because it is the honest answer. Every loop is @Scheduled(fixedDelay), so the next run starts after the previous one finishes. Hikari's connection-timeout is 10 000 ms, so a poll that used to take 2 ms now takes 10 s before throwing. The worker's poll rate therefore collapses from 2/s to roughly one attempt every 10.5 s all by itself — no retry policy, no circuit breaker, just fixedDelay plus a bounded timeout. Swap fixedDelay for fixedRate and this becomes a thread pile-up instead.

The database outage costs you an attempt on every in-flight job

Handlers keep running through a Postgres outage — LoggingHandler never touches the database. But their heartbeats cannot land, so if the outage exceeds lease-timeout every in-flight row is reclaimed the moment the sweeper can run again, and each reclaim charges an attempt. A three-minute database blip therefore dead-letters any 3-attempt job that was running when it started. The duplicatesSuppressedOnThisNode counter in /api/executions/stats going up afterwards is the idempotency ledger visibly saving you from running the survivors twice. If that bothers you, the question to sit with is whether a lease expiry during a total outage is a failed attempt in any useful sense — the sweeper cannot tell the difference between "the owner died" and "nobody could reach the database", because both are the same absent timestamp.

There is no Micrometer instrumentation in this project

Search the source for MeterRegistry and you will find nothing. Everything domain-specific — claim rate, lag, dead-letter count, duplicates suppressed — lives in AtomicLong fields on WorkerLoop and is exposed only through GET /api/executions/stats, which means it is per-instance, resets on restart, and cannot be scraped into a dashboard. That is a deliberate gap, and closing it is exercise 6. Also note that the worker pool is a hand-built ThreadPoolExecutor, not a Spring TaskExecutor, so Boot's automatic executor.* metrics do not cover it either.

Tests

four classes, one real PostgreSQLbash
make test     # depends on `up`, but the suite brings its OWN postgres:16-alpine via Testcontainers
mvn -B test -Dtest=ClaimConcurrencyTest    # the one to read first

ClaimConcurrencyTest runs six threads over 400 executions with a batch size of 7 (deliberately not a divisor of anything) and asserts set disjointness and total conservation. All five @Scheduled loops are disabled in AbstractPostgresIT; the tests call claim(), sweep(), tick() and pollOnce() directly, so an assertion is about a mechanism rather than about whether a timer happened to fire. The container is a static singleton started once for the JVM, not a per-class @Container, so four test classes cost one container start.

The Docker image build skips tests, and it has to

RUN mvn -B -q -DskipTests package is not laziness — Testcontainers needs a Docker daemon, and there is no daemon inside an image build. If you add a CI step that builds the image and calls it "tested", it is not. Run make test on the host separately.

Exercises

Ordered roughly by difficulty. Each is designed to make one mechanism visible by breaking it or extending it. Write the test first where one exists to write.

  1. Separate the two keywords. Remove SKIP LOCKED from selectDueForUpdate and run ClaimConcurrencyTest. It still passes — correctness came from FOR UPDATE alone. Now time it and watch make logs-db fill with log_lock_waits output: you have converted six workers into one. Then remove FOR UPDATE too and watch the disjointness assertion fail. Hint: the goal is to be able to say in one sentence which guarantee each keyword provides.
  2. Break the leader election two ways. Change pg_try_advisory_xact_lock to pg_try_advisory_lock and run make up-cluster; it will appear to work, then cron materialisation stops cluster-wide. Separately, remove @Transactional from CronTicker.tick. Hint: watch SELECT * FROM pg_locks WHERE locktype='advisory' in the first case; read AdvisoryLock.tryLock's guard clause for why the second case throws instead of silently letting every instance win.
  3. Make the lease too short. Set lease-timeout: 3s with heartbeat-interval: 5s — the application refuses to start. Then set lease-timeout: 6s (legal, but tight), trigger a logging job with {"sleepMs": 30000}, and watch the sweeper reclaim work that is still running. Hint: duplicatesSuppressedOnThisNode climbing is the idempotency ledger visibly doing its job.
  4. Remove the backpressure. In WorkerLoop.pollOnce, claim props.worker().claimBatchSize() unconditionally instead of Math.min(props.worker().claimBatchSize(), capacity). Queue a few hundred {"sleepMs": 20000} jobs. Hint: a claimed row is RUNNING with a ticking lease whether or not a thread is on it. Watch rows queue locally, expire, get reclaimed by the peer, and run twice. This is the most instructive bug in the project.
  5. Make cron catch-up a policy instead of an accident. Stop the cluster for ten minutes with a */10 * * * * * job defined, then start it: the cursor in CronTicker.materializeOccurrences resumes from findLatestScheduledFor, so it replays every missed occurrence, sixteen per tick (max-occurrences-per-tick), for about four minutes. Add a catch-up: ALL | LATEST_ONLY | NONE setting per job. Hint: the two hard questions are what scheduled_for should be for a coalesced occurrence (it must stay in the past, or handlers that partition by it write to the wrong day), and why a job seen for the first time deliberately starts at now rather than backfilling from job.created_at.
  6. Instrument it properly. Replace the AtomicLong counters with Micrometer meters: a counter per terminal status, a gauge for slots.availablePermits(), and a timer around handler.execute. Add a gauge for queue depth and one for oldest-due age. Hint: the oldest-due age is the single best health signal in the system and it is a SELECT min(run_at), so it must be a polled gauge with a cache, not a query per scrape.
  7. Add priority. Give job a priority column and change the claim to ORDER BY priority DESC, run_at. Hint: the index must become (status, priority DESC, run_at) or you reintroduce a Sort node. Then answer whether a low-priority job can starve, and measure it with the ClaimConcurrencyTest harness rather than guessing.
  8. Add a per-job concurrency limit. No more than N executions of the same job may be RUNNING cluster-wide. Hint: two shapes, and the trade is real. A window function inside the claim (row_number() OVER (PARTITION BY job_id)) keeps it in one statement but interacts badly with SKIP LOCKED, because rows skipped by a peer still consume window slots. A job_concurrency counter table is exact but adds a contended row. Decide which wrongness you can live with, and write the test that distinguishes them.
  9. Replace polling with LISTEN/NOTIFY. Add a trigger that NOTIFYs on insert of a PENDING row, and have workers claim on notification instead of every 500 ms. Hint: this is a latency optimisation and nothing else — you must keep the poll as a floor. NOTIFY is delivered on COMMIT and only to currently-connected listeners, it is not durable, and it needs a dedicated connection outside the Hikari pool. A row whose run_at is in the future generates no useful notification at all. Measure the p50 lag before and after and decide whether it was worth the connection.
  10. Fan out one step into N. Let a DAG step declare {"fanOut": "shards", "count": 16} and materialise sixteen sibling executions whose children wait for all of them. Hint: the idempotency key is jobId@instant, which admits exactly one row per (job, occurrence). You need a third component. Work out what that does to the NOT EXISTS (… NOT EXISTS …) eligibility predicate.
  11. Partition job_execution by month, and prune the ledger. Convert it to a PARTITION BY RANGE (scheduled_for) table with monthly children, plus a job that creates next month's partition in advance and detaches expired ones. Then prune processed_execution, which only grows. Hint: two traps. The primary key must include the partition key, which breaks the plain UNIQUE (idempotency_key) constraint the entire idempotency design rests on — decide whether to keep the ledger unpartitioned as the global uniqueness authority. And prune the ledger no faster than the longest window in which a duplicate could still arrive, which is lease-timeout + max-delay: deleting a key early silently re-enables a duplicate side effect. Also re-check the claim plan — partition pruning cannot help a predicate on status and run_at.
  12. Add distributed tracing. Bring in spring-boot-starter-actuator's Micrometer Tracing bridge and propagate a trace context from POST /trigger through materialisation, claiming and execution — including across the DAG. Hint: the hard part is that the trace crosses a database table and a process boundary with no HTTP call in between. Store the traceparent on the execution row at materialisation and restore it in WorkerLoop.run; a retry three minutes later on a different instance should still join the same trace.

What to take away

  1. Use docker kill, not docker stop, to exercise recovery. SIGTERM runs @PreDestroy, which releases rows to PENDING immediately with no attempt charged; SIGKILL is the only way to see the 30-second lease expiry and the sweeper.
  2. claimed_by is NULL on every non-RUNNING row, because releaseClaim() must clear it to satisfy the job_execution_running_is_owned CHECK. Sample it while work is in flight, or read the per-node counters from /api/executions/stats instead.
  3. Cron occurrences appear up to horizon (60 s) before they are claimable, so a freshly seeded ten-second job immediately has six PENDING rows. The claim predicate has two terms — status = 'PENDING' AND run_at <= now() — precisely for this reason.
  4. A lease expiry and a thrown exception converge on the same transition and both charge an attempt. That is what stops a handler that reliably kills its JVM from looping forever, and it also means a database outage longer than lease-timeout costs every in-flight job an attempt.
  5. The back-off under a dead database is emergent, not designed: fixedDelay plus Hikari's 10 s connection-timeout collapses the poll rate from 2/s to ~1 per 10.5 s on its own. Swapping to fixedRate would replace that with a thread pile-up.
  6. The only metrics that exist are Boot's own. Everything domain-specific is an AtomicLong behind one REST endpoint — per-instance, reset on restart, unscrapeable. Watch hikaricp.connections.pending as the leading indicator: connection starvation produces self-inflicted lease expiry, which looks exactly like a peer dying.
  7. The exercises worth doing first are 1 and 4. Exercise 1 shows you which guarantee comes from FOR UPDATE and which from SKIP LOCKED; exercise 4 shows you why claiming work you have no thread for is the same thing as running it twice.
