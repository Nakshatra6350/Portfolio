Implementation walkthrough

A file-by-file reading of the scaffold, following the decisions rather than the packages: why the claim is one transaction and not two, why the cron lock is transaction-scoped, why the worker never claims a row it cannot start, and what the arithmetic between the heartbeat and the lease actually has to satisfy.

Java 17 Spring Boot 3.4.1 PostgreSQL 16 Redis 8 distributed queue
The mental model for the whole codebase

Every instance runs all five loops and PostgreSQL alone arbitrates: row locks decide who owns work, an advisory lock decides who materialises cron occurrences, a timestamp decides who is alive. The Java is thin. Every class below either opens the right transaction, or handles what happens after a claim succeeds and its owner then fails.

The five loops, and what each one touches

Spring's default scheduler pool is one thread

Five @Scheduled methods on a single-threaded scheduler run in series: a slow cron tick delays the heartbeat, leases expire, the sweeper reclaims healthy work. Hence spring.task.scheduling.pool.size: 6. The same argument sizes Hikari at 20 — below the 8 worker threads, completions queue behind claims and the instance times out its own live work.

The claim: one transaction, two statements

Everything rests on this. The query is hand-written native SQL because JPA has no expression for FOR UPDATE SKIP LOCKED with a LIMIT — and because the exact statement text is the design.

JobExecutionRepository.selectDueForUpdate — step 1 of 2java
@Query(value = """
        SELECT e.id
          FROM job_execution e
         WHERE e.status = 'PENDING'
           AND e.run_at <= :now
         ORDER BY e.run_at
           FOR UPDATE SKIP LOCKED
         LIMIT :batchSize
        """, nativeQuery = true)
List<UUID> selectDueForUpdate(@Param("now") OffsetDateTime now,
                              @Param("batchSize") int batchSize);

Four decisions in nine lines. FOR UPDATE alone is already correct — a second worker blocks, re-evaluates after the first commits, finds the rows no longer PENDING, returns nothing. SKIP LOCKED is not what makes claiming exact; it is what makes it parallel. Ids, not entities, so the locked window stays short. ORDER BY run_at survives locking — PostgreSQL orders before it locks and drops locked rows rather than reordering; without it a large backlog starves its own head. And OffsetDateTime, not Instant: the driver binds the former unambiguously, the latter depends silently on hibernate.jdbc.time_zone.

ExecutionClaimer.claim — the transaction boundary that makes the pair atomicjava
@Transactional(propagation = Propagation.REQUIRES_NEW)
public List<Claimed> claim(String workerId, int batchSize) {
    OffsetDateTime now = OffsetDateTime.now(ZoneOffset.UTC);

    List<UUID> ids = executions.selectDueForUpdate(now, batchSize);
    if (ids.isEmpty()) {
        return List.of();
    }

    int updated = executions.markRunning(ids, workerId, now);
    if (updated != ids.size()) {
        // Cannot happen while we hold the row locks - which is exactly why it is worth
        // asserting. If this ever fires, someone has added a code path that mutates
        // job_execution without taking the lock first.
        log.warn("claim mismatch: locked {} rows but updated {} (workerId={})",
                ids.size(), updated, workerId);
    }

    // Re-read after the bulk UPDATE (which cleared the persistence context) so the snapshots
    // reflect committed-to-be state, with the definition fetch-joined.
    List<JobExecution> claimed = executions.findAllWithJobByIdIn(ids);

    // An "id IN (:ids)" query makes NO promise about row order - the planner is free to return
    // a bitmap heap scan in physical order, or an index scan in (random) UUID order. The claim
    // order that matters was established by ORDER BY run_at in selectDueForUpdate, and the
    // whole fairness property ("oldest eligible work first") depends on the batch being
    // dispatched in that order, so re-impose it here instead of inheriting the planner's whim.
    Map<UUID, JobExecution> byId = new HashMap<>();
    for (JobExecution execution : claimed) {
        byId.put(execution.getId(), execution);
    }
    List<Claimed> result = ids.stream()
            .map(byId::get)
            .filter(Objects::nonNull)
            .map(ExecutionClaimer::snapshot)
            .toList();
    log.debug("worker {} claimed {} execution(s)", workerId, result.size());
    return result;
}

The re-read is not redundant. markRunning is bulk SQL annotated @Modifying(flushAutomatically = true, clearAutomatically = true), so clearing afterwards is what makes the JOIN FETCH see post-UPDATE state rather than cached copies that still say PENDING. Rows are then flattened into a Claimed record before the transaction closes: handing a managed entity to a pool thread with no session earns a LazyInitializationException on the first payload read.

The re-read silently throws away ORDER BY run_at

selectDueForUpdate is carefully ordered oldest-first, and then findAllWithJobByIdIn — a plain WHERE e.id IN :ids with no ORDER BY — hands the rows back in whatever order the plan produced: physical heap order for a bitmap scan, UUID order for an index scan on the primary key. Neither has anything to do with run_at. Iterating that list straight into dispatch would mean the fairness property is enforced when rows are selected and then discarded when they are run, which is the half that a user actually observes: with eight threads and a batch of sixteen, the second half of the batch waits for a free slot, so batch order is execution order. The fix is the three lines above — index the re-read by id, then walk ids. filter(Objects::nonNull) guards the case where a row was deleted between the UPDATE and the re-read; a null reaching snapshot would be an NPE inside the claim transaction, i.e. the whole batch rolled back and re-claimed.

Leader election for exactly one tick

AdvisoryLock is 40 lines of code and 50 of javadoc, and the ratio is correct. Three reasons force the transaction-scoped family: HikariCP hands out an arbitrary connection, so acquiring on one and releasing on another leaks the lock and stops cron materialisation cluster-wide; a session lock needs try/finally discipline through every future refactor; and a SIGKILLed JVM must not wedge the cluster while TCP keepalive notices the dead client. Transaction scope makes the database's own lifecycle the failure detector — no lease, no TTL, no fencing token.

AdvisoryLock.tryLock — the guard is the interesting halfjava
public boolean tryLock(long key) {
    if (!TransactionSynchronizationManager.isActualTransactionActive()) {
        throw new IllegalStateException(
                "pg_try_advisory_xact_lock(" + key + ") was called outside a transaction. "
                        + "A transaction-scoped advisory lock is released at COMMIT, so in "
                        + "autocommit mode it is released by the very statement that takes it "
                        + "and provides no mutual exclusion. Annotate the calling method with "
                        + "@Transactional (and make sure the call is not a self-invocation "
                        + "that bypasses the proxy).");
    }
    Boolean acquired = jdbc.queryForObject(
            "SELECT pg_try_advisory_xact_lock(?)", Boolean.class, key);
    return Boolean.TRUE.equals(acquired);
}
The bug this guard exists to prevent is invisible in testing

In autocommit mode the lock is acquired and released by the same statement, so it returns true every time on every instance. One instance in dev: works perfectly. Three in production: all three are the leader, every tick, forever. The unique constraint on idempotency_key still prevents duplicate runs, so you do not even get failed jobs — just triple the transactions and a constraint violation logged every second.

Hence the second trap. @Transactional is proxy-based, so a call from inside the bean never reaches the proxy: had scheduledTick() simply called tick(), no transaction would start and the guard above would fire every second. CronTicker and OrphanSweeper both route through an ObjectProvider of their own type, which also avoids the circular dependency that direct self-injection creates.

CronTicker — routing back through the container, and the tick itselfjava

        return;

    }
}

    // lock is held by a database transaction rather than by a process's belief about itself.
    if (!advisoryLock.tryLock(props.cron().advisoryLockKey())) {
        log.trace("another instance holds the cron lock this tick; skipping");

Materialisation is resumable and bounded. The cursor starts at MAX(scheduled_for), not at now(), so a restart catches up missed occurrences instead of dropping them — while a job seen for the first time starts at now rather than backfilling from created_at. Catch-up is capped at max-occurrences-per-tick: 16: a one-second cron job down for a day would otherwise write 86,400 rows in one transaction and saturate every worker the instant it commits.

CronTicker.materializeOccurrences — the resumable cursorjava
CronExpression cron = CronExpression.parse(job.getCronExpr());

Instant cursorInstant = executions.findLatestScheduledFor(job.getId()).orElse(now);
ZonedDateTime cursor = cursorInstant.atZone(ZoneOffset.UTC);

int created = 0;
for (int i = 0; i < props.cron().maxOccurrencesPerTick(); i++) {
    ZonedDateTime next = cron.next(cursor);
    if (next == null) {
        // CronExpression returns null when the expression can never match again, e.g.
        // "0 0 0 30 2 *" - 30 February.
        log.warn("cron expression '{}' on job '{}' has no further occurrences",
                job.getCronExpr(), job.getName());
        break;
    }
    Instant nextInstant = next.toInstant();
    if (nextInstant.isAfter(horizonEnd)) {
        break;
    }
    created += materializer.materializeRun(job, nextInstant).size();
    cursor = next;
}
Spring cron has six fields, not five

CronExpression.parse expects second minute hour dom month dow. A five-field Unix expression is rejected by the API at create time rather than silently never firing. The seed job's */10 * * * * * is every ten seconds, not every ten minutes.

The worker loop: backpressure is the whole point

WorkerLoop never claims work it cannot start. A claimed row is RUNNING with a lease already ticking, so from any peer's point of view a row queued behind eight busy threads is indistinguishable from one being actively worked on.

WorkerLoop — the pool, the permits, and why AbortPolicyjava
int threads  = props.worker().threads();      // 8
int capacity = props.worker().capacity();     // threads * 2 = 16
this.slots = new Semaphore(capacity);

// AbortPolicy, not CallerRunsPolicy. CallerRuns would execute the job on the @Scheduled
// thread, blocking every other scheduled task - including the heartbeat that keeps this
// instance's leases alive. Rejection is handled explicitly in dispatch() by returning the
// row to the queue; silently running it here would be far worse.
this.pool = new ThreadPoolExecutor(
        threads, threads,
        0L, TimeUnit.MILLISECONDS,
        new ArrayBlockingQueue<>(Math.max(1, capacity - threads)),
        factory,
        new ThreadPoolExecutor.AbortPolicy());
pollOnce and dispatch — min(batch, free slots), and the rejection pathjava
public int pollOnce() {
    int capacity = slots.availablePermits();
    if (capacity <= 0) {
        log.debug("worker at capacity; skipping poll");
        return 0;
    }

    int batchSize = Math.min(props.worker().claimBatchSize(), capacity);
    List<ExecutionClaimer.Claimed> claimed = claimer.claim(props.nodeId(), batchSize);

    for (ExecutionClaimer.Claimed execution : claimed) {
        dispatch(execution);
    }
    return claimed.size();
}

private void dispatch(ExecutionClaimer.Claimed execution) {
    // This acquire cannot block: only pool threads release permits and only this single
    // @Scheduled thread acquires them, so the permit count measured in pollOnce() can have
    // grown but never shrunk. The blocking form is used anyway so that a future change which
    // adds a second acquirer degrades into waiting rather than into over-claiming.
    slots.acquireUninterruptibly();
    inFlight.add(execution.executionId());
    try {
        pool.execute(() -> runSafely(execution));
    } catch (RejectedExecutionException ex) {
        inFlight.remove(execution.executionId());
        slots.release();
        // We hold a RUNNING row we cannot execute. Put it straight back rather than letting
        // the lease expire, which would cost 30 seconds of latency for nothing.
        executions.releaseToPending(List.of(execution.executionId()), props.nodeId(),
                OffsetDateTime.now(ZoneOffset.UTC));
        log.warn("execution {} rejected by the pool and returned to PENDING",
                execution.executionId());
    }
}
Remove the min() and you get self-inflicted duplicate execution

Claim claimBatchSize unconditionally and dispatch blocks on slots.acquireUninterruptibly(), on the poll thread, holding the rest of the batch in a local List. Those rows are RUNNING in the database and not yet in inFlight, so the heartbeat does not cover them. Thirty seconds later the sweeper reclaims them, a peer runs them, and then this instance gets a permit and runs them too. The interval between a claim's COMMIT and inFlight.add is the only un-heartbeated window in the system; backpressure keeps it at microseconds.

Heartbeat, lease, and orphan reclaim

Liveness is a timestamp, not a membership protocol. Two scopes carry the safety argument: the SQL is scoped to claimed_by = :workerId, so a paused instance cannot stomp on a new owner's lease; the Java is scoped to inFlight, so a finished handler or a dead thread stops being heartbeated at once.

Refreshing "all rows where claimed_by = me" instead would keep leases alive for work nobody is doing, and the sweeper would never fire. The arithmetic between the intervals is the tuning surface:

The sweep loads entities rather than issuing one bulk UPDATE, deliberately: reclaim reuses the same RetryPolicy as any other failure, so the backoff formula lives in exactly one place. Duplicating it in SQL would guarantee the two drift apart, and sweep volumes are tiny by definition — if this list is ever large, N+1 queries are the least of your problems.

OrphanSweeper.sweep — a lease expiry IS a failed attemptjava
@Transactional
public int sweep() {
    Instant now = Instant.now();
    OffsetDateTime cutoff = now.minus(props.worker().leaseTimeout()).atOffset(ZoneOffset.UTC);

    List<UUID> expired = executions.selectExpiredLeasesForUpdate(
            cutoff, props.sweeper().batchSize());
    if (expired.isEmpty()) {
        return 0;
    }

    List<JobExecution> rows = executions.findAllWithJobByIdIn(expired);

    for (JobExecution row : rows) {
        String previousOwner = row.getClaimedBy();
        Instant lastBeat = row.getHeartbeatAt();
        String message = "lease expired: owner '" + previousOwner + "' last heartbeat at "
                + lastBeat + ", lease timeout " + props.worker().leaseTimeout();

        retryPolicy.recordFailure(row, message, now, true);

        log.warn("reclaimed execution {} of job '{}' from '{}' -> {} (attempt {}/{})",
                row.getId(), row.getJob().getName(), previousOwner, row.getStatus(),
                row.getAttempt(), row.getJob().getMaxAttempts());
    }

    executions.saveAll(rows);
    return rows.size();
}
Charging an attempt on reclaim is not bookkeeping pedantry

A handler that reliably wedges its process would otherwise be reclaimed and re-run forever, cycling RUNNING → PENDING → RUNNING and killing an instance each time while every dashboard shows healthy throughput. Charging the attempt makes it reach DEAD_LETTER and become visible. Graceful shutdown is the deliberate exception: releaseToPending charges nothing, or a rolling deploy across three instances would dead-letter a three-attempt job with no real failure at all.

Retry: full jitter and the attempt ledger

The formula is cap = min(max-delay, base-delay × 2^attempt), then delay = uniform(0, cap). Plain exponential backoff does not spread load, it delays a thundering herd: 500 jobs that failed in the same second all retry at exactly base × 2 seconds later, hitting the recovering dependency with the same spike that knocked it over, in lockstep. Of the AWS taxonomy — no jitter, equal jitter (cap/2 + random(0, cap/2)), full jitter (random(0, cap)) — full jitter gives the widest spread and the lowest total work under contention. Its cost is that a single retry may return almost immediately; across a herd that is a feature, since early probes are how recovery gets discovered.

RetryPolicy.capFor — repeated doubling, not a shiftjava
public Duration capFor(int attempt) {
    long base = Math.max(1L, props.retry().baseDelay().toMillis());
    long max  = Math.max(base, props.retry().maxDelay().toMillis());

    long cap = base;
    for (int i = 0; i < attempt && cap < max; i++) {
        cap = cap * 2;
    }
    if (cap > max || cap <= 0) {
        cap = max;
    }
    return Duration.ofMillis(cap);
}

public Duration nextDelay(int attempt) {
    long cap = capFor(attempt).toMillis();
    // nextLong(bound) is exclusive, so +1 makes the cap itself reachable.
    return Duration.ofMillis(ThreadLocalRandom.current().nextLong(cap + 1));
}
base << attempt is wrong twice over

Java masks the shift distance to the low six bits, so 1L << 64 is 1, not 0: a job on attempt 64 gets a one millisecond backoff — the tightest possible retry loop, on precisely the job that has failed most. The loop above exits once the value reaches the cap, and RetryBackoffTest asserts capFor(64) and capFor(1_000) for exactly that reason.

The off-by-one grants every job a silent extra run, or dead-letters a three-attempt job after two.

RetryPolicy.recordFailure — the three outcomesjava
public void recordFailure(JobExecution execution, String error, Instant now, boolean retryable) {
    int attempt = execution.getAttempt() + 1;
    execution.setAttempt(attempt);
    execution.setError(truncate(error));
    // Must happen before the status is set to anything non-RUNNING, and must happen at all:
    // the job_execution_running_is_owned CHECK constraint only permits RUNNING rows to carry
    // an owner, so leaving claimed_by set on a PENDING row is not merely untidy, the sweeper
    // and the heartbeat would both misattribute it.
    execution.releaseClaim();

    int maxAttempts = execution.getJob().getMaxAttempts();

    if (!retryable) {
        execution.setStatus(ExecutionStatus.FAILED);
        execution.setFinishedAt(now);
        return;
    }
    if (attempt >= maxAttempts) {
        execution.setStatus(ExecutionStatus.DEAD_LETTER);
        execution.setFinishedAt(now);
        return;
    }
    execution.setStatus(ExecutionStatus.PENDING);
    execution.setRunAt(now.plus(nextDelay(attempt)));
    // started_at is deliberately LEFT ALONE. It records when this occurrence first began, not
    // when the current attempt began, which is what makes ExecutionResponse.lagMillis ("how
    // late did this occurrence start?") comparable across a retried and a first-time execution.
    // Clearing it here would also make the COALESCE(started_at, :now) in the claim UPDATE dead
    // code: the column would be NULL at every claim, so each retry would overwrite the true
    // start time and end-to-end latency including retries would be unrecoverable.
    // "Is it in progress?" is answered by status, which is PENDING from here.
}
Clearing started_at on retry quietly deletes your lag metric

It reads like tidying up — the row is not running any more, so null the column that says when it started. It is not tidying up, it is a data loss. markRunning writes started_at = COALESCE(started_at, :now) precisely so a retried row keeps its first start; null the column on the way out and the COALESCE can never see a non-null value, so it becomes dead code and every claim stamps a new timestamp. ExecutionResponse.lagMillis is between(scheduled_for, started_at), so it would stop meaning "how late did the 09:00 run start?" and start meaning "how late did attempt 4 start?" — a number that shrinks as a job retries harder, on the one dashboard you would use to notice. Nothing else needs the column: "is it in progress?" is status = 'RUNNING', and it is enforced by the job_execution_running_is_owned CHECK. started_at is therefore written exactly once per occurrence, at the first claim.

Note what retry is not: a sleep in the worker. Sleeping occupies a thread and keeps the lease alive, pinning capacity for the whole backoff. Pushing run_at forward frees the slot instantly and lets any instance take the work when it comes due. FAILED and DEAD_LETTER stay distinct so you can tell "we gave up after trying" from "trying was never going to help".

DAG eligibility: universal quantification in SQL

A BLOCKED execution of job J for occurrence S becomes PENDING when every parent of J has a SUCCEEDED execution for that same S. SQL has EXISTS but no FOR ALL, so the rule is written as its double negation: there is no parent for which no successful execution exists.

DagResolver.promoteAllEligible — one set-based statementjava
@Transactional
public int promoteAllEligible() {
    return jdbc.update("""
            UPDATE job_execution e
               SET status = 'PENDING',
                   run_at = now()
             WHERE e.status = 'BLOCKED'
               AND NOT EXISTS (
                   SELECT 1
                     FROM job_dependency d
                    WHERE d.job_id = e.job_id
                      AND NOT EXISTS (
                          SELECT 1
                            FROM job_execution p
                           WHERE p.job_id = d.depends_on_job_id
                             AND p.scheduled_for = e.scheduled_for
                             AND p.status = 'SUCCEEDED'
                      )
               )
            """);
}

The obvious Java implementation — load blocked rows, loop, query each one's parents — is O(blocked × parents) round trips and races with itself across instances. Set-based, concurrent resolvers just update the same rows to the same value. run_at = now() rather than the materialised value, because a step's occurrence time is already past by the time its parents finish; scheduled_for is untouched, so the step still reports its run.

Two entry points share that predicate. promoteChildrenOf is the fast path, called from completeSuccess and scoped to one parent's direct children in one run — the difference between millisecond DAG latency and a whole scheduler.dag.interval. It still applies the full "all parents" test. Critically it runs after the completion transaction commits: inside it, the SUCCEEDED row it is looking for would not yet be visible. The periodic sweep is the safety net for a crash in that millisecond.

Cancellation propagates one level per pass, on purpose

cancelUnreachable inspects only direct parents, so the 2-second sweep walks the graph one layer per pass to a fixed point — two passes for a diamond, which the tests assert. A transitive closure in one statement needs another recursive CTE for no gain. Without cancellation, a dead-lettered root leaves its whole downstream graph BLOCKED forever: invisible in failed dashboards and running ones alike.

Idempotency: what the ledger closes, and what it does not

Every execution carries a deterministic key, idempotencyKey = jobId + "@" + ISO_INSTANT(scheduledFor), truncated to microseconds because that is timestamptz's resolution: build it from a nanosecond-precision Instant while storing the truncated value and a database round trip regenerates a different key, so the collision you were counting on never happens. A random UUID here compiles, passes every single-instance test, and duplicates every cron job the moment you scale to two replicas.

ProcessedExecutionRepository.markProcessed — the whole enforcement mechanismjava
public boolean markProcessed(String idempotencyKey) {
    int inserted = jdbc.update("""
            INSERT INTO processed_execution (idempotency_key, processed_at)
            VALUES (?, now())
            ON CONFLICT (idempotency_key) DO NOTHING
            """, idempotencyKey);
    return inserted == 1;
}

A plain JdbcTemplate repository, not an entity, precisely so Hibernate cannot turn ON CONFLICT DO NOTHING into a SELECT-then-INSERT — the very race being eliminated. Two workers on one key cannot both insert; the loser gets 0 rows and knows it is the duplicate.

    } else {

    }
    executions.save(row);
});
The asymmetry is the point — and so is the window it leaves open

A SUCCEEDED execution with no ledger row is harmless — a duplicate simply re-runs the handler. A ledger row with no SUCCEEDED execution is poisonous: the legitimate retry of a genuinely-unfinished job is suppressed as a duplicate, silently and forever. Hence one transaction, not two adjacent writes.

What it cannot fix: the marker is written after the side effect, so it closes the "completion write was lost" window, not the "side effect happened twice" window. Genuinely-once needs both in one transaction, which only works if the side effect lives in this database. Hence JobHandler's contract opening with "be idempotent", and hence never pruning the ledger faster than lease-timeout + max retry backoff.

What the tests prove

All four classes run against a real PostgreSQL 16 via a Testcontainers singleton, not H2: every mechanism here is a PostgreSQL feature, and a suite that passes on an emulation while production behaviour is wrong is worse than no suite. All five @Scheduled loops are disabled and the tests call claim(), sweep(), tick() and pollOnce() directly, so each assertion is about a mechanism rather than about whether a timer fired.

// 1. No execution was handed to two workers. This is the SKIP LOCKED guarantee.
assertThat(doubleClaims.get())
        .as("an execution was claimed by more than one worker")
        .isZero();

// 2. Conservation: exactly the rows we created, no more and no fewer.
assertThat(owners.keySet())
        .as("the union of all claims must be exactly the queue")
        .containsExactlyInAnyOrderElementsOf(expected);

// 5. The work actually spread across workers. If SKIP LOCKED were replaced by plain
//    FOR UPDATE the test above would still pass - it would just serialise - so assert
//    that more than one worker got a share.
Set<String> distinctWorkers = new HashSet<>(owners.values());
assertThat(distinctWorkers)
        .as("claiming should be spread over several workers, not serialised onto one")
        .hasSizeGreaterThan(1);

Assertion 5 is the subtle one, and it is why deleting SKIP LOCKED and re-running is such an instructive exercise: correctness survives, throughput does not. DagEligibilityTest makes the equivalent point for the fan-in rule:

Java 17, deliberately

spring.threads.virtual.enabled: false is explicit and the pool is a plain ThreadPoolExecutor of eight platform threads. On Java 21 you would size concurrency by connections rather than threads, but the backpressure argument is unchanged: the bound is still "rows whose lease I can keep alive", and a virtual thread renews a heartbeat no faster than a platform one.

What to take away

  1. The claim is exact because one transaction spans the locking SELECT and the UPDATE. Row locks hold the line until COMMIT; after COMMIT the status column does. Split them and two workers both see the row as PENDING.
  2. FOR UPDATE buys correctness, SKIP LOCKED buys parallelism, and the partial index on (status, run_at) WHERE status = 'PENDING' buys both once history outgrows the backlog. Without it every worker scans the whole backlog before skipping anything.
  3. Transaction-scoped advisory locks need no lease, TTL or unlock path — the transaction lifecycle is the failure detector. The session-scoped variant leaks through a connection pool, and either one outside a transaction always returns true, which is why AdvisoryLock throws rather than lying.
  4. Never claim a row you cannot immediately start. The heartbeat covers exactly inFlight, so the gap between a claim's COMMIT and inFlight.add is the one un-heartbeated window. min(claimBatchSize, availablePermits) keeps it at microseconds; removing it produces real duplicate execution, not just latency.
  5. Lease and heartbeat are one number with two names: 30 s over 5 s is six missed beats before anyone acts, worst-case recovery lease + sweeper.interval = 40 s. A lease shorter than the heartbeat reclaims live work, so the app refuses to start on it.
  6. Full jitter is uniform(0, min(max-delay, base × 2^attempt)), by repeated doubling because base << attempt wraps at 64. Retry means "push run_at forward and release the slot", never "sleep in the worker" — sleeping keeps the lease alive and pins capacity for the whole backoff.
  7. The ledger closes the lost-completion window, not the duplicate-side-effect window. Status and ledger row must share a transaction; the dangerous direction is a ledger row with no SUCCEEDED execution, which suppresses a legitimate retry forever.
