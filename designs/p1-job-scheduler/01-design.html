Design & data model

The requirements, the arithmetic they imply, the four tables and the indexes that make them fast — and then the one problem the whole project exists to solve: how N identical instances take exclusive ownership of the same row without a lock service, a leader, or a membership protocol.

Java 17 Spring Boot 3.4.1 PostgreSQL 16 Redis 8 design
The one sentence this design is built around

Ownership of a unit of work and the state of that unit of work must live in the same system, changed by the same commit. Every alternative — a Redis lock, a ZooKeeper ephemeral node, a leader that assigns shards — adds a second store that can disagree with the first about who owns a row. Here the lock manager is PostgreSQL and the state is a PostgreSQL row, so there is nothing to reconcile: the claim is one transaction, and after it commits the status column is the ownership record.

The estimation

Size it before designing it. Take 5,000 job definitions producing 2 million executions per day — a mean of 23/s, with the usual pathology that ~20 % of them are 0 0 0 * * * and land in the same microsecond. The defaults in application.yml then give you every number you need:

the knobs the arithmetic runs on — application.ymlyaml
  worker:
    threads: 8               # pool size; also the cap on rows RUNNING on this instance
    claim-batch-size: 16     # rows requested per poll
    poll-interval: 500ms
    lease-timeout: 30s       # a RUNNING row with an older heartbeat_at is orphaned
    heartbeat-interval: 5s   # 30s / 5s = six missed beats before reclaim
    shutdown-grace: 20s
  cron:
    tick-interval: 1s
    horizon: 60s                  # materialise occurrences this far ahead
    max-occurrences-per-tick: 16  # bound on catch-up after downtime
  sweeper:
    interval: 10s
    batch-size: 100
  retry:
    base-delay: 1s
    max-delay: 5m
  • Throughput per instance. 8 threads at a 200 ms median handler is 40 executions/s; in-flight capacity is threads × 2 = 16 rows. Four instances sustain ~160/s — seven times the mean — and drain a 1,000-row midnight burst in about seven seconds.
  • Coordination cost. Claim polls are 2/s × instances: 8/s at four instances, each one index scan plus one UPDATE. The cron tick is 1/s of real work cluster-wide, and the three losers each execute a single SELECT pg_try_advisory_xact_lock(…) and commit. The sweeper adds 0.4 scans/s. Coordination is free here; the work is what costs.
  • Storage. A job_execution tuple is roughly 250 bytes (four UUIDs, six timestamptz, a ~60-character key) before its five indexes: ~500 MB/day of heap, nearer 1 GB/day with indexes. Retention is not optional at this scale, and the partial claim index is what stops the queue degrading while you postpone it.

The data model

Four tables. job is the definition, job_execution is the queue, job_dependency is the edge set, processed_execution is the idempotency ledger. Two decisions apply to all of them and are worth stating before the DDL: every timestamp is timestamptz, and every enumeration is text plus a CHECK.

the definition tablesql
CREATE TABLE job (
    id            uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    name          text        NOT NULL,
    type          text        NOT NULL,
    cron_expr     text,
    -- payload is opaque to the scheduler except for the reserved key "handler",
    -- which selects the JobHandler bean. Everything else is passed through to
    -- the handler untouched.
    payload       jsonb       NOT NULL DEFAULT '{}'::jsonb,
    max_attempts  integer     NOT NULL DEFAULT 3,
    timeout_ms    bigint      NOT NULL DEFAULT 30000,
    enabled       boolean     NOT NULL DEFAULT true,
    created_at    timestamptz NOT NULL DEFAULT now(),
    updated_at    timestamptz NOT NULL DEFAULT now(),

    CONSTRAINT job_name_unique          UNIQUE (name),
    CONSTRAINT job_type_check           CHECK (type IN ('ONE_OFF', 'CRON', 'DAG_STEP')),
    -- A CRON job without an expression can never fire; reject it at the storage
    -- layer so a bad API call cannot create an invisible no-op job.
    CONSTRAINT job_cron_expr_required   CHECK (type <> 'CRON' OR cron_expr IS NOT NULL),
    CONSTRAINT job_max_attempts_check   CHECK (max_attempts >= 1),
    CONSTRAINT job_timeout_check        CHECK (timeout_ms > 0)
);
Why text + CHECK and not a PostgreSQL ENUM

Adding a value to a real enum takes a lock and, on older versions, could not be done inside a transaction; a CHECK is trivially altered in a later migration. The price is that the values must stay byte-identical to the Java enum ExecutionStatus — renaming a constant there compiles fine and then fails at runtime with a constraint violation, or worse, silently stops matching rows.

the queue — one row per (job, logical occurrence)sql
CREATE TABLE job_execution (
    id              uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    job_id          uuid        NOT NULL REFERENCES job (id) ON DELETE CASCADE,

    -- scheduled_for is the LOGICAL occurrence time (e.g. the cron instant).
    -- It never moves. It is also the correlation key that groups every step of
    -- one DAG run together - see job_dependency below.
    scheduled_for   timestamptz NOT NULL,

    -- run_at is the PHYSICAL earliest-eligible time. Retry backoff pushes this
    -- into the future; scheduled_for stays put. Keeping the two separate is what
    -- lets you answer "was the 09:00 run late?" after three retries.
    run_at          timestamptz NOT NULL,

    status          text        NOT NULL,
    attempt         integer     NOT NULL DEFAULT 0,

    -- The unit-of-work identity. Derived deterministically from
    -- (job_id, scheduled_for), so a leader flap that materialises the same cron
    -- occurrence twice collides here instead of double-scheduling.
    idempotency_key text        NOT NULL,

    claimed_by      text,
    claimed_at      timestamptz,
    heartbeat_at    timestamptz,
    started_at      timestamptz,
    finished_at     timestamptz,
    error           text,
    created_at      timestamptz NOT NULL DEFAULT now(),

    CONSTRAINT job_execution_idempotency_key_unique UNIQUE (idempotency_key),
    CONSTRAINT job_execution_status_check CHECK (
        status IN ('PENDING', 'BLOCKED', 'RUNNING', 'SUCCEEDED', 'FAILED', 'DEAD_LETTER', 'CANCELLED')
    ),
    CONSTRAINT job_execution_attempt_check CHECK (attempt >= 0),
    -- Invariant: a RUNNING row always names its owner and carries a heartbeat.
    -- Without this a bug that forgets claimed_by would make the orphan sweeper
    -- silently unable to attribute (or reclaim) the row.
    CONSTRAINT job_execution_running_is_owned CHECK (
        status <> 'RUNNING' OR (claimed_by IS NOT NULL AND heartbeat_at IS NOT NULL)
    )
);

A naive timestamp column silently double-fires or skips jobs

Never store scheduler time as timestamp without time zone. The claim query compares against now(); on a naive column a DST shift moves that comparison by an hour and you get an hour of duplicate firings or of skipped ones, with nothing in the logs to explain it. Everything here is timestamptz, Hibernate is pinned with hibernate.jdbc.time_zone: UTC so a worker in Europe/Berlin cannot disagree with one in UTC, and the native queries bind OffsetDateTime rather than Instant because the driver has a direct binding for it.

The claim index, and the reasoning

The hot query runs a few times per second per instance forever, against a table that grows by two million rows a day. Everything about the index follows from those two facts.

the index the whole queue rests onsql
-- Why a PARTIAL index:
--   PENDING rows are a small, self-cleaning minority. SUCCEEDED rows accumulate
--   forever. A full index on (status, run_at) would grow without bound and every
--   claim would page through dead heap entries. The partial index only ever
--   holds rows that are actually claimable, so it stays roughly the size of the
--   backlog no matter how much history the table carries.
--
-- Why (status, run_at) and not just (run_at):
--   Under the WHERE status = 'PENDING' predicate the leading column is constant,
--   so it costs one byte per entry and contributes no selectivity. It is kept
--   because it makes the index self-documenting and lets the planner match the
--   query's own predicate order without relying on predicate-implication proofs.
--   Crucially, entries are still ordered by run_at within the constant status,
--   so ORDER BY run_at is served directly from the index - no sort node, which
--   is what makes LIMIT :batch cheap even with a million-row backlog.
--
-- Why this matters for SKIP LOCKED:
--   SKIP LOCKED skips rows another transaction has locked, but it only knows to
--   skip them AFTER visiting them. With an index scan the visit order is run_at
--   order, so N workers walk the same ordered list and each takes the first
--   :batch rows nobody else holds. Without the index you get a seq scan + sort,
--   every worker materialises the whole backlog, and throughput collapses.
CREATE INDEX idx_job_execution_claim
    ON job_execution (status, run_at)
    WHERE status = 'PENDING';

The sweeper gets the same treatment for the same reason — RUNNING is a tiny, transient set, so its index should cost in proportion to in-flight work rather than to history:

the other four indexes, and what each one is forsql
CREATE INDEX idx_job_execution_heartbeat
    ON job_execution (heartbeat_at)
    WHERE status = 'RUNNING';

-- FK index. PostgreSQL does NOT create one automatically for a foreign key, and
-- without it `DELETE FROM job` has to seq-scan job_execution to enforce the
-- ON DELETE CASCADE.
CREATE INDEX idx_job_execution_job_id ON job_execution (job_id);

-- Backs the DAG eligibility check, which asks "is there a SUCCEEDED execution of
-- parent P for this exact scheduled_for?" for every parent of every BLOCKED row.
CREATE INDEX idx_job_execution_dag_lookup
    ON job_execution (job_id, scheduled_for, status);

-- Backs GET /api/jobs/{id}/executions (most recent first) and the cron ticker's
-- "what is the latest occurrence I already materialised for this job?" probe.
CREATE INDEX idx_job_execution_job_scheduled_desc
    ON job_execution (job_id, scheduled_for DESC);

CREATE INDEX idx_job_execution_blocked
    ON job_execution (scheduled_for)
    WHERE status = 'BLOCKED';
BLOCKED is a separate status, not "PENDING with a far-future run_at"

The tempting simplification is to park unsatisfied DAG steps as PENDING with run_at = 'infinity' and save a status value. Do that and every blocked step becomes an entry in the claim index: a 500-step fan-out costs the hot path 500 unclaimable index entries on every poll, forever. A distinct status keeps blocked work out of idx_job_execution_claim entirely, so wide DAGs cost the queue nothing.

The core problem: claiming work exactly once across N instances

N identical processes see the same table of due rows. Each must end up executing a disjoint subset, with no row executed by two of them, and no row left behind if a process dies. There are four credible ways to do it.

CandidateHow it worksWhy it was rejected
Single scheduler (active/passive)One process claims and executes; the others idle behind a leader lock or a Kubernetes replicas: 1.Trivially correct and trivially capacity-bound: throughput is one JVM, and a failover gap is a scheduling gap. The standby costs money to do nothing. Worse, "exactly once" degrades to "exactly once while that process is alive" — you still need everything below to recover its work.
Per-job distributed lock (Redis SET NX PX, Redlock, ZooKeeper ephemeral node)Read due rows, then take a per-row lock in the lock service before executing.Two stores that can disagree. The lock has a TTL; a GC pause longer than the TTL means the lock expires while the holder is still running, and there is no fencing token on the side effect to stop it. It is also chatty: N instances × M due rows lock round trips per poll. And a Redis outage now stops scheduling, which is exactly the coupling the design refuses.
Leader-partitioned assignment (leader hashes jobs into shards, Kafka-style rebalance)A leader assigns partitions to members; each member claims only its own shard, so claims never collide by construction.You now own a membership protocol, a rebalance protocol and a generation/epoch number. During a rebalance a partition is briefly owned by two members, so you need fencing anyway. Load skews with hash distribution, and a single hot job cannot be split. Enormous machinery for a problem the database already solves.
FOR UPDATE SKIP LOCKED  ← chosenEach worker runs one transaction: lock up to batch due rows, skipping anything a peer holds, flip them to RUNNING, commit.The lock manager and the state are the same system, so they cannot disagree. No membership, no TTL, no fencing token, no second dependency. The costs are real and accepted: it is PostgreSQL-bound, it needs the partial index to stay fast, and PostgreSQL is now a single point of failure.

Three details in those twenty lines carry the design. Ids, not entities: the projection keeps the locked window short and stops Hibernate hydrating objects while peers contend on the index. ORDER BY run_at survives the lock — PostgreSQL orders before locking and drops locked rows rather than reordering them, so the effective policy is "oldest eligible work first, minus whatever peers already took"; drop it and a large backlog starves its own head. clearAutomatically because bulk SQL bypasses the persistence context: without it the re-read serves cached copies that still say PENDING.

ExecutionClaimer.claim — the transaction boundary is the whole mechanismjava
@Transactional(propagation = Propagation.REQUIRES_NEW)
public List<Claimed> claim(String workerId, int batchSize) {
    OffsetDateTime now = OffsetDateTime.now(ZoneOffset.UTC);

    List<UUID> ids = executions.selectDueForUpdate(now, batchSize);
    if (ids.isEmpty()) {
        return List.of();
    }

    int updated = executions.markRunning(ids, workerId, now);
    if (updated != ids.size()) {
        // Cannot happen while we hold the row locks - which is exactly why it is worth
        // asserting. If this ever fires, someone has added a code path that mutates
        // job_execution without taking the lock first.
        log.warn("claim mismatch: locked {} rows but updated {} (workerId={})",
                ids.size(), updated, workerId);
    }

    // Re-read after the bulk UPDATE (which cleared the persistence context) so the snapshots
    // reflect committed-to-be state, with the definition fetch-joined.
    List<JobExecution> claimed = executions.findAllWithJobByIdIn(ids);

    // An "id IN (:ids)" query makes NO promise about row order - the planner is free to return
    // a bitmap heap scan in physical order, or an index scan in (random) UUID order. The claim
    // order that matters was established by ORDER BY run_at in selectDueForUpdate, and the
    // whole fairness property ("oldest eligible work first") depends on the batch being
    // dispatched in that order, so re-impose it here instead of inheriting the planner's whim.
    Map<UUID, JobExecution> byId = new HashMap<>();
    for (JobExecution execution : claimed) {
        byId.put(execution.getId(), execution);
    }
    List<Claimed> result = ids.stream()
            .map(byId::get)
            .filter(Objects::nonNull)
            .map(ExecutionClaimer::snapshot)
            .toList();
    log.debug("worker {} claimed {} execution(s)", workerId, result.size());
    return result;
}

The re-read is what forces the last five lines. ORDER BY run_at orders the ids, but findAllWithJobByIdIn is a separate id IN (:ids) query with no ORDER BY of its own, and SQL guarantees nothing about the order of an unordered result. So the batch is re-sorted into ids order before it is dispatched. Skip that step and half the fairness argument above evaporates at the last moment: the SELECT still picks the oldest eligible rows, but pollOnce hands them to the pool in whatever order the planner happened to emit — which, with a bounded pool, is the order they actually run in.

REQUIRES_NEW is deliberate: a claim must never be enlisted in a longer-lived caller transaction. The locks have to be released promptly, and a claim that "succeeds" and is then rolled back by an unrelated failure leaves rows RUNNING with nobody running them — recoverable only via the 30-second lease. See Spring transactions and PostgreSQL concurrency patterns.

Never claim more rows than you have free slots

A claimed row is RUNNING in the database with a lease already ticking, whether or not a thread is working on it. Claim greedily and rows time out while queued locally, the sweeper hands them to a peer, and the same work runs twice — a duplicate you inflicted on yourself. Hence pollOnce asks for Math.min(claimBatchSize, slots.availablePermits()). The pool also uses AbortPolicy, not CallerRunsPolicy: caller-runs would execute the job on the @Scheduled thread and block every other scheduled task — including the heartbeat keeping this instance's leases alive.

The claim is exact; delivery is not

Do not overstate what SKIP LOCKED buys. It guarantees that claiming never hands one row to two instances. It says nothing about afterwards: a frozen-then-thawed JVM can resume and finish a job whose row was already reclaimed and re-run elsewhere. That is unavoidable without fencing tokens on every downstream side effect, so the system accepts at-least-once and makes duplicates cheap (see idempotency). The ledger closes the "completion write was lost" window, not the "side effect happened twice" window. Handlers must still be idempotent.

Cron materialisation uses a different lock, on purpose

Claiming is contention over existing rows, so row locks work. Materialisation creates rows that do not exist yet, and you cannot lock a row that is not there. The unique constraint on idempotency_key already makes duplicate materialisation harmless, so the advisory lock is purely a cost optimisation: it makes the tick O(1) per cluster rather than O(instances), and stops every loser logging a constraint violation once a second.

pg_try_advisory_lock instead of pg_try_advisory_xact_lock wedges the cluster

A session lock is held until you unlock it or the backend session ends. Behind HikariCP you acquire on one pooled connection and release on another, the lock leaks, and cron materialisation stops cluster-wide until that connection is retired — with no error anywhere. The transaction-scoped form is released by COMMIT or ROLLBACK, so "the tick failed halfway" and "the lock was released" cannot disagree, and a SIGKILLed JVM's lock evaporates with its backend rather than waiting on TCP keepalive. AdvisoryLock.tryLock therefore throws outside a transaction: in autocommit the lock is taken and released by the same statement and always returns true — invisible in testing (one instance always wins), catastrophic in production (every instance always wins).

Spring self-invocation silently disables the transaction

@Transactional is proxy-based, and a proxy only intercepts calls arriving from outside the bean. Had scheduledTick() called this.tick() directly there would be no transaction and the advisory lock would be meaningless. The project routes the call back through the container as self.getObject().tick(), where the ObjectProvider<CronTicker> indirection avoids the circular constructor dependency a direct self-injection would create. OrphanSweeper and DagResolver do the same.

Cron semantics: zones, DST, catch-up and the midnight herd

Everything is UTC, and that is a choice with consequences

The ticker advances its cursor with cursorInstant.atZone(ZoneOffset.UTC), so 0 0 2 * * * means 02:00 UTC on every one of the year's 365 days. There is no DST, because UTC has no DST. That is the right default for a scheduler and the wrong one for a business calendar, and the difference is worth being explicit about.

Adding a per-job timezone imports two bugs you currently do not have

Evaluate a cron expression in a DST zone and the daily 02:30 job hits both hazards. On the spring-forward day 02:30 local does not exist: CronExpression.next steps over it and the job silently does not run. On the fall-back day it happens twice, an hour apart — two distinct instants, so two scheduled_for values, two idempotency keys, and the job genuinely runs twice. The unique constraint cannot save you: those are not duplicates, they are two different logical instants sharing a wall-clock label. Add a timezone column if you must, then decide per job, in writing, which of skip-or-double you prefer.

Catch-up after downtime

the cursor is what makes the ticker resumablejava
CronExpression cron = CronExpression.parse(job.getCronExpr());

Instant cursorInstant = executions.findLatestScheduledFor(job.getId()).orElse(now);
ZonedDateTime cursor = cursorInstant.atZone(ZoneOffset.UTC);

int created = 0;
for (int i = 0; i < props.cron().maxOccurrencesPerTick(); i++) {
    ZonedDateTime next = cron.next(cursor);
    if (next == null) {
        // CronExpression returns null when the expression can never match again, e.g.
        // "0 0 0 30 2 *" - 30 February.
        log.warn("cron expression '{}' on job '{}' has no further occurrences",
                job.getCronExpr(), job.getName());
        break;
    }
    Instant nextInstant = next.toInstant();
    if (nextInstant.isAfter(horizonEnd)) {
        break;
    }
    created += materializer.materializeRun(job, nextInstant).size();
    cursor = next;
}

Three policies are encoded there. The cursor starts at the newest occurrence already in the database, so a restart — or ten minutes of cluster downtime — resumes where it stopped instead of silently dropping the gap. A job seen for the first time starts from now: created at noon with 0 0 * * * * it schedules 13:00, not a replay of every hour since midnight. And catch-up is bounded, because a one-second job down for a day would otherwise create 86,400 rows in one transaction — a long lock hold, a bloated WAL record, and a burst that saturates every worker the instant it commits.

Bounded catch-up means a long outage takes hours to drain, and every recovered row is due now

Do the arithmetic before you rely on it. A once-per-second job misses 86,400 occurrences in a day of downtime; the ticker fires once per second and creates at most 16, so it closes the gap at 15/second — 86,400 / 15 ≈ 1.6 hours before the schedule is current again, with every recovered row's run_at in the past and therefore immediately claimable. For most jobs the honest policy is not "replay everything" but "run the missed occurrence once, or skip it", and the place to implement it is the cursor, clamped to max(latestScheduledFor, now - graceWindow).

The midnight thundering herd

The project does not jitter cron start times: materializeRun writes the same instant into both columns. That is right for its scale, and it stays a one-line change because the schema was shaped for it. Note what the jittered value must not touch:

/** Microsecond truncation, matching timestamptz resolution. */
public static Instant normalize(Instant instant) {
    return instant.truncatedTo(ChronoUnit.MICROS);
}
Adding start jitter — not in the project, but this is the shape

Only the run_at argument to insertIfAbsent changes. Derive the offset from the job id rather than from a random draw, so two instances materialising the same occurrence compute the same run_at and the row is identical whichever of them wins the insert.

// run_at only. scheduled_for and idempotencyKey(jobId, when) stay untouched.
long windowMs = 120_000L;                                   // spread over two minutes
long offset   = Math.floorMod(jobId.hashCode(), windowMs);  // deterministic per job
Instant runAt = when.plusMillis(offset);

The trade is visible and worth naming: p50 start latency for a midnight job goes from ~0 to ~60 s, and any job that genuinely must run at exactly 00:00:00 has to be excluded. Jitter is a load-shaping tool, not a default.

The execution state machine

RetryPolicy.recordFailure — every transition out of RUNNING except successjava
public void recordFailure(JobExecution execution, String error, Instant now, boolean retryable) {
    int attempt = execution.getAttempt() + 1;
    execution.setAttempt(attempt);
    execution.setError(truncate(error));
    // Must happen before the status is set to anything non-RUNNING, and must happen at all:
    // the job_execution_running_is_owned CHECK constraint only permits RUNNING rows to carry
    // an owner, so leaving claimed_by set on a PENDING row is not merely untidy, the sweeper
    // and the heartbeat would both misattribute it.
    execution.releaseClaim();

    int maxAttempts = execution.getJob().getMaxAttempts();

    if (!retryable) {
        execution.setStatus(ExecutionStatus.FAILED);
        execution.setFinishedAt(now);
        return;
    }
    if (attempt >= maxAttempts) {
        execution.setStatus(ExecutionStatus.DEAD_LETTER);
        execution.setFinishedAt(now);
        return;
    }
    execution.setStatus(ExecutionStatus.PENDING);
    execution.setRunAt(now.plus(nextDelay(attempt)));
    // started_at is deliberately LEFT ALONE. It records when this occurrence first began, not
    // when the current attempt began, which is what makes ExecutionResponse.lagMillis ("how
    // late did this occurrence start?") comparable across a retried and a first-time execution.
    // Clearing it here would also make the COALESCE(started_at, :now) in the claim UPDATE dead
    // code: the column would be NULL at every claim, so each retry would overwrite the true
    // start time and end-to-end latency including retries would be unrecoverable.
    // "Is it in progress?" is answered by status, which is PENDING from here.
}

The last line of that method is the one to read twice: it is the line that is not there. started_at is never cleared on a retry, so it keeps the instant the occurrence first started running — which is exactly what COALESCE(started_at, :now) in markRunning assumes. Clear it here and the COALESCE becomes dead code, because the column is NULL at every claim; each retry then stamps a fresh started_at and lagMillis silently changes meaning from "how late did the 09:00 run start?" to "how late did its most recent attempt start?" — a metric that falls as a job gets sicker. Nothing needs started_at to mean "in progress": that question is answered by status, which is PENDING from here.

Retrying is "put the row back in the queue with a future run_at", never "sleep in the worker". Sleeping would occupy a thread and, far worse, keep the lease alive, so a five-minute backoff would pin capacity for five minutes doing nothing. Pushing run_at forward frees the slot instantly and lets any instance pick the work up when it comes due.

the backoff cap, and why it is a loop and not a shiftjava
public Duration capFor(int attempt) {
    long base = Math.max(1L, props.retry().baseDelay().toMillis());
    long max = Math.max(base, props.retry().maxDelay().toMillis());

    long cap = base;
    for (int i = 0; i < attempt && cap < max; i++) {
        cap = cap * 2;
    }
    if (cap > max || cap <= 0) {
        cap = max;
    }
    return Duration.ofMillis(cap);
}

public Duration nextDelay(int attempt) {
    long cap = capFor(attempt).toMillis();
    // nextLong(bound) is exclusive, so +1 makes the cap itself reachable.
    return Duration.ofMillis(ThreadLocalRandom.current().nextLong(cap + 1));
}
base << attempt is wrong twice over

Java masks the shift distance to the low six bits, so 1L << 64 is 1, not 0 — a job on attempt 64 suddenly gets a one-millisecond backoff and hammers the failing dependency as fast as the queue can serve it. The doubling loop above cannot overflow because it exits at the cap. The clamp matters too: without it, attempt 20 at a 1 s base schedules a retry twelve days out, which is indistinguishable from losing the job.

Full jitter, not "exponential backoff"

Plain exponential backoff does not spread load, it delays a thundering herd in lockstep: 500 jobs fail in the same second, all retry at exactly base × 2, and the dependency gets the same simultaneous spike that knocked it over, forever. Of the three AWS variants — delay = cap, cap/2 + random(0, cap/2), random(0, cap) — this is full jitter: widest spread, lowest total work under contention. The orphan sweeper reuses the same policy, so a dead instance's 200 reclaimed rows do not all return to PENDING at the same instant.

DAG eligibility, in one statement

universal quantification, which SQL has no operator forsql
UPDATE job_execution e
   SET status = 'PENDING',
       run_at = now()
 WHERE e.status = 'BLOCKED'
   AND NOT EXISTS (                       -- no parent of mine is unsatisfied
       SELECT 1
         FROM job_dependency d
        WHERE d.job_id = e.job_id
          AND NOT EXISTS (                -- ... "unsatisfied" = has no SUCCEEDED run for MY occurrence
              SELECT 1
                FROM job_execution p
               WHERE p.job_id = d.depends_on_job_id
                 AND p.scheduled_for = e.scheduled_for
                 AND p.status = 'SUCCEEDED'
          )
   )

The obvious implementation — load blocked rows, loop, query each one's parents — is O(blocked × parents) round trips and races with itself across instances. The doubly-negated form promotes every eligible row in one atomic statement, so concurrent resolvers just write the same value to the same rows. And p.scheduled_for = e.scheduled_for is the run-correlation mechanism — it is why yesterday's success cannot unblock today's step. DagEligibilityTest uses a diamond rather than a chain precisely because a chain passes even with a broken "any parent succeeded" rule.

if (worker.leaseTimeout().compareTo(worker.heartbeatInterval()) <= 0) {

A lease shorter than the heartbeat interval means every instance continuously reclaims its own live work and runs everything twice, while every dashboard shows healthy throughput. The default ratio, 30 s / 5 s, is six consecutive missed heartbeats — your tolerance for GC pauses and transient database slowness, not a magic number.

What to take away

  1. Put the lock where the state is. SELECT … FOR UPDATE SKIP LOCKED followed by an UPDATE, in one transaction, gives exact claiming with no lock service, no membership protocol and no fencing tokens — because the row locks hold the line until COMMIT and the status column holds it afterwards. The price is that PostgreSQL becomes a single point of failure, and that is the trade to defend in an interview.
  2. FOR UPDATE and SKIP LOCKED buy different things. The first is correctness; the second is throughput. Without SKIP LOCKED the query is still correct and N workers give you the performance of one, plus lock-wait latency.
  3. The partial index ON job_execution (status, run_at) WHERE status = 'PENDING' is what makes SKIP LOCKED fast rather than merely correct: it stays backlog-sized rather than history-sized, and it serves ORDER BY run_at with no sort node, so every worker walks the same ordered list and takes the first rows nobody holds.
  4. Separate the logical instant (scheduled_for, never moves) from the physical one (run_at, freely moved). One extra column pays for retry backoff, DAG promotion, start jitter and the ability to still answer "was the 09:00 run late?" after three retries.
  5. Derive the idempotency key deterministically from (job, logical instant). A random UUID compiles, passes every single-instance test, and duplicates every cron job the moment you run two replicas.
  6. Transaction-scoped advisory locks (pg_try_advisory_xact_lock) over session-scoped ones: connection pools break session affinity, exception paths leak session locks, and a SIGKILLed instance must not wedge the cluster. Refuse to run outside a transaction rather than silently granting the lock to everyone.
  7. Be honest about the delivery guarantee. The claim is exact; delivery is at-least-once, because a frozen process can finish work that was already reclaimed. Write down which window the ledger closes (lost completion write) and which it does not (duplicated side effect), and require handlers to be idempotent.
