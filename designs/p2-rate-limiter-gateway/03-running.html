Running, testing & exercises

The commands that take this gateway from a git checkout to a 429 you can read, the load-test recipes that prove the limit is real rather than approximately real, and the deliberate breakages — stop Redis, pause Redis, poison an upstream — that make the fail-open policy and the circuit breaker visible instead of theoretical.

Go 1.24 Redis 8 operations
Every mechanism in this project has an observation point

A rate limiter is a distributed algorithm whose whole value is a number being exactly right under concurrency. You cannot review that into existence — you have to watch it. So each mechanism here publishes somewhere you can look at it while it runs: the binding tier in X-RateLimit-Rule, the bucket level in a Redis hash, the fail mode in gateway_ratelimit_errors_total, the breaker in /breakers. Work through this page with three terminals open — one running the gateway, one polling the admin plane, one driving traffic — and every design decision from the previous two pages turns into a number that moves.

Bring the stack up

The dependencies run in containers; the gateway itself runs from source on the host. That split is deliberate: it gives you a sub-second edit–compile–run loop and a debugger you can attach, while Redis and the two upstreams stay fixed. make up starts only the three dependency services and blocks until their healthchecks pass.

the three-command startbash
# 1. dependencies: Redis 8 + two httpbin-style upstreams, waited until healthy
make up

# 2. the gateway itself, from source, on :28080 (admin on :29090)
make run

# 3. in another terminal: watch a 200 become a 429
make smoke

The --wait in the up target is the part worth copying into your own projects. Without it, make up && make smoke races container startup and fails intermittently — and the healthcheck is redis-cli ping, not a port probe, because Redis binds its port before it has finished loading and a client that connects in that window gets LOADING errors.

Makefile: why the wait is not optionalbash
## up: start redis and the two upstreams, and wait for them to be healthy
up:
	# --wait blocks until every started service reports healthy, so the next
	# command in a script can assume the stack is actually ready. Without it,
	# `make up && make smoke` races container startup and fails intermittently.
	$(COMPOSE) up -d --build --wait $(DEPS)

If you have no make — Windows without Git Bash or WSL — every recipe is a plain shell command you can run by hand:

Allowed, then limited — and the headers that say why

The free plan is 5 requests per second burst and 60 per minute sustained. The critical detail in reproducing that from a shell is that the requests must be genuinely simultaneous. Ten separate curl invocations take tens of milliseconds each to start, and the burst bucket refills at 5 tokens per second — 1 token every 200 ms — so a naive for i in 1..10; do curl; done loop can pass all ten. Hand one curl process all ten URLs instead:

ten requests, one curl processbash
URLS=$(for i in $(seq 1 10); do printf 'http://localhost:28080/alpha/json '; done)
curl -s -o /dev/null -H 'X-API-Key: demo-free-key' \
  -w 'status=%{http_code} limit=%header{X-RateLimit-Limit} remaining=%header{X-RateLimit-Remaining} rule=%header{X-RateLimit-Rule} retry=%header{Retry-After}\n' \
  $URLS
five through, then rejectiontext
status=200 limit=5 remaining=4 rule=burst retry=
status=200 limit=5 remaining=3 rule=burst retry=
status=200 limit=5 remaining=2 rule=burst retry=
status=200 limit=5 remaining=1 rule=burst retry=

Now the same ten on demo-enterprise-key (500/s burst): all ten pass, and rule reports whichever tier is closest to exhaustion. That is the header worth understanding, because it is the one that tells a client why it was refused. Burst pressure clears in a second; an exhausted sustained quota clears in a minute; the fleet-wide global ceiling is not the client's fault at all. One undifferentiated 429 hides which is happening, and a client that cannot tell them apart will retry into the same wall.

%header{} needs curl 7.83; older curl prints nothing and you conclude the headers are missing

The -w '%header{X-RateLimit-Limit}' form landed in curl 7.83.0 (2022). On an older build — and the curl bundled with some Git-for-Windows installs is older — the placeholder expands to an empty string with no error, so every line reads limit= remaining= rule= and it looks exactly like a gateway that is not setting headers at all. Check with curl --version, and fall back to -D - plus grep -i '^x-ratelimit', which works everywhere.

Watching burst give way to sustained

The multi-tier design only earns its complexity when you can see one tier hand over to another. Offer the free plan a steady 5 requests per second — exactly its burst rate, five times its sustained rate — and the handover happens on a schedule you can predict to the second. The sustained bucket holds 60 tokens and refills at 60 per minute, which is 1 per second. You are draining it at 5 per second. Net drain is 4 per second, so it hits zero after exactly 15 seconds, and from then on the gateway admits precisely 1 request per second forever.

tokenbucket.lua — why the reported rule changes on its ownlua
local idx = denied_index
if idx == 0 then
  -- Allowed: report the rule closest to exhaustion, measured as a FRACTION of
  -- its own capacity. Comparing raw remaining counts would let a global tier of
  -- 2000 always look "roomier" than a burst tier of 5 even when the burst tier
  -- is the one about to reject the next request.
  local worst = nil
  idx = 1
  for i = 1, n do
    local fraction = tokens[i] / caps[i]
    if worst == nil or fraction < worst then
      worst = fraction
      idx = i
    end
  end
end

Run the same 5 rps for 30 seconds under the other algorithm and the shape changes. Set GATEWAY_LIMITER_ALGORITHM=sliding_window, let the client idle for a full window first, then burst: the token bucket hands you all five instantly because it banked the idle time, while the sliding window counter banks nothing and holds you near a smooth rate. That difference is the entire reason both are in the repository.

the algorithm swapbash
GATEWAY_LIMITER_ALGORITHM=sliding_window go run ./cmd/gateway

# then re-run the ten-request burst above and compare the 200/429 split.
# token_bucket   : idle time is credit. Five instantly, then trickle.
# sliding_window : estimate = prev_count * (1 - elapsed/window) + current_count
#                  no credit accrues, and the fixed-window boundary doubling
#                  (limit at 0.999s + limit at 1.001s) cannot happen.

Inspecting limiter state in Redis

Every bucket is one hash with two fields: t, the token level as a decimal string, and ts, the millisecond timestamp at which that level was accurate. There is no background refill job, so what you read is the level as of the last allowed request — the current level is that plus elapsed time times the refill rate, computed on the next call.

poking at the bucketsbash
R="docker compose exec -T redis redis-cli"

# Keys are rl:{t:<tenant>}:<rule>. The braces are the Redis Cluster hash tag, so
# a tenant's tiers always share a slot and one script can touch them all.
$R --scan --pattern 'rl:*'
#   rl:{t:acme-free}:burst
#   rl:{t:acme-free}:sustained
#   rl:{g}:global

$R HGETALL 'rl:{t:acme-free}:burst'
#   t   0.482000        <- fractional tokens; rounding these away would drift the limit
#   ts  1756800123456   <- when t was accurate

$R PTTL 'rl:{t:acme-free}:burst'       # ~2000  (1s window + 1s TTL_SLACK)
$R PTTL 'rl:{t:acme-free}:sustained'   # ~61000 (60s window + 1s TTL_SLACK)

# Watch the script run, one line per command. Never on a production instance:
# MONITOR streams every command from every client and costs real throughput.
$R MONITOR

Two things are worth confirming with your own eyes here. First, a rejected request writes nothing: hammer a drained bucket and ts does not move. That is the difference between a limiter that protects Redis and one that melts under the traffic it was installed to survive. Second, the keys expire: leave a tenant idle for two seconds and its burst key is gone, which bounds Redis memory to the number of active tenants rather than the number ever seen. A missing key means "start full", which is correct — a bucket that expired has necessarily been idle for at least one full window, which is exactly how long it takes to refill anyway.

KEYS * on a limiter is how you turn a rate-limit outage into a Redis outage

KEYS is O(N) over the entire keyspace and Redis executes it on the single command thread, so on a keyspace holding one hash per active tenant it blocks every other client — including every gateway replica's EVALSHA, on every request. Under GATEWAY_LIMITER_TIMEOUT=150ms that is a fail-open storm triggered by your own debugging. Use --scan, which is cursor-based and cooperative, every single time.

Driving load: hey, vegeta, and which one lies to you

The two drivers are not interchangeable, and for rate-limit work the difference decides whether your numbers mean anything. hey -c 50 keeps 50 requests in flight: a closed-loop generator. When the gateway starts returning fast 429s, the offered load silently rises, because rejections are cheap and the tool immediately sends more. It cannot answer "what happens at exactly 200 rps", because it never actually offers 200 rps. Vegeta's -rate is open-loop — it sends what you asked for regardless of how fast answers come back, which is how real clients behave.

scenario 1: does the limit actually hold?bash
go install github.com/tsenart/vegeta@latest

echo "GET http://localhost:28080/alpha/json" \
  | vegeta attack -rate=200 -duration=60s \
      -header "X-API-Key: demo-pro-key" \
  | tee results.bin \
  | vegeta report

The pro plan is 50/s burst and 3000/min sustained, so a 60-second run at 200 rps offers 12,000 requests and should admit roughly 3,050 — the 3,000 sustained tokens plus the ~50 the burst bucket started full with. Divide the 200: count by 60. If it lands within a percent or two of 50/s the limiter is atomic. If it is meaningfully higher, it is not, and that is the single most important number on this page: a check-and-consume split across a network round trip admits more than its limit only under concurrency, which is precisely when the limit matters.

hey, and the trap it setsbash
make load     # hey -z 30s -c 50 -H "X-API-Key: demo-pro-key" http://localhost:28080/alpha/json

# hey will happily report 4000+ req/s here and it is not a throughput number:

The global tier will bite you at laptop scale and look like a per-tenant bug

GATEWAY_LIMITER_GLOBAL_LIMIT defaults to 2000 per second across all tenants, and it is deliberately small so it is reachable from one machine. Drive two vegeta attacks at 1500 rps each and you will see 429s on the enterprise key that is entitled to 500/s and nowhere near it — because the fleet-wide ceiling bound first. X-RateLimit-Rule: global is the only thing that tells you so. Before concluding the per-tenant maths is wrong, check that header and gateway_ratelimit_decisions_total{rule="global"}.

Cardinality is a design decision, not an afterthought

Every label combination is a separate time series held in memory in this process and forever in your TSDB. This project labels by route (bounded by the number of upstreams), never by URL path; by plan (three values), never by tenant id; never by request id. Adding tenant to gateway_ratelimit_decisions_total looks like a five-character change and multiplies your series count by your customer count — see exercise 9 for the way to get that data without paying for it.

Deliberately breaking Redis

The fail-open/fail-closed flag is the one genuinely unresolved decision in the system, and the only way to have an opinion about it is to watch both modes. There are two ways to break Redis and they produce different failure shapes through the same policy — which is why you should run both.

two different Redis failuresbash
# (a) STOP: connection refused. The limiter fails in microseconds.
docker compose stop redis
curl -s -o /dev/null -w '%{http_code} %{time_total}\n' \
  -H 'X-API-Key: demo-free-key' http://localhost:28080/alpha/json
#   200 0.003     <- fail_open: forwarded, unlimited, in 3ms

# (b) PAUSE: the socket stays open and nothing ever answers. SIGSTOP on the
#     container process, so every limiter call burns the FULL timeout.
docker unpause rlg-redis 2>/dev/null; docker compose start redis
docker pause rlg-redis
curl -s -o /dev/null -w '%{http_code} %{time_total}\n' \
  -H 'X-API-Key: demo-free-key' http://localhost:28080/alpha/json
#   200 0.153     <- GATEWAY_LIMITER_TIMEOUT=150ms, paid on EVERY request

docker unpause rlg-redis

Case (b) is the one that actually happens in production — a Redis under memory pressure, a network partition, a node being cordoned — and it is far worse than case (a), because fail-open now costs 150 ms of added latency on every single request rather than nothing. That is what GATEWAY_LIMITER_TIMEOUT is buying: a bounded amount of damage. The middleware applies it itself rather than delegating to the Redis client, so the trade-off is visible at the point where it is made.

the same flag, at startupgo
// Connectivity is checked at startup rather than discovered on the first
// request. Which way a failure here is fatal depends on the SAME policy the
// limiter uses at runtime -- it would be incoherent to refuse to boot when
// Redis is down and then fail open once running, or vice versa.
switch {
case pingErr != nil && !cfg.Limiter.FailOpen:
	return fmt.Errorf("redis unreachable at %s and the limiter is configured fail-closed: %w",
		cfg.Redis.Addr, pingErr)
case pingErr != nil:
	logger.Warn("redis unreachable at startup; the limiter will fail open until it recovers",
		slog.String("addr", cfg.Redis.Addr),
		slog.String("error", pingErr.Error()),
	)

Liveness must not check Redis — readiness must

/healthz deliberately checks nothing. A liveness probe that fails when Redis is down makes Kubernetes kill and restart every gateway replica during a Redis outage, turning a degraded system into a crash loop at exactly the moment you need the gateway to keep serving. /readyz does ping Redis, and answers differently per mode: fail-open stays 200 ready (degraded) because the replica can still proxy correctly; fail-closed returns 503 so a load balancer drains it. Wiring both probes to the same handler is one of the most common and most expensive Kubernetes mistakes.

Recovery, and the NOSCRIPT path

Bring Redis back and there should be no error spike at all — but the first request pays for something. Redis's script cache is not persistent: it is emptied by a restart, by SCRIPT FLUSH, and, the case that bites people years into a deployment, by failing over to a replica that never saw the script. You can trigger it on demand, which is a far better test than waiting for a failover:

forcing the cold-cache pathbash
R="docker compose exec -T redis redis-cli"

$R CONFIG RESETSTAT
$R SCRIPT FLUSH                     # every EVALSHA now returns NOSCRIPT

curl -s -o /dev/null -H 'X-API-Key: demo-free-key' http://localhost:28080/alpha/json
curl -s -o /dev/null -H 'X-API-Key: demo-free-key' http://localhost:28080/alpha/json

$R INFO commandstats | grep -E 'cmdstat_(eval|evalsha)'
#   cmdstat_eval:calls=1,...        <- one full script body, sent once
#   cmdstat_evalsha:calls=2,...     <- the failed attempt, then the hit
# No errors reached the client. That is the fallback doing its job.

Deliberately breaking an upstream

The test upstream can be told to fail or stall at runtime, with no restart. That is what makes the circuit breaker observable rather than a thing you take on faith.

the fault injectorbash
curl -X PUT 'http://localhost:28081/control?fail_ratio=0.3'         # 30% of requests fail
curl -X PUT 'http://localhost:28081/control?fail_ratio=1&fail_code=503'
curl -X PUT 'http://localhost:28081/control?delay=2s'               # add 2s latency
curl -X PUT 'http://localhost:28081/control?fail_ratio=0&delay=0'   # heal
curl -s http://localhost:28081/control                              # settings + request count
open it, then watch it recoverbash
curl -X PUT 'http://localhost:28081/control?fail_ratio=1&fail_code=503'

curl -s -o /dev/null -H 'X-API-Key: demo-enterprise-key' -w '%{http_code} ' $URLS
#   503 503 503 ... (the upstream's OWN answer) ... then upstream_unavailable

make breakers
#   alpha	state=open	requests=0	failures=0	successes=0
#   beta	state=closed	requests=1	failures=0	successes=1

curl -s http://localhost:29090/breakers      # -> half_open

  http://localhost:28080/alpha/json http://localhost:28080/alpha/json http://localhost:28080/alpha/json

Trickle traffic will never trip the breaker, and it is not broken

GATEWAY_BREAKER_ROLLING_WINDOW is 30 s and the volume threshold is 20. Send failing requests by hand at one per second and the closed-state counters reset before they ever reach 20, so the ratio is never consulted and the breaker sits at closed forever while every request 503s. That is correct behaviour — without the volume threshold the first failed request of a quiet minute is a 100 % failure ratio — but it means the breaker demo needs burst traffic. Use the 30-URL curl above or a vegeta run, not a sleep 1 loop.

why the client sees the upstream's 503, not a synthetic 502go
	if err != nil {
		if resp != nil {
			// We have a real response (a 5xx). The breaker has recorded the
			// failure; the client still gets the upstream's own answer, which is
			// far more useful than a synthetic 502.
			return resp, nil
		}
		return nil, err
	}

Retry amplification and the 504/502 split

scenario 7: a slow upstream, and what your retries do to itbash
curl -X PUT 'http://localhost:28081/control?delay=4s'      # under the 5s budget, over the 3s header timeout

echo "GET http://localhost:28080/alpha/json" \
  | vegeta attack -rate=50 -duration=30s -timeout=10s \
    -header "X-API-Key: demo-enterprise-key" \
  | vegeta report

curl -s localhost:28081/control | jq .requests
#   With MAX_RETRIES=2, 50 rps of failing requests becomes up to 150 rps at the
#   upstream: you are hitting a struggling service three times harder than the
#   client is hitting you. Re-run with GATEWAY_UPSTREAM_MAX_RETRIES=0 and watch
#   this counter drop by two thirds.

The status codes are load-bearing. 504 means "we tried and ran out of time" — retrying may help. 502 means "the conversation failed" — it may not. 503 with upstream_unavailable means the breaker refused and we never tried at all. A gateway that answers 502 for everything teaches its clients to retry things that will never succeed, and teaches its load balancer nothing. The same reasoning governs which upstream statuses are worth another attempt:

proxy.go — the retry classifiergo
	switch resp.StatusCode {
	case http.StatusBadGateway, http.StatusServiceUnavailable, http.StatusGatewayTimeout:
		// These three mean "the upstream infrastructure could not serve this",
		// which is exactly the transient class worth another try.
		//
		// 500 is deliberately NOT retried: it usually means the application
		// threw, and re-sending the same request reproduces the same exception
		// while doubling the load. 429 is not retried either -- the upstream has
		// explicitly asked us to slow down.
		return "status_" + strconv.Itoa(resp.StatusCode), true
	default:
		return "", false
	}
Prove that POST is never retried — do not assume it

Set fail_ratio=1 and send 1,000 POSTs to /alpha/anything. The upstream's own request counter must equal 1,000, not 3,000. Repeat with GET and watch it triple. Retrying a POST is how one "create order" click becomes three orders, and the guard is two conditions that must both hold — isIdempotent(req.Method) and bodyIsReplayable(req). A body over GATEWAY_UPSTREAM_MAX_RETRY_BODY_BYTES (64 KiB) is forwarded once and never retried at all, because buffering unbounded uploads is how a proxy runs out of memory.

The tests, and the one that matters

no Docker requiredbash
make test      # go test -race -count=1 ./...
make bench     # go test -run='^$' -bench=. -benchmem ./internal/limiter/...
make lint      # gofmt + go vet (+ golangci-lint if installed)

Tests run against miniredis, which executes the real .lua through a Lua interpreter in-process — so the script under test is byte-for-byte the script that ships. -race is not optional: the limiter's entire reason for existing in Lua is concurrency correctness and the breaker is mutex-protected shared state, so a suite that never runs under -race does not test either claim. -count=1 defeats Go's test result cache, which otherwise makes make test a very fast way to learn nothing.

the assertion that justifies the whole designgo
	if got := allowed.Load(); got != capacity {
		t.Fatalf("granted %d requests out of %d attempts, want exactly %d; "+
			"a count above the capacity means the check-and-consume was not atomic",
			got, goroutines*attemptsPerWorker, capacity)
	}

Fifty goroutines make 500 attempts against a 100-token bucket and exactly 100 are granted. A naive Go-side GET/compute/SET limiter passes every sequential test in the file and fails this one — and it fails it in production as "our 100/s limit somehow lets through 140/s, but only when we're busy." make bench makes the other structural claim measurable: three tiers cost roughly 15–20 % more than one, not 3×, because they are one round trip and not three.

Exercises

Roughly in order of difficulty. Each one has an observable success condition — a test that should fail, a header that should change, a metric that should move. Write the check first.

  1. Add a leaky bucket as a third algorithm. Write leakybucket.lua and a LeakyBucket type over the existing redisLimiter; it should be ~15 lines of Go, because the marshalling layer is already shared. The bucket holds queued work that drains at a fixed rate, so it admits at a perfectly constant rate and grants no burst credit at all — a client that idles for an hour still gets one request per interval. Add it to TestBothAlgorithmsHonourTheSameContract. The interesting part is RetryAfter: for a leaky bucket it is the queue's drain time, which is a genuinely more useful number than the token bucket's.
  2. Per-endpoint limits. Today the key is {t:<tenant>}:burst, so one expensive endpoint can consume a tenant's entire budget. Add a fourth rule keyed {t:<tenant>}:route:<route> with limits from a small route table. Two traps: the route is only known after the registry matches, but rate limiting deliberately runs before routing — so you need a lightweight prefix matcher ahead of the limiter, and you must keep the new key inside the tenant's hash tag or the script becomes CROSSSLOT on a cluster.
  3. A distributed monthly quota. Add a fourth tier with a 30-day window — say 1,000,000 requests per month. Three things break immediately: the PEXPIRE now keeps a key alive for a month per tenant (memory is no longer bounded by activity), a bucket that expires or is LRU-evicted silently refunds a customer their entire monthly quota, and allkeys-lru in docker-compose.yml is now actively wrong. Decide whether a quota belongs in a limiter at all, or in the billing system with the limiter merely reading it. Write down the answer — this is the exercise about knowing which tool a problem belongs to.
  4. Request coalescing with singleflight. Add golang.org/x/sync/singleflight to the proxy so that N concurrent identical GETs to the same upstream path become one upstream request whose response is shared. Measure it: set delay=2s on alpha, fire 100 concurrent identical GETs, and check curl localhost:28081/control | jq .requests went up by 1 and not 100. Then find the hazards — the shared *http.Response body can only be read once (buffer it, and now you need a size cap), and coalescing requests from different tenants means one tenant's Authorization header serving another's request. Key the flight by the full identity, not the URL.
  5. Weighted routing. Extend GATEWAY_UPSTREAMS to accept several targets per route with weights (alpha|/alpha|http://a:8080=80,http://b:8080=20) and pick per request. Each target still needs its own transport, pool and breaker — that is the whole point — so the registry now owns a slice per route rather than one handler. Then make it useful: skip targets whose breaker is open and renormalise the weights, so a canary that starts failing sheds its traffic automatically instead of failing 20 % of requests.
  6. mTLS to the upstreams. proxy.New already builds a dedicated http.Transport per upstream, so this is a TLSClientConfig with a client certificate and a RootCAs pool — and then all the real work: certificate rotation without a restart (use tls.Config.GetClientCertificate, not Certificates, so a reload is a pointer swap), verifying the upstream's identity rather than setting InsecureSkipVerify, and confirming that ForceAttemptHTTP2 still negotiates h2 over your new config. Check the handshake cost lands in gateway_http_request_duration_seconds only once per connection — if it is per request, your pool is not being reused and MaxIdleConnsPerHost is the reason.
  7. Replace the Lua script with a Redis Function. Redis 8 supports FUNCTION LOAD and FCALL: register the limiter as a named function in a library, and call it by name instead of by SHA1. The payoff is that functions are part of the keyspace — they survive restarts and replicate to replicas — so the entire NOSCRIPT fallback and its digest bookkeeping disappear. Delete luaScript and watch TestColdScriptCacheFallsBackToEval stop making sense; replace it with a test that FUNCTION FLUSH is a deployment operation you must handle, because it is now a much sharper edge.
  8. Adaptive limits driven by upstream latency. Feed the p99 from gateway_http_request_duration_seconds back into the rate card: when an upstream's p99 crosses a threshold, scale every tenant's burst limit down by a factor, and restore it as latency recovers. This is a control loop, so it needs everything control loops need — hysteresis so it does not oscillate, a floor so you cannot throttle to zero, and a bound on how fast the limit may change. Compare it honestly with the alternative you already have: the circuit breaker is a cruder controller that is far harder to get catastrophically wrong. Decide when the extra machinery is worth it.
  9. Per-tenant visibility without per-tenant cardinality. You want to know which tenants are being limited; you cannot afford a tenant label. Keep a bounded count-min-sketch or heavy-hitters structure in the middleware and export the top-N as a gauge you recompute every 30 seconds, so the series count is N regardless of customer count.
  10. Give the breaker's 503 an honest Retry-After. It is currently hard-coded to 5 while the reset timeout is configurable. Expose the breaker's remaining time and use it. Then notice the leak you have created: telling every rejected client the exact instant the breaker half-opens synchronises them all onto it, and the recovering upstream is hit by a thundering herd on a timer. Add jitter, for the same reason the retry backoff already has it.
  11. Shard the global tier. Split it into K counters keyed {g:0} … {g:K-1} with limit/K each, so it can live on a Redis Cluster alongside per-tenant keys. Then measure the fairness cost: a bursty client can exhaust one shard while the others sit idle, so your effective global ceiling is somewhere between limit/K and limit depending on how requests hash. Quantify it before you ship it.

What to take away

  1. Reproduce a burst from one curl process, not a shell loop. The free plan's bucket refills a token every 200 ms, which is faster than a process can start, so a loop of ten curl invocations can pass all ten and convince you the limiter is broken.
  2. Use vegeta, not hey, for anything about rate limits. A closed-loop generator raises its offered load as rejections get cheap, so it measures how fast the gateway can say no — it can never tell you what happens at exactly 200 rps.
  3. The number that validates the whole design is admitted-requests ÷ duration. If it is meaningfully above the configured rate under concurrency, the check-and-consume was not atomic — and that is invisible in every sequential test, including all of the ones that pass.
  4. There are two ways Redis fails and they cost different amounts. docker compose stop gives connection-refused in microseconds; docker pause gives a hang that burns the full GATEWAY_LIMITER_TIMEOUT=150ms on every request. Test the second one — it is the one production gives you.
  5. Fail-open is invisible by construction: traffic flows, nothing 500s, no dashboard turns red. gateway_ratelimit_errors_total{mode="fail_open"} and the matching ERROR log line are the only evidence your rate limits stopped existing. Alerting on them is not monitoring hygiene, it is the control itself.
  6. A breaker needs volume before a ratio means anything, so it will not trip under hand-typed traffic — 20 requests inside a 30-second rolling window, or nothing happens. And it must sit outside the retry loop: retries climbing while the gauge reads open is the signature of getting that backwards.
  7. Every counter should tie out against something you can count by hand. 20 requests × 2 retries = gateway_upstream_retries_total 40. When the arithmetic stops working, trust the mechanism and fix the instrument — an instrument you cannot trust is worse than none.
