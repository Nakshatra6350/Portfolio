Design & algorithms

Why the limit decision lives inside Redis as Lua rather than in Go, why the token bucket is the default of the four candidate algorithms, how three tiers cost one round trip, and where the two genuinely unresolved decisions in this system are — fail-open versus fail-closed, and the middleware ordering.

Requirements, and the numbers they imply

Six requirements drive every decision on this page. Each one eliminates something.

The mental model that matters

A rate limiter is not a counter. It is a compare-and-swap on shared state that sits in front of every single request. That sentence contains both hard parts: the compare-and-swap must be atomic across processes (so it cannot live in your process), and it is on the hot path of everything (so it gets exactly one round trip and a tight deadline). Every design choice below falls out of those two facts.

Four algorithms

Fixed window, and its boundary burst

INCR key, EXPIRE key window, reject above the limit. Two commands, O(1) memory, trivially correct-looking — and wrong at the seam. Windows are aligned to wall-clock boundaries, so a client that spends its whole allowance at the end of one window and its whole allowance at the start of the next has served 2× the limit inside a couple of milliseconds, without ever breaking a rule.

Sliding log, sliding counter, token bucket

A sliding log stores a timestamp per request in a sorted set and trims with ZREMRANGEBYSCORE. It is exact, and its memory and CPU scale with the request rate — precisely the thing you are trying to survive. A client sending 50 000 rejected requests per second makes you store and sort 50 000 entries per second on its behalf.

The sliding window counter keeps the current and previous fixed-window counts and interpolates. O(1) state, no boundary burst, approximate under bursty traffic:

internal/limiter/slidingwindow.lua — the estimate, and its honest error boundlua
--     estimate = prev_count * (1 - elapsed/window) + current_count
--
--   Cost is O(1) in memory and time regardless of rate. The estimate assumes the
--   previous window's requests were spread evenly through it, so it can be off by
--   a bounded amount when traffic was bursty -- roughly the size of one window's
--   worth of clustering. In exchange it kills the fixed-window boundary problem,
--   where a client sends `limit` requests at 0.999s and `limit` more at 1.001s
--   and gets 2x its limit in 2ms.

The token bucket stores a fractional token level and a timestamp, refills lazily from elapsed time, and charges the request. Two fields, O(1), exact, and — uniquely among the four — it has an explicit burst parameter separate from the rate.

Why token bucket is the default for a public API

Real clients are bursty and it is usually harmless: a page load fires twenty parallel requests, a batch job wakes up every minute. The token bucket banks idle capacity, so a quiet client is rewarded with a burst the system can trivially absorb; the sliding counter banks nothing. As slidingwindow.go puts it, "refusing a burst that the system can trivially absorb is a worse experience for no benefit". Flip GATEWAY_LIMITER_ALGORITHM=sliding_window when the thing behind the gateway genuinely cannot take a spike.

internal/limiter/tokenbucket.lua — lazy refill, pass 1lua
  -- One HMGET per bucket. Reading both fields together keeps this at N reads
  -- for N tiers rather than 2N.
  local state = redis.call('HMGET', KEYS[i], 't', 'ts')
  local level = tonumber(state[1])
  local ts    = tonumber(state[2])

  if level == nil or ts == nil then
    -- Missing key means either a brand-new client or an expired bucket. Both
    -- start full: a bucket that expired has necessarily been idle for at least
    -- one full window, which is exactly how long it takes to refill anyway.
    level = capacity
    ts    = now
  end

  -- Lazy refill. elapsed can go negative if this replica's clock is behind the
  -- replica that last wrote; clamping to 0 makes a slow clock harmless (it just
  -- refills nothing) instead of destroying tokens.
  local elapsed = now - ts
  if elapsed < 0 then
    elapsed = 0
  end
  if elapsed > 0 then
    -- capacity/window is the refill rate in tokens per millisecond. Doing the
    -- multiplication before the division keeps precision for small windows.
    level = level + (elapsed * capacity / window)
    if level > capacity then
      level = capacity
    end
  end

There is no refill job, no timer, no cron. Tokens are a function of the stored timestamp, so an idle tenant costs one hash and zero CPU, and a tenant who never comes back costs nothing at all once the key expires.

Store fractional tokens, or your limit quietly drifts

The level is written as string.format('%.6f', level), not as an integer. Round to a whole token on every call and each request leaks or destroys up to one token; at 500 req/s that is a systematic error of the same order as the limit itself — "at high rates drifts the effective limit by a noticeable percentage", as the script says. It never shows up in a unit test at 10 req/s, and it is unattributable in production.

The clock comes from the gateway, not from Redis

ARGV[1] is time.Now().UnixMilli() on the calling replica. That makes the script deterministic and lets tests travel through time without sleeping — but replicas must then agree on the time, and one running fast refills buckets faster than it should. The alternative, redis.call('TIME'), removes skew entirely at the cost of determinism and replayability. The project chose testability and says "run NTP"; see time & clocks for how bad that assumption can get.

Why the check and the update must be one operation

This is the requirement that decides the whole architecture, and it is worth demonstrating rather than asserting. Consider the obvious Go implementation: read the bucket, compute the new level, write it back.

the version that passes every sequential test — do NOT write thisgo
// A read-modify-write limiter. Every single-threaded test in the file passes.
func (b *broken) Allow(ctx context.Context, rules []Rule) (Decision, error) {
    state, err := b.rdb.HGetAll(ctx, key).Result()   // 1. READ
    if err != nil {
        return Decision{}, err
    }
    level := refill(state, time.Now())               // 2. COMPUTE, in this process
    if level < 1 {
        return Decision{Allowed: false}, nil
    }
    b.rdb.HSet(ctx, key, "t", level-1, "ts", now)    // 3. WRITE
    return Decision{Allowed: true}, nil
}
The race is invisible until the exact moment you need the limiter

The broken version is correct at low concurrency, so every sequential test passes. It fails only when callers overlap — precisely when a rate limiter matters. In production it presents as "our 100/s limit somehow lets through 140/s, but only when we're busy", and nobody blames the limiter, because its own dashboard says it is rejecting people.

internal/limiter/tokenbucket_test.go — the test that justifies the designgo
const (

        got, goroutines*attemptsPerWorker, capacity)
}
Why not WATCH/MULTI?

Optimistic concurrency is correct here — WATCH, read, compute, MULTI/EXEC, retry on abort. It costs at least two round trips, and its retry count rises with contention, so its latency is worst exactly when the tenant is hottest. A Lua script is a pessimistic lock that happens to be free: one round trip, no aborts, regardless of load. See transactions & scripting.

Keys, TTLs and the cluster problem

internal/limiter/tiers.go — every key carries a hash taggo
// BuildKey constructs a Redis key suffix with a cluster hash tag.
//
// The tag is the substring between '{' and '}'. Redis Cluster hashes ONLY that
// substring to pick a slot, so every key sharing a tag is guaranteed to live on
// one node -- which is the precondition for evaluating them in one Lua script.
// Tagging by tenant is the natural choice: a tenant's tiers are always evaluated
// together, and different tenants never need to be atomic with each other.
func BuildKey(tag, rule string) string {
	return "{" + tag + "}:" + rule
}

The TTL is the memory bound: expiry turns "every tenant that ever called us" into "every tenant active in the last window or two", which is what makes the 24 MB estimate hold. The slack absorbs clock skew — without it a replica running slightly ahead expires a bucket early and hands a client a free full one.

Adding a global tier breaks Redis Cluster, and the error is CROSSSLOT

A Lua script may only touch keys in one hash slot. The per-tenant keys share {t:<tenant>} and are fine; the global key is {g}, a different slot, so on a real cluster this exact EVAL is rejected. It works here only because the project assumes a single non-clustered Redis — and the estimate above is why that is reasonable. tokenbucket.go documents three ways out, in the order to consider them: (1) give the limiter its own unclustered Redis; (2) evaluate the global tier in a second, pipelined call and accept that a coarse safety net can overshoot; (3) shard it into K counters {g:0}…{g:K-1} with limit/K each — exact totals, but a bursty client can drain one shard while the others idle. See clustering.

Nothing is written on a rejection — and that is load-bearing

Pass 2 does not run when any tier denied. State is always recomputed from (t, ts), so skipping the write loses nothing, and a client hammering a drained bucket generates pure reads: 3 HMGET instead of 9 commands. Invert this — write on every attempt, as naive implementations do — and the harder you are attacked, the more write load your limiter puts on the datastore it shares with everything else.

Composing tiers

A single limit cannot say what an API wants. "1000 per minute" as one bucket lets a client fire all 1000 in the first millisecond. "17 per second" forbids the harmless burst of a page loading twenty resources. Two per-tenant tiers say both things at once, and a third, fleet-wide tier says what neither can: a thousand free tenants each perfectly within 5 rps is still 5000 rps arriving at a service sized for 2000.

internal/limiter/tiers.go — the rate cardgo
// The burst allowance is deliberately a small multiple of the sustained rate
// (roughly 5-10 seconds' worth), not a large one. A burst bucket sized at a
// whole minute of traffic is not a burst allowance, it is a second sustained
// limit that happens to drain quickly.
var plans = map[Plan]PlanLimits{
	PlanFree: {
		Burst:     Tier{Limit: 5, Window: time.Second},
		Sustained: Tier{Limit: 60, Window: time.Minute},
	},
	PlanPro: {
		Burst:     Tier{Limit: 50, Window: time.Second},
		Sustained: Tier{Limit: 3000, Window: time.Minute},
	},
	PlanEnterprise: {

		Sustained: Tier{Limit: 30000, Window: time.Minute},
	},
}

Order matters, and it is a deliberate UX decision. Rules travel narrowest-first, and the script reports the first rule that rejects — so a client that is both bursting and over its monthly volume is told about the burst, the constraint that clears in a second, and gets a short, actionable Retry-After instead of a multi-second one.

Single-pass evaluation permanently strands a client at its sustained limit

Check-and-consume tier by tier and a request rejected by the sustained tier has already burned a burst token. A client pinned at its sustained limit finds its burst allowance drained by requests that never succeeded — and the harder it retries, the longer it stays broken. Exercise 4 has you move the HSET into pass 1 and watch TestRejectedRequestConsumesFromNoTier fail.

On an allow, the script still has to choose which tier to report. It picks the rule with the smallest remaining fraction of its own capacity, not the smallest raw count — otherwise a global tier of 2000 always looks roomier than a burst tier of 5, even when the burst tier is about to reject the next request. Headers that lie are worse than no headers: a client told it has 2900 remaining while its burst bucket is empty retries immediately and is rejected again.

Fail open or fail closed

Redis is now on the critical path of every request. When it is unreachable the gateway must choose between availability and correctness, and there is no universally right answer — which is exactly why it is a configuration flag and not a default buried in code.

internal/middleware/ratelimit.go — the policy, applied in one placego
	// Always at error level, in both modes. Fail-open is the dangerous one
	// precisely because it is invisible from the outside: traffic keeps flowing,
	// nothing 500s, and the only evidence that your rate limits stopped existing
	// is this log line and its metric. Alert on them.
	opts.Logger.LogAttrs(r.Context(), slog.LevelError, "limiter unavailable",
		slog.String("request_id", RequestIDFromContext(r.Context())),
		slog.String("tenant", tenant.ID),
		slog.String("mode", mode),
		slog.String("error", err.Error()),
	)

	if opts.FailOpen {
		next.ServeHTTP(w, r)
		return
	}

	// 503, not 429: the client did nothing wrong, and Retry-After tells it this
	// is a transient condition on our side.
	w.Header().Set(HeaderRetryAfter, "1")
	WriteJSONError(w, r, http.StatusServiceUnavailable, "limiter_unavailable",
		"Rate limiting is temporarily unavailable; the request was not forwarded.")

Two details make the choice deliberate rather than accidental. First, the policy applies only to errors — a rejection is a Decision with Allowed=false, never an error, so fail-open can never turn a legitimate 429 into a 200. Second, the same flag governs startup:

Liveness must not check Redis; readiness must

/healthz answers "is this process alive?" and deliberately checks nothing. A liveness probe that fails when Redis is down makes the orchestrator restart every replica during a Redis blip — a fleet-wide crash loop, and restarting a gateway does not fix Redis. /readyz answers "should this replica take traffic?", and there the dependency matters: fail-open it stays ready (degraded), fail-closed it leaves rotation.

The circuit breaker

The limiter protects upstreams from clients. The breaker protects the gateway from upstreams. When an upstream is failing, each doomed request holds a connection, a goroutine and a client's patience for the full 5-second timeout before failing — so one sick upstream becomes an exhausted gateway and the outage spreads. The breaker converts slow failure into fast failure.

internal/breaker/breaker.go — volume first, then ratiogo
// readyToTrip applies the volume threshold first, then the ratio.
func (b *Breaker) readyToTrip() bool {
	if b.counts.Requests < uint64(b.settings.VolumeThreshold) {
		return false
	}
	ratio := float64(b.counts.TotalFailures) / float64(b.counts.Requests)
	return ratio >= b.settings.FailureRatio
}

A ratio, because "20 failures" means something completely different at 10 rps and at 10 000 rps. A volume threshold first, because without it the first request of a quiet minute failing is a 100 % failure ratio. A rolling window, because cumulative counts let a long-lived healthy process bank so many successes that a real outage can never move the ratio.

The generation counter, and the stale result that closes a breaker it does not belong to

A request issued while CLOSED can return long after the breaker has opened and half-opened. Counted naively, that late success looks like a probe success and closes the circuit on an upstream nobody has actually re-tested. Every state change and every rolling-window reset bumps generation; afterRequest drops any result whose generation no longer matches. Without it, a breaker under load flaps between open and closed and you will spend a day convinced the state machine is wrong.

The breaker sits OUTSIDE the retry loop

The transport stack is breakerTransport → retryTransport → http.Transport. One client request must be one sample. Put the breaker inside and a single failing request with three attempts registers as three failures: the breaker trips three times faster than its threshold claims, and VolumeThreshold: 20 silently means seven. The observable symptom is gateway_upstream_retries_total still climbing while the breaker is open, which is impossible if the ordering is right.

A 5xx is a breaker failure but not a client-visible error

breakerTransport counts any response ≥ 500 as a failure via errUpstreamServerError, then returns it anyway. A breaker that only counts connection errors happily keeps hammering an upstream returning 503 to everything — and the client gets the upstream's own answer, more useful than a synthetic 502.

The request pipeline

internal/middleware/chain.go — build backwards so the list reads forwardsgo
// Chain composes middleware around a handler.
//
// The list reads OUTERMOST FIRST, which is the order requests actually travel:
//
//	Chain(h, A, B, C)  ==  A(B(C(h)))
//
// Building it by iterating backwards is what produces that reading order. The
// naive forward loop gives you A innermost, which reads backwards from how
// anyone describes a request path and is a reliable source of ordering bugs.
func Chain(h http.Handler, middlewares ...Middleware) http.Handler {
	for i := len(middlewares) - 1; i >= 0; i-- {
		h = middlewares[i](h)
	}
	return h
}
Rate-limited requests are attributed to route="unmatched"

Rate limiting deliberately runs before routing, so a throttled tenant costs no routing work. The price is that 429s carry no route label. If you want them attributed, move SetRoute into a lightweight matcher ahead of the limiter and accept that every rejected request now pays for a prefix match.

What to take away

  1. The check and the consume must be one operation. A Go-side read–compute–write passes every sequential test and over-admits under exactly the concurrency the limiter exists to handle. Redis executes a Lua script as one indivisible command; that is the entire reason the algorithm lives in .lua and not in .go.
  2. Token bucket by default, sliding window counter as the alternative. Fixed window loses on the 2×-limit boundary burst; sliding log loses because its cost scales with the request rate you are trying to survive. The token bucket is the only one of the four with a burst parameter independent of the rate.
  3. Two passes, one round trip. Check every tier before consuming from any, or a request rejected by the sustained tier permanently drains the burst allowance of the client that needs it most. All tiers travel in one EVALSHA, which is why three tiers cost ~15–20 % more than one rather than 3×.
  4. Write nothing on a rejection. State is recomputed from (t, ts), so a drained client generates pure reads. Invert this and your limiter's load grows with the attack.
  5. Hash-tag every key by tenant ({t:<tenant>}) so a tenant's tiers share a cluster slot — and know that the fleet-wide {g} tier cannot join them, so a real cluster returns CROSSSLOT. A limiter's working set is tens of megabytes; the first answer is usually "don't shard it".
  6. Fail-open is dangerous because it is invisible. Traffic keeps flowing, nothing 500s, and your only evidence is one error log line and one counter. Alert on both. Keep the same policy at startup and at runtime, keep liveness free of dependencies, and let readiness carry the degradation.
  7. Order is design. Breaker outside retry so one request is one sample; Metrics/Logging outside Recover so a panic is recorded as a 500; Auth before RateLimit so unauthenticated junk never costs a Redis round trip.
