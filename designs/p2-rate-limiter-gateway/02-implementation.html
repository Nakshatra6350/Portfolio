// Chain(h, A, B, C)  ==  A(B(C(h)))  -- built by iterating BACKWARDS, so the
// list reads outermost-first, which is the order requests actually travel.
func Chain(h http.Handler, middlewares ...Middleware) http.Handler {
    for i := len(middlewares) - 1; i >= 0; i-- {
        h = middlewares[i](h)
    }
    return h
}
Metrics and Logging sit OUTSIDE Recover, deliberately

If Recover were the outer wrapper it would write its 500 to the raw ResponseWriter, and both observers would record a success. A panic has to appear in the access log and in gateway_http_requests_total{status="500"}, so the observers must wrap the panic net, not the other way round.

The heart: tokenbucket.lua, pass by pass

Everything else in this project is plumbing around one script. The script exists because the alternative — GET, compute in Go, SET — is a textbook race: two replicas both read “9 tokens left”, both allow, and the limit is silently doubled. Redis executes a script to completion with nothing interleaved, so check-and-consume is one indivisible step across the whole fleet.

pass 1 — lazy refill and the first deniallua
for i = 1, n do
  local base     = 3 + (i - 1) * 3
  local capacity = tonumber(ARGV[base])
  local window   = tonumber(ARGV[base + 1])
  local cost     = tonumber(ARGV[base + 2])

  -- One HMGET per bucket. Reading both fields together keeps this at N reads
  -- for N tiers rather than 2N.
  local state = redis.call('HMGET', KEYS[i], 't', 'ts')
  local level = tonumber(state[1])
  local ts    = tonumber(state[2])

  if level == nil or ts == nil then
    -- Missing key means either a brand-new client or an expired bucket. Both
    -- start full: a bucket that expired has necessarily been idle for at least
    -- one full window, which is exactly how long it takes to refill anyway.
    level = capacity
    ts    = now
  end

  -- Lazy refill. elapsed can go negative if this replica's clock is behind the
  -- replica that last wrote; clamping to 0 makes a slow clock harmless.
  local elapsed = now - ts
  if elapsed < 0 then
    elapsed = 0
  end
  if elapsed > 0 then
    -- capacity/window is the refill rate in tokens per millisecond. Doing the
    -- multiplication before the division keeps precision for small windows.
    level = level + (elapsed * capacity / window)
    if level > capacity then
      level = capacity
    end
  end

  tokens[i] = level

  if denied_index == 0 and level < cost then
    local missing = cost - level
    local wait = missing * window / capacity
    denied_retry_ms = math.ceil(wait)
    if denied_retry_ms < 1 then
      denied_retry_ms = 1   -- never advertise "retry after 0ms"
    end
    denied_index = i
  end
end

No background refill job, no timers: a bucket is a hash of two fields, and its level is computed from the milliseconds elapsed since ts, so an idle tenant costs exactly nothing. The refill is clamped at capacity, so idling overnight does not bank eight hours of tokens and let a quiet tenant flatten every upstream at once. And because the first failing rule wins with rules supplied narrowest-first, the client is told about the constraint that clears in a second rather than the one that clears in a minute.

pass 2 — commit, or write nothing at alllua
if denied_index == 0 then
  for i = 1, n do
    local level = tokens[i] - costs[i]
    tokens[i] = level

    -- %.6f keeps sub-token precision across calls. Storing an integer here would
    -- round away up to a whole token per request, which at high rates drifts the
    -- effective limit by a noticeable percentage.
    redis.call('HSET', KEYS[i], 't', string.format('%.6f', level), 'ts', tostring(now))

    -- A bucket is fully refilled at most `window` ms after this write, so any
    -- key that survives longer than that carries no information. Expiring it
    -- bounds memory to the number of ACTIVE keys rather than the number of keys
    -- ever seen. The slack absorbs clock skew between replicas.
    redis.call('PEXPIRE', KEYS[i], math.ceil(windows[i]) + ttl_slack_ms)
  end
end
Integer token levels leak or destroy budget, and nobody notices for months

string.format('%.6f', level) is doing real work. Round the stored level down and every call throws away up to a whole token — a systematic error of several percent against the limit you sell. Round it up and you manufacture tokens. The reply is floored because Redis truncates Lua numbers on the way out anyway; the stored state must stay fractional.

The reply picks a rule to report. On a denial it is the rule that denied. On an allow it is the rule closest to exhaustion measured as a fraction of its own capacity — not by raw remaining count, which would let a global tier of 2000 always look roomier than a burst tier of 5 that is one request from rejecting.

The clock comes from the client, and that is a trade

ARGV[1] is time.Now().UnixMilli() from the gateway. That makes the script deterministic and lets tests travel through time without sleeping — but replicas must now agree on the time, because one running fast refills buckets faster than it should. Run NTP. redis.call('TIME') removes the skew entirely by giving every replica Redis's clock, at the cost of determinism and replayability. Pick deliberately.

The second algorithm, and what actually changes

slidingwindow.lua answers the same questions with the same reply shape, so the two swap on one environment variable. A true sliding window stores a timestamp per request in a sorted set; its memory and CPU then scale with the request rate, which is precisely the thing you are trying to survive. The counter keeps two integers and estimates.

rolling the window forward and weighting the previous onelua

else

if weight > 1 then weight = 1 end

local estimate = (p * weight) + c

What the counter buys you

A fixed-window counter lets a client send limit requests at 0.999 s and limit more at 1.001 s — twice its limit in 2 ms. The weighted estimate kills that boundary problem at O(1) cost, for a bounded error when traffic was bursty. See Redis · rate limiting.

EVALSHA, NOSCRIPT, and why the fallback is not optional

go:embed compiles the script into the binary, so the deployed artefact has no external file to lose and the script cannot drift out of sync with the Go that parses its reply. The digest is SHA-1 of the body — the same thing Redis keys on — so it is computed locally and SCRIPT LOAD is never needed on the hot path.

internal/limiter/tokenbucket.go — the whole fallbackgo
type luaScript struct {
    src string
    sha string
}

func newLuaScript(src string) *luaScript {
    sum := sha1.Sum([]byte(src))
    return &luaScript{src: src, sha: hex.EncodeToString(sum[:])}
}

func (s *luaScript) run(ctx context.Context, rdb redis.Scripter, keys []string, args []any) (any, error) {
    res, err := rdb.EvalSha(ctx, s.sha, keys, args...).Result()
    if err == nil {
        return res, nil
    }
    if !isNoScriptErr(err) {
        // Anything else -- a timeout, a dead connection, a Lua runtime error --
        // must propagate. Retrying a genuine error as EVAL would just double the
        // latency before failing.
        return nil, err
    }
    return rdb.Eval(ctx, s.src, keys, args...).Result()
}

// Redis signals this with an error string starting "NOSCRIPT"; there is no typed
// error to match on, so string matching is the only option.
func isNoScriptErr(err error) bool {
    if err == nil || errors.Is(err, context.Canceled) || errors.Is(err, context.DeadlineExceeded) {
        return false
    }
    return strings.HasPrefix(err.Error(), "NOSCRIPT")
}
A client without the NOSCRIPT fallback fails at the worst possible moment

The cold-cache path is not an edge case — it is the first request of every process, and it recurs on a restart or a failover, i.e. exactly when you are already having an incident. A limiter that errors there hands fail-open a spike of unlimited traffic, or fail-closed a spike of 503s, for no reason. Warm() is an optimisation on top, not a substitute: main.go treats a failed warm as a warning, never as fatal.

Why Warm compares digests

warm() calls ScriptLoad and then asserts, with strings.EqualFold, that the SHA-1 Redis returns equals the one computed locally — failing startup with script sha mismatch: redis %s, local %s if not. A mismatch would mean every EVALSHA misses and silently degrades to shipping the whole body, forever, while behaving perfectly. That is the worst class of bug: correct output, quietly terrible performance.

The Limiter interface, and tenant → tier resolution

The interface is deliberately narrow, and its most important sentence is about errors.

internal/limiter/limiter.gogo
type Limiter interface {
    // Allow evaluates every rule and consumes budget only if all of them pass.
    //
    // The returned error is reserved for infrastructure failures (Redis down,
    // context deadline, malformed script reply). A rejection is NOT an error: it
    // is a Decision with Allowed=false. Callers apply their fail-open or
    // fail-closed policy to the error, never to the decision.
    Allow(ctx context.Context, rules []Rule) (Decision, error)

    // Name returns the algorithm identifier, for logs and metrics.
    Name() string
}

Two implementations sit behind it, both thin wrappers over the same redisLimiter: they differ only in the Lua they run. That is what makes the swap real rather than aspirational — marshalling, key construction, reply decoding and NOSCRIPT handling are literally the same code, and TestBothAlgorithmsHonourTheSameContract runs identical assertions against both.

Identity comes from the API key, not the IP. Behind NAT thousands of users share an address; behind a mobile carrier one user changes address mid-session. Keying on the credential keys on the thing you actually bill.

internal/middleware/auth.go — the tenant, and constant-time lookupgo
type Tenant struct {
    ID   string        // stable identifier used to build limiter keys
    Plan limiter.Plan  // selects the rate card
    // KeyFingerprint is a short hash of the presented key, safe to log. The raw
    // key is never stored on the Tenant, so it cannot leak into a log line or a
    // panic dump by accident.
    KeyFingerprint string
}

func (a *Authenticator) lookup(presented string) (Tenant, bool) {
    tenant, ok := a.keys[presented]
    if !ok {
        // Burn a comparison anyway so a miss costs roughly what a hit costs.
        var zero [sha256.Size]byte
        presentedSum := sha256.Sum256([]byte(presented))
        subtle.ConstantTimeCompare(zero[:], presentedSum[:])
        return Tenant{}, false
    }
    if subtle.ConstantTimeCompare([]byte(tenant.KeyFingerprint), []byte(fingerprint(presented))) != 1 {
        return Tenant{}, false
    }
    return tenant, true
}
internal/limiter/tiers.go — composing the rule setgo
// BuildKey constructs a Redis key suffix with a cluster hash tag. Redis Cluster
// hashes ONLY the substring between '{' and '}' to pick a slot, so every key
// sharing a tag is guaranteed to live on one node -- the precondition for
// evaluating them in one Lua script.
func BuildKey(tag, rule string) string {
    return "{" + tag + "}:" + rule
}

// ORDER MATTERS. The script reports the FIRST rule that rejects, and these are
// ordered narrowest-first, so a client that is both bursting and over its
// monthly volume is told about the burst.
func RulesFor(tenant string, plan Plan, global Tier, cost int64) []Rule {
    limits := LimitsFor(plan)
    tag := "t:" + tenant

    rules := []Rule{
        {Name: RuleBurst, Key: BuildKey(tag, RuleBurst),
            Limit: limits.Burst.Limit, Window: limits.Burst.Window, Cost: cost},
        {Name: RuleSustained, Key: BuildKey(tag, RuleSustained),
            Limit: limits.Sustained.Limit, Window: limits.Sustained.Window, Cost: cost},
    }

    if global.Limit > 0 && global.Window > 0 {
        rules = append(rules, Rule{
            Name: RuleGlobal, Key: BuildKey("g", RuleGlobal),
            Limit: global.Limit, Window: global.Window, Cost: cost,
        })
    }
    return rules
}

The global tier cannot share a slot with the per-tenant tiers — CROSSSLOT

A Lua script may only touch keys in one hash slot. {t:acme} guarantees burst and sustained land together; {g} is shared by every tenant, so it cannot carry any tenant's tag and a real cluster rejects this EVAL outright. Three ways out, in order: (1) give the limiter its own non-clustered Redis — its working set is tiny and its access pattern uniform, so it rarely needs sharding; (2) evaluate the global tier in a second pipelined call, non-atomic with the first, which is fine for a coarse safety net; (3) shard the global limit into K counters {g:0}…{g:K-1} at limit/K each — exact totals, but a bursty client can exhaust one shard while the others idle. See Redis · clustering.

A missing tenant is a 500, not a free pass

If RateLimit ever runs before Auth, TenantFromContext returns false and the middleware answers 500 with “check the middleware order” rather than picking a default plan: an unlimited path through the gateway is worse than an error that gets noticed. Configuration bugs caught by normalise() are likewise returned before any Redis call, so fail-open can never turn a typo into unbounded traffic.

The circuit breaker

The breaker is mutex-protected rather than lock-free, and that is the right call: the critical section is a handful of integer operations, negligible next to the network call it guards. A lock-free version trades real clarity for imaginary throughput. The interesting field is generation.

internal/breaker/breaker.go — the statego
type Breaker struct {
    settings Settings

    mu    sync.Mutex
    state State

    // generation increments on every state change and on every rolling-window
    // reset. It is how a result that started in one state is prevented from
    // being counted in another: a request issued while closed, that returns
    // after the breaker has already opened and half-opened, must not count as a
    // probe success and close the circuit. Its generation no longer matches, so
    // it is dropped.
    generation uint64

    counts Counts

    // expiry means "when does the current phase end": the moment an open breaker
    // may start probing, or the moment a closed breaker's counters reset.
    expiry time.Time
}
the generation check, and lazy time-driven transitionsgo
func (b *Breaker) afterRequest(generation uint64, success bool) {
    b.mu.Lock()
    defer b.mu.Unlock()

    now := b.settings.Now()
    state, current := b.currentState(now)
    if generation != current {
        // Stale result from a previous state or window. Dropping it is the whole
        // point of the generation counter.
        return
    }
    if success {
        b.onSuccess(state, now)
    } else {
        b.onFailure(state, now)
    }
}

// currentState applies time-driven transitions and returns the live state and
// generation. It must be called with the mutex held.
func (b *Breaker) currentState(now time.Time) (State, uint64) {
    switch b.state {
    case StateClosed:
        if !b.expiry.IsZero() && b.expiry.Before(now) {
            b.newGeneration(now)          // roll the counting window forward
        }
    case StateOpen:
        if b.expiry.Before(now) {
            b.setState(StateHalfOpen, now)
        }
    case StateHalfOpen:
        // No deadline. A timeout here would either cut a recovery short or, if
        // the upstream has gone silent, leave the breaker stuck.
    }
    return b.state, b.generation
}
Without generations, a slow success closes a breaker that has already re-opened

A request issued while closed sits on a 5 s upstream timeout. Meanwhile 20 fast failures trip the breaker, 10 s pass, it half-opens — and now the old call returns 200. Counted naively it is a probe success and it closes the circuit, on evidence gathered before the outage started. TestStaleResultFromAnEarlierGenerationIsIgnored pins exactly this. The same counter drives the rolling window, so failures from 03:00 do not still drag the ratio down at noon.

Classify errors before you count them

registry.go installs IsSuccessful so context.Canceled counts as a success. A request cancelled by the client — a closed browser tab, an impatient mobile app — is not the upstream's failure, and counting it lets one flaky client take an upstream out of service for everyone else. This is the most common way a naively configured breaker fires in production.

The reverse proxy

Each upstream gets its own http.Transport, and therefore its own connection pool, breaker and timeout budget. Sharing one transport would let a slow upstream's connections crowd out a fast one's, coupling the availability of services that have nothing to do with each other.

counting a 5xx as a failure without swallowing itgo
func (t *breakerTransport) RoundTrip(req *http.Request) (*http.Response, error) {
    var resp *http.Response

    err := t.breaker.Do(func() error {
        var callErr error
        resp, callErr = t.next.RoundTrip(req)
        if callErr != nil {
            return callErr
        }
        if resp.StatusCode >= http.StatusInternalServerError {
            return errUpstreamServerError
        }
        return nil
    })

    if err != nil {
        if resp != nil {
            // We have a real response (a 5xx). The breaker has recorded the
            // failure; the client still gets the upstream's own answer, which is
            // far more useful than a synthetic 502.
            return resp, nil
        }
        return nil, err
    }
    return resp, nil
}

A breaker that counts only connection errors will happily hammer a service answering every request with “500 database down”. Counting the status while still returning the body is the whole trick here.

what is worth retrying, and what is notgo
func retryReason(ctx context.Context, resp *http.Response, err error) (string, bool) {
    // Never retry once the caller's budget is gone.
    if ctx.Err() != nil {
        return "", false
    }
    if err != nil {
        // A connection refused, reset or timed out never delivered the request
        // semantics to the upstream, so replaying is safe for the idempotent
        // methods we have already filtered on.
        return "network_error", true
    }
    switch resp.StatusCode {
    case http.StatusBadGateway, http.StatusServiceUnavailable, http.StatusGatewayTimeout:
        // 500 is deliberately NOT retried: it usually means the application
        // threw, and re-sending reproduces the same exception while doubling the
        // load. 429 is not retried either -- the upstream asked us to slow down.
        return "status_" + strconv.Itoa(resp.StatusCode), true
    default:
        return "", false
    }
}

// RFC 9110: sending these N times has the same effect as sending them once.
// POST and PATCH are not idempotent, and retrying them is how one "create order"
// click becomes three orders. The correct way to make a POST retryable is an
// idempotency key the UPSTREAM honours -- not a guess made at the proxy.
func isIdempotent(method string) bool {
    switch method {
    case http.MethodGet, http.MethodHead, http.MethodOptions,
        http.MethodPut, http.MethodDelete, http.MethodTrace:
        return true
    default:
        return false
    }
}
full jitter, not exponential backoffgo
// Full jitter -- a uniform sample from [0, exponential) rather than the
// exponential value itself -- is what actually de-synchronises clients. When an
// upstream blips, every in-flight request fails at the same instant; with fixed
// backoff they all retry at the same instant too, and the recovering upstream is
// hit by the same thundering herd that knocked it over, on a timer.
func (t *retryTransport) backoff(attempt int) time.Duration {
    const maxDelay = time.Second

    delay := t.baseDelay << (attempt - 1) // base * 2^(attempt-1)
    if delay > maxDelay || delay <= 0 {   // <= 0 also catches shift overflow
        delay = maxDelay
    }
    return time.Duration(rand.Int64N(int64(delay) + 1))
}
An abandoned response leaks a connection unless you drain it

When a retry abandons a response, closing the body is not enough: an unread body means the connection cannot return to the idle pool, so every retry opens a fresh connection and the pool leaks until the process dies. The drain is bounded, because reading a gigabyte to be polite to the pool is worse than closing:

func drainAndClose(resp *http.Response) {
    if resp == nil || resp.Body == nil {
        return
    }
    _, _ = io.Copy(io.Discard, io.LimitReader(resp.Body, 64<<10))
    _ = resp.Body.Close()
}
Buffering a body for replay is where a proxy runs out of memory

Replay needs GetBody, which needs the bytes in memory. bufferBodyForReplay reads limit+1 bytes so “at the limit” and “over it” are distinguishable in one read; over the limit it rebuilds the stream with io.MultiReader(bytes.NewReader(buf), req.Body) so nothing is lost, leaves GetBody nil, and the request is never retried. It happens in the Rewrite hook, not the transport, because a RoundTripper is contractually forbidden from modifying the request it is given.

Rewrite, not Director

With the legacy Director hook the outbound request inherits the inbound X-Forwarded-For, so a client can inject any address it likes and your upstream's logs and IP allowlists become fiction. Rewrite's pr.SetXForwarded() replaces those values with what the gateway observed. The same hook strips the routing prefix, sets pr.Out.Host to the upstream's hostname, propagates the request id, and deletes X-API-Key and Authorization — the credential stops here, so a leaked key has one place it can be used, not one per upstream.

Graceful shutdown, in order

cmd/gateway/main.gogo
// A fresh context, NOT the cancelled one: the shutdown budget must survive the
// signal that started it. Passing the cancelled ctx to Shutdown would abort every
// in-flight request instantly, which is precisely what graceful shutdown exists
// to avoid.
shutdownCtx, cancel := context.WithTimeout(context.Background(), cfg.Server.ShutdownTimeout)
defer cancel()

// Data plane first: stop accepting new work while the admin plane is still up, so
// the orchestrator's health checks and the final metrics scrape remain answerable
// while requests drain.
dataErr := dataServer.Shutdown(shutdownCtx)
adminErr := adminServer.Shutdown(shutdownCtx)

if err := errors.Join(dataErr, adminErr); err != nil {
    // Deadline exceeded here means requests were still running when the budget
    // ran out and their connections were dropped. It usually means the shutdown
    // budget is shorter than the request timeout, which can only end this way.
    logger.Error("graceful shutdown incomplete", slog.String("error", err.Error()))
    return err
}
Shutdown budget < upstream timeout is a guaranteed dropped request

The upstream budget is 5 s. Set GATEWAY_SHUTDOWN_TIMEOUT to 3 s and a request that started 1 s before SIGTERM is still running when Shutdown gives up, and its connection is severed. The ordering constraint runs outward too: the pod must leave the Service's endpoints before SIGTERM, or new requests keep arriving at a listener that has stopped accepting. serverErrs is buffered (capacity 2) so a server failing after shutdown began cannot block forever on a send nobody is listening for.

Liveness and readiness split for the same reason. /healthz checks nothing external: a liveness probe that fails when Redis is down makes the orchestrator kill and restart every replica during a Redis outage, turning a degraded system into a crash loop. /readyz does check Redis, and answers 200 ready (degraded) under fail-open but 503 under fail-closed — because that is exactly when the replica cannot do its job.

Cardinality is the design, not an afterthought

Never label by URL path — every /users/12345 is a new time series, held in this process's memory and in your TSDB forever. Label by route, bounded by the upstream count. Never by tenant id, which grows with your customer base; by plan, of which there are three. Never by request id — that is what logs are for. The gateway also registers NewGoCollector and NewProcessCollector: a goroutine leak or FD exhaustion is one of the likeliest ways this process dies, and neither is visible in request metrics.

The route box, and why 429s say route="unmatched"

The metrics middleware runs before routing, so it puts a mutable pointer in the context that the router fills in later. context.WithValue in the router would produce a new context visible only on the inner side of the call — the outer middleware, the one recording the metric, would never see it. Rate limiting also runs before routing, so a throttled tenant costs no routing work and its 429 is attributed to unmatched: an intentional trade.

The tests that carry the design

Tests run against miniredis, which executes the real Lua through an in-process interpreter. That matters: the algorithm under test is the script, so a fake limiter reimplementing the maths in Go would assert nothing about what ships. Clocks are injected, never slept through. And -race is not optional here — the limiter exists in Lua for concurrency correctness, and the breaker is mutex-protected shared state.

the test that justifies the entire designgo
// N goroutines racing on one bucket must together be granted EXACTLY the
// capacity -- not capacity+3 because several of them read "1 token left" at the
// same moment.
//
// A Go-side implementation that did GET, compute, SET would pass every
// sequential test above and fail this one, and it would fail it in production as
// "our 100/s limit somehow lets through 140/s under load, but only when busy".
func TestConcurrentCallersAreGrantedExactlyTheCapacity(t *testing.T) {
    const (
        capacity          = 100
        goroutines        = 50
        attemptsPerWorker = 10 // 500 attempts for 100 tokens
    )
    rules := []Rule{rule(RuleBurst, capacity, time.Minute)}

    wg.Add(goroutines)
    for i := 0; i < goroutines; i++ {
        go func() {
            defer wg.Done()
            // Release every goroutine at once, so the calls genuinely overlap
            // rather than trickling out as the scheduler starts them.
            <-start
            for j := 0; j < attemptsPerWorker; j++ {
                d, err := tb.Allow(ctx, rules)
                if err != nil { errs.Add(1); return }
                if d.Allowed { allowed.Add(1) }
            }
        }()
    }
    close(start)
    wg.Wait()

    if got := allowed.Load(); got != capacity {
        t.Fatalf("granted %d requests out of %d attempts, want exactly %d; "+
            "a count above the capacity means the check-and-consume was not atomic",
            got, goroutines*attemptsPerWorker, capacity)
    }
}

The clock is frozen for the run, so the refill term is exactly zero for every caller and the expected count is a single number rather than a range. Its sibling, TestConcurrentCallersRespectTheTightestTier, asserts the all-or-nothing commit holds under contention: 40 goroutines against a 200-token burst and a 30-token sustained tier admit exactly 30, and the burst bucket ends at exactly 170 — charged once per admitted request.

RESP2 is pinned in the tests on purpose

redis.NewClient(&redis.Options{Addr: mr.Addr(), Protocol: 2}). go-redis v9 negotiates RESP3 with HELLO by default, and the two protocols decode a Lua array reply into different Go types. decodeDecision asserts on []any of int64, so the protocol is part of the contract being tested, not an incidental detail. If you ever see “reply element 0 is float64, want integer” in production, this is why.

The benchmarks make the multi-tier claim measurable rather than asserted: BenchmarkTokenBucketOneTier against BenchmarkTokenBucketThreeTiers is the marginal cost of two extra HMGETs and HSETs inside the same script invocation — roughly 15–20 % more, not 3×. That gap is the entire argument for evaluating tiers in Lua rather than in Go.

What to take away

  1. The atomicity lives in one place: a Lua script Redis runs to completion. Everything in tokenbucket.go is marshalling around it. If you move the arithmetic into Go you get a limiter that passes every sequential test and overshoots its limit under exactly the load it exists to control.
  2. Two passes, not one. Check every tier before consuming from any, and write nothing at all on a rejection — that keeps a client hammering a drained bucket from generating write load, and keeps a sustained-limited client's burst allowance intact.
  3. Store fractional token levels (%.6f) and floor only in the reply. Rounding the stored state leaks or destroys up to a whole token per request, which at high rates silently shifts the limit you sell by several percent.
  4. Every Redis client using EVALSHA must implement the NOSCRIPT fallback, and must implement it only for NOSCRIPT. The script cache is emptied by a restart, a SCRIPT FLUSH or a failover to a replica that never saw the script — so it fires during incidents, not in a quiet corner.
  5. Put the circuit breaker outside the retry loop so one client request is one sample, and give it a generation counter so an in-flight result cannot vote in a state it no longer belongs to. Classify client cancellations as successes, or a single impatient caller can take an upstream out for everyone.
  6. Retry only idempotent methods, only on 502/503/504 and connection errors, with full jitter, and drain the response you abandon. Retrying a 500 reproduces the exception at double the load; retrying a POST turns one click into three orders.
  7. Set every http.Server timeout and raise MaxIdleConnsPerHost off its default of 2. Shut the data plane down before the admin plane, with a fresh context and a budget longer than the upstream timeout.
  8. Label metrics by route and plan, never by path, tenant or request id — and alert on gateway_ratelimit_errors_total{mode="fail_open"}, because fail-open is dangerous precisely in being invisible.
