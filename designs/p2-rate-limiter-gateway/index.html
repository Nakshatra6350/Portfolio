Distributed Rate Limiter & API Gateway

A reverse-proxy gateway in Go that puts a multi-tenant rate limiter in front of a set of upstream services, with every limit decision made inside Redis by a Lua script so the limit is global across replicas rather than per-process. Around that core sit the things a gateway needs to survive contact with production — per-upstream circuit breakers, bounded timeouts, retries that only fire on idempotent methods, request-id propagation and metrics whose cardinality is designed rather than accidental.

The one hard problem this project exists to teach

A rate limit is shared mutable state that every replica reads and writes on every single request. Everything difficult here follows from that one sentence.

The naive limiter — GET the counter, decide in Go, SET it back — is a textbook lost update. Two replicas both read “9 tokens left”, both allow, and your 100/s limit quietly admits 140/s. It is invisible in every sequential test, it only appears under load, and it appears exactly when the limiter matters most. The fix is to move the entire read–modify–write inside Redis, where the single-threaded execution model makes a Lua script a critical section you get for free.

That fix immediately creates the second half of the problem: the limiter is now on the network, on the hot path, in front of everything. Its latency is added to every request, so three tiers must cost one round trip and not three. Its failure is now your failure, so you must decide in advance whether an unreachable Redis means “let everything through” or “let nothing through”. There is no universally correct answer, which is why it is a configuration flag in this codebase and an argument you should be able to make in both directions.

What you will build

One Go binary that listens on two ports. The data plane on :28080 carries tenant traffic through a middleware chain — request id, metrics, logging, panic recovery, API-key authentication, rate limiting — and then reverse-proxies whatever survives to an upstream chosen by path prefix. The admin plane on :29090 serves /metrics, /healthz, /readyz and /breakers, is not rate limited and can be firewalled off, so no tenant can starve your monitoring and no Prometheus scrape costs a customer part of their quota.

Each request is checked against three tiers at once — a per-key burst, a per-key sustained rate, and a fleet-wide global ceiling — by a single EVALSHA. The script evaluates every tier before consuming from any of them, so a request rejected by the sustained tier does not burn a burst token on its way out.

Go 1.24 is not container-aware

The Dockerfile builds on golang:1.24-alpine and sets no GOMAXPROCS. Under a CPU limit — a Kubernetes limits.cpu, a compose cpus: — a Go 1.24 runtime still sizes its scheduler from the host’s core count, so a 32-core node with a 1-CPU limit gives you 32 Ps competing for one CPU’s worth of quota, and throttled latency spikes on the request path. Automatic container-aware GOMAXPROCS arrives in Go 1.25. On 1.24 you set it yourself, from the limit, at startup.

Quick start

Docker and Compose v2 for the stack; make from Git Bash or WSL on Windows. The tests need neither — they run the real Lua against miniredis, in process.

from the repository rootbash
cd 10-projects/p2-rate-limiter-gateway/code

# 1. dependencies: Redis 8 and the two upstreams, waited until healthy
make up

# 2. the gateway itself, from source: data plane :28080, admin plane :29090
make run

# 3. in another terminal -- five 200s on the free plan, then 429s
make smoke
everything in containers, gateway includedbash
make up-all      # compose brings up redis, both upstreams and the gateway
make down        # stop the stack and delete its volumes
tests, benchmarks and lint -- no Docker requiredbash
make test        # go test -race -count=1 ./...
make bench       # limiter benchmarks with allocation counts
make lint        # gofmt + go vet (+ golangci-lint if installed)
poking at a running gatewaybash
curl -s -o /dev/null -H 'X-API-Key: demo-free-key' \
  -w 'status=%{http_code} rule=%header{X-RateLimit-Rule} remaining=%header{X-RateLimit-Remaining}\n' \
  http://localhost:28080/alpha/json

curl -s http://localhost:29090/breakers    # per-upstream circuit breaker state
make metrics                              # the gateway_* series only, no runtime noise
without make (Windows PowerShell or cmd)bash
docker compose up -d --build --wait redis upstream-alpha upstream-beta
go run ./cmd/gateway
Separate curl invocations will not trip the limiter

The free plan allows 5 requests per second. Twelve separate curl processes take long enough to start that the bucket refills between them, and you will see twelve 200s and conclude the limiter is broken. Pass every URL to one curl process so the requests are genuinely close together:

URLS=$(for i in $(seq 1 10); do printf 'http://localhost:28080/alpha/json '; done)
curl -s -o /dev/null -H 'X-API-Key: demo-free-key' -w 'status=%{http_code}\n' $URLS

This is not a quirk of the demo. It is the token bucket doing exactly what it is for: refilling continuously, so a client that spaces its requests out never notices the limit exists.
