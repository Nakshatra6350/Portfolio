Mini-Redis: an in-memory store in Go

A Redis-compatible server written to be read: 71 commands over a streaming RESP2 parser that the real redis-cli connects to without noticing the difference. It implements the mechanisms that make Redis interesting rather than the commands that make it useful — a sharded concurrent keyspace, a hand-written skip list, two-part key expiry, sampled LRU and logarithmic LFU eviction under a memory cap, an append-only log with three fsync policies and a compacting rewrite, and a checksummed binary snapshot. Every one of those is built here rather than imported, in 7,655 lines of implementation and 4,704 lines of tests and benchmarks, with zero third-party dependencies.

The one hard problem

A store that answers in microseconds cannot afford to know the truth. Every question this engine has to answer — which keys have expired, which key is coldest, how much memory am I holding, is this write actually on disk — has an exact answer that costs either a full keyspace walk or a disk flush. The data path can pay for neither. So the engine approximates, and the whole of the engineering is choosing an approximation whose error you can state, bound and test.

That is the project. Five approximations, each with a different shape of error:

  1. Which keys expired? Never scan. Sample 20 keys that have a TTL, delete the dead ones, and repeat immediately if more than 25% of the sample was dead — capped at 16 rounds per shard per call so a keyspace that expires all at once cannot monopolise the cron goroutine. The error is memory held by dead keys, bounded near that 25%; it is never a dead key being visible, because every lookup checks the TTL first. Two halves, and Redis needs both.
  2. Which key is coldest? No LRU list — that would be a pointer write and a cache miss on every read, plus a global structure to lock. Store a timestamp per object, sample maxmemory-samples (default 5) random keys and evict the oldest one you saw. The error is measurable and is measured: TestSampledLRUApproximatesTrueLRU asserts the victim's mean age rank over 200 trials on a 100-key store lands far below the ~50 a random choice would give.
  3. How hot is a key? One byte, and it holds a logarithm, not a count: the probability of incrementing is 1/(baseval × lfu-log-factor + 1), so 5→6 takes a couple of hits and 250→251 takes millions. The error is deliberate — you cannot recover the access count, you can only compare two keys — and without the decay of one point per lfu-decay-time minutes of idleness the counter would be a permanent record rather than a measure of now.
  4. How much memory? Recomputing an entry's size on every mutation is the mutation. So cache a size per entry and keep a per-shard atomic total. This error is the dangerous one: drift is unbounded and silent, and a drifting counter makes eviction either never fire or never stop. Store.VerifyMemoryAccounting() recomputes every entry from scratch and names the first shard that disagrees; the tests call it after randomised workloads.
  5. Is it on disk? appendfsync everysec is one write syscall per command and one flush per second: you survive a process crash intact and lose up to one second to a power cut. always removes the window and buys a disk flush per write. The error is a stated duration, which is the only honest way to sell durability.

The sharded keyspace is the same trade one level up. Real Redis is single-threaded on purpose — nothing can interleave with a running command, so every command is atomic for free. This server runs a goroutine per connection over N independently locked shards: it keeps per-command atomicity exactly, gives up cross-key atomicity, and gains real parallelism across cores. An approximation you imported is one you cannot characterise, which is why none of these are imported.

What you will build

One binary and four internal packages, and the dependency arrows only ever point downward. resp knows about bytes and imports nothing from the project, so the wire format cannot leak into the data structures. store knows about the keyspace and does not import resp. commands sees the server only through two narrow interfaces — ConnInfo and ServerInfo — and those interfaces are the only reason there is no import cycle. server owns the sockets and wires it all together.

Five data types with real representations: strings are byte slices, lists are doubly linked lists, hashes and sets are Go maps, and sorted sets are a skip list plus a member→score map — the same pairing real Redis uses, with a span on every forward pointer so ZRANK is O(log n) rather than a walk. Ordering is by score then lexicographically by member, because that tie-break is what makes the order total and therefore makes ZRANGE deterministic.

The eviction you must log, and the expiry you must not

Every eviction is propagated to the AOF as an explicit DEL. Delete that line and nothing fails: the keyspace is correct, the log faithfully contains every command a client actually sent, and no test that avoids restarting will notice. Then restart. The replay reconstructs the client's stream, every evicted key comes back, and the dataset is over maxmemory before the server has accepted its first connection. Eviction is a decision the server made on its own, so only the server can record it.

The mirror case is the one you must not log. An expired key is never propagated as a DEL here, because the AOF only ever contains absolute deadlines (PEXPIREAT): the replay reaches the same instant and the key expires again by itself. Real Redis does propagate expiry, for a reason that does not apply to a server with no replicas — a replica must never expire a key on its own initiative or the two diverge.

EXPIRE key 60 must never be written to the log as EXPIRE key 60

A relative deadline in a replay log is a key that gains a fresh minute of life every time the process starts. Restart hourly and the key is immortal; the cache silently becomes a leak, and the symptom — memory that only grows on long-lived instances — points nowhere near the cause. EXPIRE key 60 is rewritten to PEXPIREAT key <absolute-ms> before it is appended. aof_test.go asserts the exact bytes on disk for precisely this reason: it is the one bug in the persistence layer that a round-trip test cannot see, because a round trip within the same second still passes.

Go 1.24, and the two things that are not in it

The module targets Go 1.24 and uses math/rand/v2, testing.B.Loop and the min builtin. Two things a reader might reach for are 1.25, not 1.24, and are deliberately absent: runtime.GOMAXPROCS is not container-aware here, so if you run the benchmarks in a CPU-limited container you must set GOMAXPROCS yourself or BenchmarkShardContention will measure the host's core count and tell you nothing; and there is no wg.Go, so the concurrent tests spell out wg.Add(1) / go func(){ defer wg.Done() … }().

Quick start

Go 1.24 or newer and nothing else — there are no dependencies to fetch. Optionally redis-cli and redis-benchmark (any 6.x–8.x), which are the point: a real client must work. Port 6380 is used throughout so it cannot collide with a real Redis on 6379. GNU Make is optional; every target is plain go underneath.

make run persists, so your “fresh” server is not fresh

make run defaults to APPENDONLY=true and DATADIR=./data, which is the right default for a project about persistence and the wrong one when you are chasing a bug. Keys from a previous session are replayed on startup, so a test that assumed an empty keyspace passes or fails for reasons that are not in the code you just changed. Either make clean (which removes ./data, appendonly.aof and dump.mrdb) or run with APPENDONLY=false. Note also that the server loads either the AOF or the snapshot, never both: when the AOF is enabled it is strictly more recent, and merging the two would double-apply every command the snapshot already contains.
