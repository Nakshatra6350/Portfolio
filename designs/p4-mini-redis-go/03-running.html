Running, testing & exercises

Build the server, point the real redis-cli at it, and then push on every mechanism until it shows itself: watch keys expire, fill the store past maxmemory and compare LRU against LFU under a scanning workload, kill the process and replay the AOF, and measure the whole thing against Redis 8 with redis-benchmark — including where it loses, and why.

Go 1.24.6 Redis 8 (redis-cli) run & measure

There are no dependencies to fetch — go.mod declares the module and nothing else — so the first run is a compile and a bind.

A container cannot reach 127.0.0.1:6380

The default listen address is loopback. If your redis-cli lives in Docker, the container's loopback is its own, and the connection is refused with no useful message. Bind the bridge instead and reach the host by name:

go run ./cmd/miniredis -addr 0.0.0.0:6380 -dir ./data -appendonly

docker run --rm -it redis:8 redis-cli -h host.docker.internal -p 6380
docker run --rm    redis:8 redis-benchmark -h host.docker.internal -p 6380 -t get -n 100000

Then remember what you just did: this server has no AUTH, no ACLs and no TLS. 0.0.0.0 on a machine with a routable interface is an open, unauthenticated database. Real Redis ships with protected mode on for exactly this reason. Bind it for the duration of the experiment and put it back.

That cursor is not a bucket index

SCAN returned 163841, not 1. The cursor packs a shard index into the low bits and a slot position into the high bits — cursor = (slot << shardBits) | shardIndex — because Go's map exposes no bucket handle, so Redis's reverse-binary walk is unavailable. internal/store/scan.go documents the one hole this leaves: a shard compaction during an in-flight iteration can shift slot positions downward and skip keys. Exercise 11 in the README is to close it.

Verifying RESP compatibility

Compatibility is easy to assert and easy to check. Drive the socket by hand and read the bytes:

both dialects, and what a lost frame doesbash
# The inline dialect: this is what you get when you type into telnet, and it is
# also what makes `redis-cli --pipe` work with a plain text file of commands.
printf 'SET k "hello world"\r\nGET k\r\n' | nc 127.0.0.1 6380
# +OK
# $11
# hello world

# The multibulk dialect a real client sends.
printf '*2\r\n$3\r\nGET\r\n$1\r\nk\r\n' | nc 127.0.0.1 6380
# $11
# hello world

# A bulk length that lies. Framing is lost, so the server explains and hangs up
# rather than trying to resynchronise by guesswork.
printf '*2\r\n$3\r\nGET\r\n$99\r\nk\r\n' | nc 127.0.0.1 6380
# -ERR Protocol error: expected CRLF after bulk payload

# RESP3 is refused with the code clients look for before falling back.
redis-cli -3 -p 6380 PING
# NOPROTO this server speaks RESP2 only
Protocol errors are a distinct type for one reason

resp.IsProtocolError exists so Conn.serve can tell "the client went away" from "the byte stream no longer makes sense". The first is routine and logged at debug; the second gets an error reply and an immediate close, because a RESP stream that has lost its framing cannot be recovered — every subsequent byte would be interpreted against the wrong grammar. Any protocol implementation that tries to skip forward to the next plausible * is building a security bug.

Expiry, watched from the outside

Two halves, and you can see each one separately. Passive expiry is what makes an expired key invisible; active expiry is what makes it stop costing memory.

the passive half: TTL sentinels and invisibilitytext
127.0.0.1:6380> SET session:9 abc PX 1500
OK
127.0.0.1:6380> PTTL session:9
(integer) 1487
127.0.0.1:6380> TTL nosuchkey
(integer) -2            <- the key does not exist
127.0.0.1:6380> SET permanent v
OK
127.0.0.1:6380> TTL permanent
(integer) -1            <- exists, no TTL
127.0.0.1:6380> EXPIRE session:9 -1
(integer) 1             <- a deadline in the past is a synonym for DEL
127.0.0.1:6380> EXISTS session:9
(integer) 0

The active half only shows up in aggregate. Write a hundred thousand keys that all die within a few seconds, then watch DBSIZE fall without anyone reading them — that is the cron goroutine sampling twenty volatile keys per shard per round and resampling while more than a quarter of the sample comes back dead.

the active cycle, from the client sidebash
# 100k keys, all expiring 5 seconds from now. --pipe streams them in one connection.
seq 1 100000 | awk '{printf "SET vol:%d x PX 5000\n", $1}' | redis-cli -p 6380 --pipe

watch -n1 'redis-cli -p 6380 dbsize; redis-cli -p 6380 info stats | grep -E "expired|cycles"'

# dbsize drops from 100000 toward 0 over a couple of seconds with no reads at all,
# and expired_keys climbs to match. Run the server with -loglevel debug to see
# "active expiry reclaimed keys keys=N" once per cron tick (10 ticks/second at -hz 10).
The active cycle is bounded per call — that bound is visible

activeExpireMaxRounds = 16 caps the rounds per shard per cycle, so with 16 shards one tick reclaims at most 16 × 16 × 20 = 5120 keys. At -hz 10 that is ~51k keys per second of reclamation ceiling. Expire a million keys at the same instant and DBSIZE takes roughly twenty seconds to drain — and used_memory stays high the whole time even though every one of those keys is already invisible to clients. Raising -hz raises the ceiling and the idle CPU cost together; real Redis bounds the same loop with a time budget instead, which is the better shape and a fair thing to change here.

used_memory is accounted bytes, not RSS — and eviction only runs on writes

Two surprises, both real. First, maxmemory 4mb bounds the store's own per-entry accounting (key length, value bytes, per-entry overhead), not the Go heap. Expect RSS several times higher: map buckets, skip list towers, the AOF buffer and GC headroom are all outside it. That is true of real Redis too — used_memory is not RSS there either — but here the gap is wider because there are no listpack or intset encodings. Second:

// dispatch.go
if cmd.IsWrite() {
    // Free memory before the write, not after: the point of maxmemory is
    // that the server never exceeds it, so the room has to be made first.
    evicted, err := d.store.EvictIfNeeded()
    d.propagateEvictions(evicted)
    ...
}

Eviction is driven only by write commands. Lower maxmemory with CONFIG SET on an idle server and nothing at all happens — used_memory stays above the limit until the next write arrives. It looks like the setting was ignored. It was not; there was simply no write to hang the eviction on.

LRU against LFU, under a scan

The interesting comparison is not "which evicts the oldest key" — both do what they say. It is the workload that breaks one of them: a small hot working set plus a long stream of keys that are touched exactly once. That stream is the newest thing in the store at every moment, so recency says keep it and frequency says throw it away.

the experiment, run twice with only the policy changedbash
POLICY=allkeys-lru   # then repeat with allkeys-lfu
go run ./cmd/miniredis -addr 127.0.0.1:6380 -maxmemory 8mb -maxmemory-policy $POLICY &

# 1. Establish the working set and make it genuinely hot.
seq 0 999 | awk '{printf "SET hot:%d %0200d\n", $1, $1}' | redis-cli -p 6380 --pipe
for round in $(seq 1 50); do
  seq 0 999 | awk '{printf "GET hot:%d\n", $1}' | redis-cli -p 6380 --pipe >/dev/null
done

# 2. The scan: 100k single-touch keys, spread over ~30s so the LRU clock ticks.
seq 1 100000 | awk '{printf "SET cold:%d %0200d\n", $1, $1}' \
  | pv -L 4000 -q | redis-cli -p 6380 --pipe

# 3. How much of the working set survived?
survived=0
for i in $(seq 0 999); do
  [ "$(redis-cli -p 6380 exists hot:$i)" = "1" ] && survived=$((survived+1))
done
echo "$POLICY: $survived / 1000 hot keys survived"

redis-cli -p 6380 object freq cold:99999

Fill it in under a second and LRU degenerates into random

The stamp is coarse on purpose:

// lruClock returns the coarse second-resolution clock stored on each value.
// Second resolution is deliberate: it is all the precision an approximated LRU
// needs, and it keeps the per-object metadata small.
func (s *Store) lruClock() uint32 { return uint32(s.now() / 1000) }

A --pipe load that finishes in 400 ms stamps every key with the same second, so idleSeconds returns 0 for every candidate, every score ties, and evictOne keeps sample[0] — whichever key the map iteration happened to yield first. Your LRU experiment measures Go's map randomisation. Spread the load over tens of seconds (the pv -L above) or the result is noise. The same trap exists in real Redis, which is why its LRU test suites all use timed loads.

Switching policy at runtime leaves the other metric stale

Store.touch updates one field — the LFU counter under an LFU policy, the LRU stamp otherwise. So CONFIG SET maxmemory-policy allkeys-lfu on a server that has been running LRU for an hour leaves every existing key at lfuInitVal = 5: for the next few minutes LFU has no information and its evictions are arbitrary. Real Redis says the same thing in the error text OBJECT FREQ returns under the wrong policy, and this server copies that message verbatim. Change the policy at startup when you can; when you cannot, expect a warm-up.

Kill it, restart it, replay the log

The AOF is a RESP stream of the commands that actually changed something. Two properties make the replay trustworthy, and both are visible in the file itself.

what is really on diskbash
redis-cli -p 6380 SET user:1 ada
redis-cli -p 6380 SET user:1 ada NX      # vetoed: nothing changed
redis-cli -p 6380 DEL nosuchkey          # removed nothing
redis-cli -p 6380 EXPIRE user:1 600      # relative
redis-cli -p 6380 INCR hits

cat -A data/appendonly.aof | tr -d '$'   # or: xxd data/appendonly.aof | head
data/appendonly.aof — note what is absent, and what was rewrittentext
*3\r\n
3\r\nSET\r\n
6\r\nuser:1\r\n
3\r\nada\r\n
*3\r\n                       <- the NX-vetoed SET is NOT here (ctx.Dirty stayed 0)
3\r\nPEXPIREAT\r\n           <- EXPIRE 600 was rewritten to an ABSOLUTE deadline
6\r\nuser:1\r\n
13\r\n1756800600000\r\n
*2\r\n                       <- the DEL of a missing key is NOT here either
3\r\nINCR\r\n
4\r\nhits\r\n
Why PEXPIREAT is the only expiry form the log ever contains

From commands/keyspace.go: propagating EXPIRE key 60 verbatim "would give the key a fresh minute of life on every restart, which is one of the classic ways a cache turns into a leak." Because the log only carries absolute deadlines, a replay reconstructs the same instant the key originally had — which is also why this server can get away with not propagating expiry DELs at all, and why it must still propagate eviction DELs. Expiry is a decision time made; eviction is a decision the server made.

crash and recoverbash
redis-cli -p 6380 dbsize          # (integer) 2
kill -9 $(pgrep -f 'miniredis -addr')   # no graceful path, no final snapshot

go run ./cmd/miniredis -addr 127.0.0.1:6380 -dir ./data -appendonly
# level=INFO msg="aof loaded" commands=3 keys=2 took=1ms
redis-cli -p 6380 TTL user:1      # (integer) 583  <- NOT 600. The deadline survived.

# Now simulate a crash *during* a write by lopping off the tail.
truncate -s -8 data/appendonly.aof
go run ./cmd/miniredis -addr 127.0.0.1:6380 -dir ./data -appendonly
# level=WARN msg="aof ends with a partial command; the tail was ignored" commands=2

# And compaction: 500 INCRs collapse into one SET.
for i in $(seq 1 500); do echo "INCR hits"; done | redis-cli -p 6380 --pipe
wc -c data/appendonly.aof         # ~14 KB
redis-cli -p 6380 BGREWRITEAOF
wc -c data/appendonly.aof         # ~120 bytes
kill -9 with appendfsync everysec loses nothing; a power cut loses a second

AOF.Append calls a.w.Flush() on every command regardless of policy, with the comment: "Keeping them in a user-space buffer would mean a clean process kill (not even a crash) could lose commands the client was told had succeeded." So the bytes are always in the page cache and kill -9 is survivable under all three policies. What appendfsync buys is survival of the machine dying. Testing durability with kill -9 therefore proves nothing about always vs everysec — you need to pull the power, or run the server in a VM you can hard-reset.

A rewrite blocks every write for its whole duration

Server.RewriteAOF takes the propagation lock for writing, so during a rewrite every write command queues behind it. On a million-key dataset that is a multi-second stall your clients see as a timeout. Real Redis forks and gets a copy-on-write snapshot for free; Go has no fork. The auto-rewrite trigger (-auto-aof-rewrite-percentage 100, floor 64 MiB) means this can fire on its own at 3 a.m. Building the fork-free equivalent — snapshot shard by shard, buffer arriving commands, drain the buffer before the swap — is the headline exercise in the README.

Set GOMAXPROCS yourself in a container

Go 1.24 is not container-aware: it gives you one P per host core regardless of the cgroup CPU quota. Benchmark this server in a 2-CPU container on a 32-core host and you get 32 Ps fighting over 2 cores' worth of quota, CFS throttling, and numbers that look like lock contention but are scheduler starvation. Container awareness landed in Go 1.25; on 1.24.6 pass GOMAXPROCS explicitly.

CaseWhich winsThe mechanism behind it
-c 1, no pipeline (latency)Redis 8, comfortablyIts event loop reads, executes and writes on one thread with no handoff. Here every command costs a netpoller wakeup and a goroutine schedule.
-c 50 -P 1 (typical)Redis 8, by a smaller marginRedis's parser and reply builder are hand-tuned C with no per-argument allocation. Ours copies every bulk argument out of the read buffer so it stays valid after the next read.
-c 50 -P 16 (pipelined)Close — miniredis can pull ahead on ≥8 coresSyscalls amortise for both, and this is where sharded parallelism actually pays: 16 shards, 50 goroutines, real cores. Redis 8 is one thread for command execution.

Two of those gaps are the code's fault rather than the design's, and a profile finds them immediately. Command lookup upper-cases the name on every single command:

internal/resp/types.go — two allocations per command, on the hot pathgo
// Name returns the upper-cased command name (argv[0]), or "" for an empty
// command. Redis command lookup is case insensitive.
func (c Command) Name() string {
    if len(c) == 0 {
        return ""
    }
    return strings.ToUpper(string(c[0]))
}

string(c[0]) copies, and strings.ToUpper copies again unless the name is already upper-case. At a million commands a second that is two million allocations a second handed to the GC for no result — and BenchmarkCommandLookup exists precisely so you can see it next to the dispatch numbers. Fixing it without changing behaviour is exercise 1.

Run it under -race

The race detector is not optional here, and the Makefile says why: "the store is a sharded, mutex-protected map read and written by one goroutine per connection plus the cron goroutine. A data race here is a correctness bug, not a performance note."

the whole suite, plus a live server under loadbash
make race                       # go test -race -count=1 ./...
go test -race -count=1 ./internal/store -run 'Concurrent|Active|Evict'

# The detector only sees code that actually executes, so drive a RACE-INSTRUMENTED
# SERVER with real traffic while the cron goroutine and eviction are both busy:
go run -race ./cmd/miniredis -addr 127.0.0.1:6380 -hz 100 \
    -maxmemory 8mb -maxmemory-policy allkeys-lfu &

# -race costs roughly 2-20x CPU and ~5-10x memory. Never benchmark under it, and
# never compare a -race number with a clean one.
A clean -race run is evidence, not proof

It reports a race only when two conflicting accesses actually happen, on this run, with no happens-before edge between them — never on a path you did not execute. Three interleavings are worth forcing because the tests cannot easily reach them: eviction firing while the cron cycle holds a different shard, an AOF rewrite (which takes propMu for writing) racing pipelined writes, and Server.Close arriving with fifty connections mid-command. Send SIGINT during the redis-benchmark above and watch the graceful path unwind under instrumentation.

Exercises

Roughly in order of difficulty. Each is a real feature with a real design question inside it, and the package boundaries were drawn so that none of them needs a rewrite.

  1. Profile it and kill the dispatch-path allocations. Add net/http/pprof behind a -pprof-addr flag, run redis-benchmark -t get -n 1000000 -P 16, then go tool pprof -alloc_space http://localhost:6060/debug/pprof/heap and -http=: http://localhost:6060/debug/pprof/profile?seconds=30. You will find Command.Name and the reply path. Fix the lookup with a case-insensitive comparison over the existing []byte (no allocation) or a small perfect-hash table, and prove it with benchstat over BenchmarkDispatch and BenchmarkCommandLookup.
  2. MULTI/EXEC/DISCARD. Queue commands on the connection, then execute them as a unit. The design question is the one store.go's package comment already names: cross-key atomicity is exactly what sharding gave away. Either take every shard lock in a fixed index order (deadlock-free, but it serialises the whole server for the duration of the transaction) or offer a weaker guarantee and write down what it is. Do not offer the strong one and implement the weak one.
  3. WATCH and optimistic locking. Needs a per-key version counter bumped inside shard.drop and every mutation path, plus a per-connection watch list checked at EXEC. Decide what happens when a watched key is evicted or expires — real Redis aborts the transaction, and getting that right means eviction has to bump the version too.
  4. Pub/Sub: SUBSCRIBE, UNSUBSCRIBE, PUBLISH, PSUBSCRIBE. The connection loop in conn.go only ever writes in response to a read, so a published message has nowhere to go. The Go-shaped answer is a buffered outbox channel per connection plus a writer goroutine; a mutex around resp.Writer also works and is worse. Then answer the hard part: what happens when a subscriber stops reading and its outbox fills? Block the publisher, drop the message, or disconnect the slow client — Redis picks the third, via client-output-buffer-limit.
  5. Keyspace notifications. Built on the previous one: __keyspace@0__:<key> and __keyevent@0__:<event> channels, with a notify-keyspace-events flag string selecting classes. The interesting part is where the hook goes. Emitting from inside a shard lock means a channel send under a mutex; emitting from the dispatcher means the event has no access to which key changed unless the handler reports it. The ctx.Dirty pattern already shows the shape of the answer.
  6. RESP3. HELLO 3 currently returns NOPROTO. Add maps (%), sets (~), doubles (,), nulls (_) and push messages (>) to internal/resp, a per-connection protocol version, and make the reply helpers in commands/context.go emit the right shape for both. If that touches more than those two files, the boundaries were drawn in the wrong place — that is the real point of the exercise. redis-cli -3 is your test harness.
  7. Blocking commands: BLPOP, BRPOP, BLMOVE. A goroutine parked until a key gains an element, with a timeout, correct behaviour when the key is deleted or retyped, and no lost wakeups when a push and a block interleave. The trap: you cannot hold the shard lock while waiting. Use a per-key waiter registry outside the lock and re-check the condition after acquiring it.
  8. Lua via a Go VM. Wire in a pure-Go Lua interpreter (yuin/gopher-lua is the usual choice) behind EVAL, EVALSHA and SCRIPT LOAD, with KEYS/ARGV and a redis.call bridge back into the dispatcher. Two hard requirements, both of which real Redis enforces: the script must be deterministic (no wall clock, no unseeded random, no host I/O) or a replayed AOF diverges from the original run; and it must be atomic, which on a sharded store means it inherits the whole of exercise 2. Note this is the first exercise where the project's central trade-off actually stops you.
  9. A Streams type. XADD, XLEN, XRANGE, XREAD, and XADD ... MAXLEN ~. A new ValueType, a new arm in the tagged union, a new case in writeEntryCommands and in the snapshot encoder, and a new memory-accounting path that VerifyMemoryAccounting must still agree with. The ID allocator (<ms>-<seq>, monotonic even when the clock steps backwards) is a nice self-contained problem. Consumer groups are a second exercise, not part of this one.
  10. Replication: REPLICAOF, full sync, then a command stream. The replica connects, the primary sends a snapshot (you already have the binary format), then keeps streaming propagated commands from the point the snapshot was taken — which means a replication backlog buffer and the same "no command may slip between the snapshot and the stream" problem propMu already solves for the AOF rewrite. Then the rule expire.go already warns about: a replica must never expire a key on its own initiative. It serves the key as missing but waits for the primary's DEL, or the two diverge. Test it by pointing a real redis-cli --stat at both.
  11. Consistent hashing across N independent nodes. A client-side or proxy-side ring with virtual nodes, so that adding a fifth server moves ~1/5 of the keys instead of rehashing everything. Measure the actual movement with a script that records key→node before and after. Then find the limitation yourself: MGET across the ring is now N round trips, and there is no MOVED to tell a confused client where a key went.
  12. Cluster-style hash slots with MOVED redirects. 16384 slots, CRC16(key) mod 16384, hash tags ({user:1}:profile), a slot→node map, and a -MOVED <slot> <host>:<port> error for anything not owned locally. Add CLUSTER SLOTS and redis-cli -c follows the redirects for you, which is the moment this stops being a toy. Then reshard: ASK redirects and the MIGRATING/IMPORTING states, which exist because a slot in motion has keys on two nodes at once.
  13. Put it together. Three primaries by slot range from exercise 12, one replica each from exercise 10, and a failover in which the replica is promoted, the slot map updated, and clients learn about it through MOVED. You are now face to face with why real Redis Cluster needs gossip and a majority vote — and why it refuses multi-key commands spanning slots.

What to take away

  1. An unmodified redis-cli, redis-cli --pipe and redis-benchmark all work against this server, and that is the compatibility test that matters. Supporting the inline dialect as well as multibulk is what makes --pipe with a plain text file of commands work at all.
  2. Eviction runs only on write commands, and used_memory is the store's own accounting rather than RSS. Lowering maxmemory on an idle server appears to do nothing until the next write — check evicted_keys in INFO stats before concluding the setting was ignored.
  3. LRU's clock is second-resolution, so any eviction experiment that loads its data in under a second is measuring Go's map iteration order, not the policy. Spread the load, then compare policies — and under a scanning workload expect LFU to keep the working set that LRU throws away.
  4. The AOF contains only commands that changed something (ctx.Dirty > 0) and only absolute deadlines (PEXPIREAT). That pair is what makes a replay reconstruct the same database instead of one where every TTL restarted. Evicted keys are propagated as explicit DELs because no client command implies them; expired keys are not, because the absolute deadline already does.
  5. appendfsync is about surviving the machine, not the process: Append flushes to the OS on every command under all three policies, so kill -9 loses nothing regardless. Benchmarking durability with a kill -9 proves only that the page cache exists.
  6. Against Redis 8 the honest picture is: worse on single-command latency and memory per key (event loop, hand-tuned C, listpack/intset encodings), competitive under deep pipelining on multiple cores (sharded parallelism against one execution thread), and behind on guarantees (no cross-key atomicity). Two of the throughput gaps — the per-command upper-casing in Command.Name and the per-argument copy in the parser — are code, not design, and pprof finds them in a minute.
  7. Run make race before every commit, and drive a go run -race server with real traffic at least once: the detector only sees the interleavings that actually happen, and the ones worth forcing here are eviction against the cron cycle, a rewrite against pipelined writes, and shutdown against fifty live connections.
