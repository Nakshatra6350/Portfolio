Expiry, eviction & persistence

The three mechanisms that turn a concurrent map into a cache: an expiry that never scans the keyspace, a sampled LRU and LFU that never maintains a list, and an append-only log whose durability you dial. All three are approximate on purpose; this page is what each gives up.

Go 1.24.6 store & persistence
The one idea underneath all three

Every exact algorithm here costs O(keyspace) somewhere — time, memory or lock contention; the approximate one costs O(1) with a bound you can state. Exact expiry is a timer per key; exact LRU is a list every read must mutate; exact durability is an fsync per command. Redis approximates all three and makes the error bounded: ~25 % of volatile keys awaiting reclamation, a victim from the oldest sixth, one second of writes. The tests assert those bounds, not the outcomes.

Expiry, half one: passive on access

A key with a TTL is not deleted when the TTL passes. It is deleted when something next looks at it. That is the whole of passive expiry, and it lives in one branch of Store.lookup:

internal/store/store.go — the passive half is four linesgo
// lookup returns the live value for key, deleting it first if it has expired.
//
// This is *passive* expiry: a key with a TTL in the past is still physically
// present until something touches it. Together with the active cycle in
// expire.go it is how Redis keeps expiry O(1) on the hot path.
func (s *Store) lookup(sh *shard, key string) *Value {
	v, ok := sh.entries[key]
	if !ok {
		s.counters.misses.Add(1)
		return nil
	}
	if v.expireAt != 0 && v.expireAt <= s.now() {
		sh.drop(key, v)
		s.counters.expired.Add(1)
		s.counters.misses.Add(1)
		return nil
	}
	s.counters.hits.Add(1)
	s.touch(v)
	return v
}

One comparison against an int64 on a cache line the lookup already pulled in. Free, and it makes the guarantee absolute: an expired key is never visible to a client, however far behind the background cycle is. expireAt is an absolute Unix-millisecond timestamp, not a duration — the decision that makes AOF replay and snapshots correct.

A second reader must not have lookup's side effects, and forgetting it is the classic bug in this design:

internal/store/store.go — the read that must not count as a readgo
// peek is lookup without the hit/miss accounting or the LRU/LFU touch. Scans,
// TTL inspection and eviction sampling use it: looking at a key to decide
// whether to evict it must not make that key look recently used.
func (s *Store) peek(sh *shard, key string) *Value {
	v, ok := sh.entries[key]
	if !ok {
		return nil
	}
	if v.expireAt != 0 && v.expireAt <= s.now() {
		return nil
	}
	return v
}
peek hides the key but does not reclaim it

peek returns nil without calling drop — right for TTL, SCAN and eviction sampling, none of which should mutate a shard they only meant to inspect. But the entry is still in the map, still in sh.expires, still counted in sh.mem. So Store.Len filters explicitly and MemoryUsed genuinely over-reports — not fixable by tightening the accounting, because it is exactly what the 25 % rule bounds.

Expiry, half two: the active sampling cycle

Passive expiry alone leaks: a key written once with a TTL and never read again occupies memory forever. Something has to go looking. The rejected alternatives matter more than the chosen one, because each is the design someone reaches for first:

internal/store/expire.go — the three constants that define the algorithmgo
const (
	// activeExpireSampleSize is how many volatile keys one sampling round looks
	// at. Redis uses ACTIVE_EXPIRE_CYCLE_KEYS_PER_LOOP = 20.
	activeExpireSampleSize = 20

	// activeExpireThresholdNum/Den is the "keep going" threshold: if more than
	// 25% of the sample was expired, the shard is probably full of dead keys,
	// so sample again immediately. Below that, stop and let the next cron tick
	// pick it up. The choice of 25% bounds the expected fraction of expired-but-
	// still-resident keys in the keyspace.
	activeExpireThresholdNum = 1
	activeExpireThresholdDen = 4

	// activeExpireMaxRounds caps the work per shard per cycle so that a
	// keyspace where everything expires at once cannot monopolise the cron
	// goroutine. Redis bounds the same loop by a time budget instead.
	activeExpireMaxRounds = 16
)
internal/store/expire.go — the cyclego
func (s *Store) ActiveExpireCycle() int {
	s.counters.cycles.Add(1)
	total := 0
	for _, sh := range s.shards {
		for round := 0; round < activeExpireMaxRounds; round++ {
			sampled, expired := s.expireSampleRound(sh)
			total += expired
			if sampled == 0 {
				break
			}
			// Keep going only while the sample was dense with dead keys.
			if expired*activeExpireThresholdDen <= sampled*activeExpireThresholdNum {
				break
			}
		}
	}
	return total
}

The comparison is integer cross-multiplication, expired*4 <= sampled*1, not a float division: no rounding, no divide, and the threshold stays a pair of constants you can move to 1/8 and re-run expire_test.go against.

internal/store/expire.go — one roundgo
// The sample is drawn by iterating the shard's `expires` set. Go randomises the
// starting bucket of every map range, which is precisely the uniform-ish sample
// this algorithm needs; Redis has to call dictGetRandomKey explicitly to get
// the same effect.
func (s *Store) expireSampleRound(sh *shard) (sampled, expired int) {
	now := s.now()

	sh.mu.Lock()
	defer sh.mu.Unlock()

	if len(sh.expires) == 0 {
		return 0, 0
	}
	var doomed []string
	for key := range sh.expires {
		sampled++
		v, ok := sh.entries[key]
		if !ok {
			// Defensive: the expires set should never outlive its entry.
			doomed = append(doomed, key)
			continue
		}
		if v.expireAt != 0 && v.expireAt <= now {
			doomed = append(doomed, key)
		}
		if sampled >= activeExpireSampleSize {
			break
		}
	}
	for _, key := range doomed {
		if v, ok := sh.entries[key]; ok {
			sh.drop(key, v)
			expired++
		} else {
			delete(sh.expires, key)
		}
	}
	s.counters.expired.Add(uint64(expired))
	return sampled, expired
}

Two details carry weight. The sample comes from sh.expires — exactly the keys carrying a TTL — not from sh.entries: with ten million keys and a hundred TTLs, sampling the main table finds an expired key roughly never. And deletions happen in a second pass over doomed, because deleting from a map you are ranging over is legal in Go but its interaction with the 20-key bound is not worth reasoning about.

The arithmetic behind 25 %

why a fraction, why 25, why 20text
ONE ROUND:  draw S = 20 keys from the shard's volatile set; D of them are dead.
CONTINUE WHILE:   D * 4 > S * 1        i.e.   D/S > 25%

WHY A FRACTION AND NOT A COUNT
  D/S estimates the DENSITY of dead keys in the volatile set. Stopping at 25%
  means: when the cycle gives up, its best estimate of the dead-but-resident
  fraction is <= 1/4. That is the actual guarantee this design offers. It is
  NOT "a key is reclaimed within X ms" - nothing here promises that. It is
  "at most about a quarter of the volatile keys are waiting", which is what
  bounds the wasted memory, and therefore what maxmemory has to be sized for.

WHY IT CONVERGES
  A round at density f deletes about f*20 keys, so the density falls
  geometrically while it stays above the threshold. Starting from f = 1.0 on a
  volatile set of V keys it takes roughly  ln(0.25) / ln(1 - 20/V)  rounds to
  fall under 25%. V = 1000 -> ~69 rounds. That is why the 16-round cap exists:
  the convergence is fine, the LATENCY of getting there is not, and the cap
  converts "one long stall" into "spread over the next few ticks".

WHY S = 20 AND NOT 200
  sd(D/S) = sqrt(f(1-f)/S).  At f = 0.25, S = 20:  sd = 0.097.
  One round reads the density to about +/- 10 percentage points - far too
  noisy to trust. It is not trusted once. At -hz 10 the decision is retaken
  ten times a second per shard, so the error averages across ticks instead of
  being averaged inside one long lock-holding round. Sampling more per round
  buys precision you do not need and lock hold time you cannot afford.
Go's map randomisation gives you a random window, not a random subset

What Go randomises is the starting bucket and cell; after that, iteration is in bucket order. So one round's 20 keys are 20 consecutive entries from a random offset, not 20 independent draws — keys hashing into the same bucket are always sampled together, and a shard whose dead keys cluster reads deader or livelier than it is. Real Redis calls dictGetRandomKey per draw to avoid this. It does not break the algorithm — the decision is retaken 10× a second from a fresh offset — but a test asserting one round's density will be flaky.

Eviction: why there is no LRU list

A textbook LRU cache is a hash map plus a doubly linked list, and every read unlinks a node and relinks it at the head. Count that here: two pointer writes per read, dirtying a cache line on every operation; a node elsewhere in memory, so an extra cache miss on the hot path; and a global list, so with the keyspace split into 16 independently locked shards it is one lock every reader on every shard must take. Not a smaller problem — the whole problem back again.

internal/store/evict.go — the metadata that replaces the listgo
// lruClock returns the coarse second-resolution clock stored on each value.
// Second resolution is deliberate: it is all the precision an approximated LRU
// needs, and it keeps the per-object metadata small.
func (s *Store) lruClock() uint32 { return uint32(s.now() / 1000) }

// touch records an access. Called by every lookup, so it must be cheap: two
// field writes for LRU, a decay plus a probabilistic increment for LFU.
func (s *Store) touch(v *Value) {
	if s.Policy().isLFU() {
		v.lfu = s.lfuLogIncr(s.lfuDecay(v))
		v.lfuDecay = s.lfuMinutes()
		return
	}
	v.lru = s.lruClock()
}

That is the trade: nine bytes inline in the Value struct, one store instruction on the read path, no shared structure, no lock. The cost is that eviction no longer knows which key is oldest — it has to go and find out.

Switching maxmemory-policy at runtime leaves stale metadata behind

touch updates only the metric the current policy uses, which TestOnlyTheActivePolicysMetadataIsUpdated pins down. So after CONFIG SET maxmemory-policy allkeys-lfu on a server that ran allkeys-lru for a week, every key still carries its birth counter of lfuInitVal = 5, which lfuDecay ages to 0 over "idleness" that never happened. Every old key now scores identically cold, so the first eviction wave is effectively random and discards your hottest data. Change the policy at a restart.

Sampled LRU, and how good the approximation is

internal/store/evict.go — drawing the samplego
// The sample size is the whole basis of the approximation: taking the oldest of
// five draws from a hundred keys lands on the oldest sixth of the keyspace,
// while taking the oldest of three only reaches the oldest quarter. So the
// per-shard cap below must never be allowed to silently shrink the sample --
// one pass over the shards yields at most len(shards)*perShard candidates,
// which falls short of n on a store with very few shards, and the sampler has
// to keep going until it has the n it was asked for.
func (s *Store) sampleVictims(policy Policy, n int) []victim {
	if n < 1 {
		n = 1
	}
	out := make([]victim, 0, n)

	// Take at most half the sample from any one shard: a sample drawn entirely
	// from one shard would be biased toward whatever that shard happens to
	// hold, and with few shards that skews which keys survive.
	perShard := n/2 + 1
	now := s.now()
	lruNow := s.lruClock()

	// Make repeated passes over the shards until the sample is full. Ranging
	// over a Go map starts at a fresh random position every time, so a second
	// pass over the same shard draws different keys; a pass that adds nothing
	// at all means the keyspace is simply smaller than n, and we stop.
	for len(out) < n {
		before := len(out)
		start := int(rand.Uint64N(uint64(len(s.shards))))
		for i := 0; i < len(s.shards) && len(out) < n; i++ {
			sh := s.shards[(start+i)%len(s.shards)]
			want := perShard
			if remaining := n - len(out); want > remaining {
				want = remaining
			}
			out = s.sampleShard(sh, policy, want, now, lruNow, out)
		}
		if len(out) == before {
			break
		}
	}
	return out
}

Two things in that loop carry weight. The repeated passes exist because the per-shard cap bounds a single pass at len(shards) × (n/2+1) candidates: run with -shards 1 and one pass yields 3, not the 5 maxmemory-samples asked for — a quietly worse approximation on exactly the single-shard store TestSampledLRUApproximatesTrueLRU builds. The len(out) == before guard is what ends those passes. Progress is guaranteed while any shard yields a candidate, because the want > remaining clamp keeps want at 1 or more; so a pass that adds nothing means there is nothing to add — an empty keyspace, or a volatile-* policy on a store where no key has a TTL. Without the guard that case spins forever; with it the sampler returns an empty slice, evictOne reports failure, and EvictIfNeeded answers OOM rather than hanging the connection. The price of the extra passes is that nothing dedupes out: on a keyspace smaller than n the later passes re-draw keys the earlier ones already took, so the sample is padded with repeats rather than being short.

internal/store/evict.go — one line per policygo
// score ranks a candidate; larger means evict sooner.
func (s *Store) score(policy Policy, v *Value, now int64, lruNow uint32) int64 {
	switch policy {
	case PolicyAllKeysLRU, PolicyVolatileLRU:
		// Idle seconds: the longer since the last access, the better a victim.
		return int64(idleSeconds(lruNow, v.lru))
	case PolicyAllKeysLFU, PolicyVolatileLFU:
		// Invert the frequency so that rarely used keys score high.
		return int64(lfuMaxVal - s.lfuDecay(v))
	case PolicyVolatileTTL:
		// Evict whatever dies soonest. Scores are negative expiry timestamps so
		// that "sooner" is "larger", keeping the comparison uniform.
		if v.expireAt == 0 {
			return math.MinInt64
		}
		return -v.expireAt
	default: // the random policies
		return 0
	}
}

Accuracy is a one-line order statistic: the best of k uniform draws from N sits at expected rank N/(k+1). That is the whole theory of maxmemory-samples, and TestSampledLRUApproximatesTrueLRU measures it over 200 trials on a 100-key store aged one second apart.

Why N/(k+1)

Rank the N keys by age on [0,1]. Drawing k independently, the chance all k land above x is (1−x)k, so the best draw has CDF 1−(1−x)k and expectation 1/(k+1). Returns diminish harmonically, and the approximation degrades gracefully — a key only has to be old, not oldest, to be a fine victim.

LFU: a one-byte logarithm that forgets

LRU asks "when was this last touched". LFU asks "how often", the right question when a key read a thousand times an hour ago beats one read once a minute ago. But a useful counter costs 4–8 bytes per key. Redis's answer is one byte holding the logarithm of the access count:

internal/store/evict.go — probabilistic increment and time decaygo
// lfuLogIncr increments the counter logarithmically.
//
// The counter is a single byte, but it has to represent access frequencies
// spanning many orders of magnitude. So it is not a count, it is the logarithm
// of one: the probability of incrementing is 1/(baseval*factor + 1), which
// means going from 5 to 6 takes a couple of hits while going from 250 to 251
// takes millions. With the default factor of 10 the counter saturates at 255
// around a million accesses.
func (s *Store) lfuLogIncr(counter uint8) uint8 {
	if counter >= lfuMaxVal {
		return lfuMaxVal
	}
	baseval := float64(counter) - lfuInitVal
	if baseval < 0 {
		baseval = 0
	}
	factor := math.Float64frombits(s.lfuLogFactor.Load())
	p := 1.0 / (baseval*factor + 1)
	if rand.Float64() < p {
		return counter + 1
	}
	return counter
}

// lfuDecay returns the counter after ageing it.
//
// Without decay an LFU counter is a permanent record: a key that was hot during
// startup would outrank everything forever. Every lfu-decay-time minutes of
// idleness costs the counter one point.
func (s *Store) lfuDecay(v *Value) uint8 {
	decayTime := s.lfuDecayTime.Load()
	if decayTime == 0 {
		return v.lfu
	}
	now := s.lfuMinutes()
	if now <= v.lfuDecay {
		return v.lfu
	}
	periods := (now - v.lfuDecay) / decayTime
	if periods == 0 {
		return v.lfu
	}
	if uint32(v.lfu) <= periods {
		return 0
	}
	return v.lfu - uint8(periods)
}

New keys start at lfuInitVal = 5, not 0, so a key written a millisecond ago is not instantly the coldest thing in the store; baseval subtracts that floor, so p = 1 at the initial value and the first access always counts. A new key that cannot leave the floor is a cache that evicts everything it just admitted.

The expected accesses to reach counter c with log factor F is the sum of the per-step geometric means, Σ(F·j+1) for j = 0…c−6 = F(c−6)(c−5)/2 + (c−5):

The gate, the loop and the bound

internal/store/evict.go — freeing until it fitsgo
// maxEvictionsPerCall bounds one EvictIfNeeded call. Without it, a maxmemory
// set below the size of a single large value would spin forever trying to get
// under a limit it can never reach.
const maxEvictionsPerCall = 100_000

func (s *Store) EvictIfNeeded() ([]string, error) {
	limit := s.MaxMemory()
	if limit <= 0 || s.MemoryUsed() <= limit {
		return nil, nil
	}
	policy := s.Policy()
	if policy == PolicyNoEviction {
		return nil, ErrOOM
	}

	var evicted []string
	for i := 0; i < maxEvictionsPerCall && s.MemoryUsed() > limit; i++ {
		key, ok := s.evictOne(policy)
		if !ok {
			break
		}
		evicted = append(evicted, key)
	}
	if s.MemoryUsed() > limit {
		return evicted, ErrOOM
	}
	return evicted, nil
}
internal/server/dispatch.go — evict before the write, and log the DELsgo
	if cmd.IsWrite() {
		// Free memory before the write, not after: the point of maxmemory is
		// that the server never exceeds it, so the room has to be made first.
		evicted, err := d.store.EvictIfNeeded()

			// Commands that only free memory (DEL, LPOP, EXPIRE) are still
			// allowed when we are over the limit -- refusing them would leave

			out.WriteError(store.ErrOOM.Error())
			return
		}
	}
Evictions must be propagated; expiries need not be

propagateEvictions appends an explicit DEL key per evicted key. Not tidiness: eviction is a decision the server made under memory pressure that nothing in the client's command stream implies. Replay without those DELs and every evicted key returns, putting the restored dataset instantly over maxmemory. Expiry needs no such record — an absolute PEXPIREAT replays to the same instant. Expiry is derivable; eviction is a decision. (Real Redis propagates expiry DELs anyway, because a replica may never expire a key on its own initiative.)

The append-only file

The AOF is a RESP command stream, byte for byte what a client would have sent — no second serialisation format to keep in sync with the protocol, and redis-cli --pipe < appendonly.aof replays one into any real Redis:

internal/persist/aof.go — append, and where the bytes actually gogo
func (a *AOF) Append(args [][]byte) error {
	a.mu.Lock()
	defer a.mu.Unlock()
	if a.closed || a.f == nil {
		return errors.New("aof: closed")
	}

	if err := a.w.WriteCommand(args); err != nil {
		return err
	}
	// Always push the bytes to the OS. Keeping them in a user-space buffer
	// would mean a clean process kill (not even a crash) could lose commands
	// the client was told had succeeded.
	if err := a.w.Flush(); err != nil {
		return err
	}
	a.needsFsync = true

	if a.policy == FsyncAlways {
		if err := a.f.Sync(); err != nil {
			return err
		}
		a.needsFsync = false
	}
	return nil
}

"Nothing lost on kill -9" is a property of Append, not of the policy

Every policy flushes the user-space resp.Writer to the OS on every command, no included. Delete that a.w.Flush() to "make no faster" and you break all three at once: a clean SIGKILL drops every command still in the buffer — commands the client was told had succeeded. Safe buffering is the kernel's, because the kernel outlives your process.

Rewrite: compacting the log

A log of everything that ever happened is enormous and mostly redundant: a counter INCRed a million times is a million commands one SET replaces. The rewrite walks the current dataset and emits the shortest sequence that rebuilds it:

internal/persist/aof.go — rebuild, then swap atomicallygo
	tmpPath := a.path + ".rewrite"
	tmp, err := os.OpenFile(tmpPath, os.O_CREATE|os.O_TRUNC|os.O_WRONLY, 0o644)
	// ... write every entry, then Flush, Flush, Sync, Close ...

	// The live file has to be closed before the rename: on Windows you cannot
	// replace a file that is still open. Closing first also means a crash
	// between the two steps leaves either the old file or the new one intact,
	// never a half-written mixture.
	if err := a.w.Flush(); err != nil {
		os.Remove(tmpPath)
		return err
	}
	if err := a.f.Close(); err != nil {
		os.Remove(tmpPath)
		return err
	}
	if err := os.Rename(tmpPath, a.path); err != nil {
		// Try to get back to a working state before reporting the failure.
		if f, rerr := os.OpenFile(a.path, os.O_CREATE|os.O_WRONLY|os.O_APPEND, 0o644); rerr == nil {
			a.f = f
			a.w = resp.NewWriter(f)
		}
		return fmt.Errorf("aof rewrite: rename: %w", err)
	}

		if err := w.WriteCommand([][]byte{
			[]byte("PEXPIREAT"), []byte(e.Key),
			[]byte(strconv.FormatInt(e.ExpireAt, 10)),
		}); err != nil {
			return err
		}
	}

Note min — the builtin since Go 1.21, no helper and no generics ceremony. And note the third place absolute time pays off: whatever the client sent, the compacted file holds PEXPIREAT key <absolute-ms>. Rewrite ten times and the key still dies at the instant it was always going to.

The rewrite blocks every write, and the reason is that Go has no fork

Real Redis forks a child and gets a copy-on-write heap snapshot free. Go cannot fork — a forked Go process inherits one thread and a runtime full of locks held by threads that no longer exist. So server.RewriteAOF takes the dispatcher's propagation lock for writing across the whole rewrite, stopping a command being applied to the store but not yet logged while the rewriter reads the keyspace. The cost: every write stalls for the length of the rewrite (the everysec flusher too, so the one-second guarantee is suspended), and auto-aof-rewrite-percentage 100 makes that happen unannounced whenever the log doubles. The fork-free version is the README's headline exercise.

Propagation is driven by a dirty counter, not by the command name

Context.Dirty decides what reaches the log: a SET that NX vetoed, a DEL of a missing key, an SREM that removed nothing — all stay out. PropagateAs then rewrites two classes: non-deterministic (SPOP → explicit SREM key member…) and relative-time (EXPIRE key 60 → PEXPIREAT key <ms>). Skip the second and a key gains a fresh minute of life on every restart.

Replay, snapshots and the durability table

internal/persist/aof.go — a truncated tail is expected, not exceptionalgo
	r := resp.NewReaderSize(f, 256*1024)
	applied := 0
	for {
		args, err := r.ReadCommand()
		if err != nil {
			if errors.Is(err, io.EOF) {
				return applied, nil
			}
			if errors.Is(err, io.ErrUnexpectedEOF) || resp.IsProtocolError(err) {
				// The process died mid-write. Everything up to here is intact.
				return applied, ErrTruncated
			}
			return applied, err
		}
		if len(args) == 0 {
			continue
		}
		if err := exec(args); err != nil {
			return applied, fmt.Errorf("aof replay: %q: %w", args.String(), err)
		}
		applied++
	}

A file ending mid-command is what a crash during a write looks like — everything before the truncation point was acknowledged, so the server warns and carries on. A command that parses but fails to execute is different: the log disagrees with the code, and that is fatal. Replay goes through Dispatcher.Replay, bypassing eviction, the OOM gate and propagation — evicting during a load would silently drop data, and re-propagating would append every command back to the file it came from.

internal/persist/snapshot.go — the whole format, from the package commenttext
"MINIRDB1"                       8 byte magic
repeated entries:
  1 byte   type tag (1 string, 2 list, 3 hash, 4 set, 5 zset)
  uvarint  key length, then the key bytes

  payload, depending on the tag

8 bytes  little-endian CRC-64 (ECMA) of everything above

Lengths are varints because most of them are small: a 12 byte key costs one
length byte, not eight. The trailing checksum is what makes a truncated or
corrupted file detectable instead of silently loading half a database.

Three decisions worth copying. Scores go out as raw IEEE-754 bits, not decimal: a formatted-then-parsed float is not guaranteed to be the same float, and a score off by one ULP reorders the skip list. readUvarint is hand-written to decode a byte at a time so every consumed byte lands in the running CRC. And maxBlobLen plus minCap mean a corrupt length field fails on the checksum rather than on an OOM. TestSnapshotAndAOFRewriteAgree then runs one dataset through both paths — two independent encoders, so a bug in either shows up as a disagreement.

On startup it is the AOF or the snapshot, never both

With -appendonly set, loadFromDisk replays the AOF and never touches the snapshot. The reason is arithmetic: the AOF is strictly more recent, and applying both double-applies every command the snapshot contains — harmless for SET, and it doubles your lists for RPUSH. So enabling the AOF on a snapshot-only server silently ignores dump.mrdb and starts empty.

Assert the invariant, not the bytes

Eviction rests entirely on the memory accounting, so the tests call Store.VerifyMemoryAccounting() after randomised workloads: it recomputes every entry from scratch and names the first drifted shard. Incremental accounting rots silently, and a drifting counter makes eviction either never fire or never stop.

What to take away

  1. Passive expiry is the correctness guarantee; the active cycle is the memory guarantee. One int64 comparison in lookup makes an expired key permanently invisible; the sampling cycle exists only so a key nobody reads again does not occupy memory forever. Neither alone is sufficient.
  2. The 25 % threshold bounds wasted memory, not latency. Nothing promises a key is reclaimed within any particular time. It promises that when the cycle stops, its estimate of the dead-but-resident fraction of the volatile set is under a quarter — the number maxmemory has to be sized against. A 20-key sample reads that density to only ±10 points; the fix is re-deciding 10× a second, not sampling more per round.
  3. True LRU is rejected for what it costs on reads, not on evictions. A list means two pointer writes, a cache miss and a global lock on every GET. Sampling moves the whole cost to eviction time, and the best of k draws lands at expected age rank N/(k+1) — the oldest sixth at the default maxmemory-samples 5, with harmonically diminishing returns after that.
  4. The LFU byte is a logarithm with a half-life. Increment probability 1/(baseval*factor+1) makes 250→251 cost ~2,500× what 5→6 costs, so one byte spans five orders of magnitude; the per-minute decay stops a key that was hot at startup being immortal. Switching maxmemory-policy at runtime leaves every counter stale and the first eviction wave pays for it.
  5. Absolute deadlines, everywhere. expireAt is a Unix-millisecond timestamp; EXPIRE propagates as PEXPIREAT, SET … EX as SET … PXAT; the rewrite re-emits PEXPIREAT; the snapshot stores the same integer. That invariant is why replay is idempotent over time and why expired keys need no DEL in the log.
  6. Evicted keys must be logged as explicit DELs. Eviction is a server-side decision no client command implies, so a replay without them resurrects every evicted key and puts the restored dataset instantly over its limit.
  7. The fsync dial only trades against power cuts. All three policies write(2) per command, so all three survive kill -9 identically; what always, everysec and no change is the window a power failure can take — one command, one second, or one kernel writeback interval.
