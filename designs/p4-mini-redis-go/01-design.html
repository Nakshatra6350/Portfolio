Design & the RESP protocol

The four packages, the wire format byte by byte, why the parser refuses to trust a length prefix, and the one decision that shapes everything else: real Redis is single-threaded and therefore trivially atomic, and this server is not.

Go 1.24.6 resp & keyspace design

What we are building, and what we are not

A Redis-compatible server the real redis-cli talks to without noticing, in four packages with no third-party dependencies. Everything interesting is written rather than imported: a streaming RESP2 parser, a sharded keyspace, five data types with a real skip list behind the sorted set, two-part expiry, sampled LRU/LFU eviction, an append-only log and a checksummed snapshot. It is not a clone, and the divergences are stated up front — a teaching implementation that hides its shortcuts teaches the wrong thing.

RESP2 on the wire

RESP2 is deliberately trivial: the first byte names the type, every frame ends in CRLF, and an aggregate has no terminator — the declared count is the contract. That is the whole protocol, and it is why a server can push millions of frames a second while you can still debug it with telnet.

internal/resp/types.go — the five type bytes and the limitsgo
// Frame type bytes. These are the first byte of every RESP2 frame.
const (
	TypeSimpleString byte = '+'
	TypeError        byte = '-'
	TypeInteger      byte = ':'
	TypeBulkString   byte = '$'
	TypeArray        byte = '*'
)

// Protocol limits. Real Redis uses the same values (proto-max-bulk-len defaults
// to 512MB, the multibulk limit to 1M elements, inline requests to 64KB). They
// exist to stop a malicious client from making the server allocate unbounded
// memory from a three byte header.
const (
	MaxBulkSize        = 512 * 1024 * 1024
	MaxMultiBulkLength = 1024 * 1024
	MaxInlineSize      = 64 * 1024
	maxHeaderLine      = 128
)

Requests are narrower than replies: a command is always an array of bulk strings. There is a second dialect — inline commands, a bare space-separated line, what you get typing into telnet — parsed with Redis's own sdssplitargs rules: double quotes allow \n \r \t \b \a \xHH \" \\, single quotes only \', and an unbalanced quote is a protocol error rather than a guess, "because guessing would silently execute a different command than the user typed".

RESP3 is a superset, and this server refuses it honestly

RESP3 (Redis 6+) adds the typed frames the flat arrays above have to fake: _ null, , double, # boolean, % map, ~ set, ( big number, = verbatim and > out-of-band push — which is what makes client-side caching and Pub/Sub on a live connection possible. A client asks with HELLO 3:

// cmdHello answers the handshake redis-cli sends when it is asked for RESP3.
// We only speak RESP2, so anything other than protocol 2 is refused with the
// error code clients look for before falling back.
func cmdHello(c *Context) {
	if c.ArgCount() > 1 {
		ver, err := strconv.Atoi(c.Str(1))
		if err != nil || (ver != 2 && ver != 3) {
			c.Errorf("NOPROTO unsupported protocol version")
			return
		}
		if ver == 3 {
			c.Errorf("NOPROTO this server speaks RESP2 only")
			return
		}
	}

NOPROTO is the specific code every client library checks before downgrading, so a modern redis-cli connects and works. Returning a generic ERR here would make the client give up instead.

The parser: streaming, bounded, hostile-input-safe

"Streaming" means the parser never needs a whole command in memory and never loses its place when one arrives split across TCP segments. In an event-loop server that needs a hand-rolled state machine with saved partial state; with a goroutine per connection it falls out of bufio.Reader for free — when the buffer runs dry mid-frame the underlying Read just blocks.

internal/resp/reader.go — the element loop, with every check that mattersgo
	count, err := strconv.Atoi(string(line))
	if err != nil || count > MaxMultiBulkLength {
		return nil, protoErrorf("invalid multibulk length")
	}
	if count <= 0 {
		// "*0\r\n" and "*-1\r\n" are legal no-ops. redis-cli --pipe emits them.
		return Command{}, nil
	}

	args := make(Command, 0, count)
	for i := 0; i < count; i++ {
		typ, err := r.br.ReadByte()
		if err != nil {
			return nil, err
		}
		if typ != TypeBulkString {
			return nil, protoErrorf("expected '$', got '%c'", printable(typ))
		}
		line, err := r.readLine(maxHeaderLine, "too big bulk count string")
		if err != nil {
			return nil, err
		}
		length, err := strconv.Atoi(string(line))
		if err != nil || length < 0 || length > MaxBulkSize {
			return nil, protoErrorf("invalid bulk length")
		}
		// Read the payload plus its CRLF in one shot. io.ReadFull is what makes
		// partial reads a non-issue: it keeps pulling until it has every byte.
		buf := make([]byte, length+2)
		if _, err := io.ReadFull(r.br, buf); err != nil {
			return nil, err
		}
		if buf[length] != '\r' || buf[length+1] != '\n' {
			return nil, protoErrorf("expected CRLF after bulk payload")
		}
		// Three-index slice so a later append cannot scribble over the CRLF
		// bytes that are still inside the same allocation.
		args = append(args, buf[:length:length])
	}

Read if err != nil || length < 0 || length > MaxBulkSize as the security control it is. make([]byte, length+2) is the one place where a remote peer picks an allocation size, and the guard sits directly above it — before the allocation, because a Go allocation of 3 GiB does not fail gracefully, it takes the process down.

Never trust a length prefix — and "trust" includes the count, the header, and the line

Three separate unbounded quantities hide in a RESP request and all three need a lid:

  • The element count. *2000000\r\n is 11 bytes; without MaxMultiBulkLength, make(Command, 0, count) turns them into 16 MB of slice headers, and a few hundred connections doing that concurrently is an OOM kill.
  • The payload length. Bounded by MaxBulkSize before the allocation.
  • The header line itself. The subtle one. readLine loops on bufio.ErrBufferFull to assemble a line longer than the 16 KiB buffer, so without a cap a client sending "*" and an endless stream of digits with no newline grows r.line forever. Hence readLine(maxHeaderLine, …).

A negative bulk length is rejected too: $-1 is a reply construct. Accepting it in a request would mean make([]byte, -1+2) and an index into buf[-1] — a panic any client could trigger at will.

The three-index slice is not stylistic

args = append(args, buf[:length:length]). The payload and its CRLF live in one allocation. A two-index buf[:length] carries capacity length+2, so a later append to that argument — handlers do append, e.g. strconv.AppendInt(v.str[:0], next, 10) — writes into bytes another part of the code still believes are a frame terminator. Capping capacity forces a copy instead.

readLine's result aliases a reusable buffer

It returns a slice of r.line, the Reader's scratch, which the next read overwrites: "callers must parse or copy it immediately". Hence strconv.Atoi(string(line)) at every call site — the string() is the copy — and hence Command.Copy(): the AOF keeps commands after the connection buffer has been recycled. Skip it and the log fills with the next command's bytes.

Once framing is lost there is nothing to do but hang up. The parser signals it with a distinct type, so the connection loop can tell "you sent nonsense" from "you hung up":

Inline mode makes every non-RESP byte stream a command

Anything not starting with * is an inline command — what real Redis does, and why "cross-protocol scripting" is a Redis CVE class: a browser tricked into POSTing to port 6379 produces lines like POST / HTTP/1.1 that the server happily parses, letting the attacker smuggle a CONFIG SET dir in the body. Real Redis now hard-closes a connection whose first inline word is POST or Host:. This server does not, and has no authentication — hence the 127.0.0.1 default.

The reply side has one idea worth stealing. resp.Writer is sticky: after the first failure every write is a no-op and the error is latched until Flush reports it. Seventy handlers that would otherwise be half error-handling become straight-line code, and the socket-is-broken discovery lands where it can be acted on.

internal/resp/writer.go — error latching, and why the count is the contractgo
func (w *Writer) writeBytes(b []byte) {
	if w.err != nil {
		return
	}
	if _, err := w.bw.Write(b); err != nil {
		w.err = err
	}
}

// WriteArrayLen writes an array header. The caller must then write exactly n
// elements; RESP has no terminator, the count is the contract.
func (w *Writer) WriteArrayLen(n int) error {
	w.writeHeader(TypeArray, int64(n))
	return w.err
}

// WriteFloat writes a float as a bulk string using Redis's formatting rules.
// RESP2 has no float type, which is why ZSCORE returns a bulk string.
func (w *Writer) WriteFloat(f float64) error {
	return w.WriteBulkString(FormatFloat(f))
}
Declare n, write n — a miscount desynchronises the client forever

There is no closing bracket in RESP. A handler writing WriteArrayLen(3) and emitting two elements leaves the client blocking for a third it then takes from the next command's reply. Every reply on that connection is off by one from then on. Build the slice, take its length, then write — never count and emit in two passes over data that can change between them.

Concurrency: what we traded away

Real Redis executes every command on a single thread. That is not a performance compromise; it is the source of its strongest guarantee. Nothing interleaves with a running command, so every command — INCR, SINTERSTORE, a whole Lua script — is atomic for free, with no locks and no data races. It works because the bottleneck is the network, not the CPU.

Rebuilding that in Go means rebuilding an event loop and discarding the reason to use Go. So we take the idiomatic shape — goroutine per connection — and pay for it with a keyspace split into independently locked shards. The trade is written down where it is made:

internal/store/store.go — the package comment is the design documentgo
// This server instead runs one goroutine per connection over a keyspace split
// into N independently locked shards. The trade is explicit:
//
//   - We keep atomicity per command, because every command that touches one key
//     holds that key's shard lock for its whole duration. INCR is still safe.
//   - We give up atomicity across keys. A multi-key command in real Redis sees
//     one consistent snapshot; here a DEL of two keys in different shards is two
//     separate atomic steps. MULTI/EXEC and Lua would need a global lock.
//   - We gain real parallelism on multi-core machines, which is the point of
//     writing this in Go. Goroutine-per-connection is the idiomatic Go server
//     shape, and sharding is the idiomatic way to keep the shared map from
//     becoming the single contended lock that erases that parallelism.
//
// Shard count is a power of two so that the shard index is a mask of the hash
// rather than a division.
the whole of shard selection — and the cost, made explicitgo
// hashKey is FNV-1a. It is inlined here rather than used through hash/fnv's
// interface so that hashing a key allocates nothing.
func hashKey(key string) uint64 {
	const (
		offset64 = 14695981039346656037
		prime64  = 1099511628211
	)
	h := uint64(offset64)
	for i := 0; i < len(key); i++ {
		h ^= uint64(key[i])
		h *= prime64
	}
	return h
}

func (s *Store) shardFor(key string) *shard {
	return s.shards[hashKey(key)&s.mask]
}

// Delete removes keys and returns how many existed.
//
// Each key is removed under its own shard lock, one at a time. That is the
// visible cost of sharding: a two-key DEL is not one atomic step. Locking every
// shard up front would restore atomicity and reintroduce the global lock we
// sharded to avoid.

Adding MSET is where you discover you cannot lock two shards

Looping the pairs and locking each key's shard in turn is not MSET; it is N independent SETs with observable intermediate states. Holding every relevant lock at once deadlocks as soon as two clients issue MSET a b and MSET b a across two shards. The safe version takes locks in a fixed global order (ascending shard index, deduplicated), the discipline in sync internals. MULTI/EXEC is the same problem at full scale.

The skip list, properly

A sorted set answers two questions that want opposite structures: ZSCORE key member is a point lookup, ZRANGEBYSCORE key 10 20 an ordered range. A hash does the first in O(1) and the second not at all; a tree does both in O(log N) and makes the common case slower. Redis uses both, kept in lockstep by every mutation, and so do we.

A skip list is a linked list with express lanes: level 0 links every node in order, level 1 roughly every fourth (p = 0.25), level 2 every sixteenth. A search runs forward while the next node is smaller than the target, then drops a level. Node height is chosen by coin flips, so there is no rebalancing code at all — a few dozen lines instead of a red-black tree's few hundred.

internal/store/zset.go — levels, and the total ordergo
const (
	zskiplistMaxLevel = 32   // enough for 2^64 elements at p=0.25
	zskiplistP        = 0.25 // probability of promoting a node one more level
)

// randomLevel returns 1 with probability 0.75, 2 with probability 0.75*0.25,
// and so on. math/rand/v2's top-level functions are safe for concurrent use,
// and we only ever get here holding a shard lock anyway.
func randomLevel() int {
	level := 1
	for level < zskiplistMaxLevel && rand.Float64() < zskiplistP {
		level++
	}
	return level
}

// less orders nodes by score, breaking ties by member bytes. The tie-break is
// part of the contract: ZRANGE on equal scores returns members in lexicographic
// order, and ZRANGEBYLEX depends on it entirely.
func less(scoreA float64, memberA string, scoreB float64, memberB string) bool {
	if scoreA != scoreB {
		return scoreA < scoreB
	}
	return memberA < memberB
}

Insert is a search that remembers where it turned. update[i] is the last node visited at level i, rank[i] is that node's rank, and the two together are exactly what the span arithmetic needs.

insert: the update vector, then splitting the spansgo
	var (
		update [zskiplistMaxLevel]*zslNode // last node visited at each level
		rank   [zskiplistMaxLevel]int      // rank of that node, for span maths
	)

	x := zsl.head
	for i := zsl.level - 1; i >= 0; i-- {
		if i == zsl.level-1 {
			rank[i] = 0
		} else {
			rank[i] = rank[i+1]
		}
		for x.level[i].forward != nil &&
			less(x.level[i].forward.score, x.level[i].forward.member, score, member) {
			rank[i] += x.level[i].span
			x = x.level[i].forward
		}
		update[i] = x
	}

	level := randomLevel()
	// ... head becomes the predecessor at any newly created levels ...

	x = &zslNode{member: member, score: score, level: make([]zslLevel, level)}
	for i := 0; i < level; i++ {
		x.level[i].forward = update[i].level[i].forward
		update[i].level[i].forward = x
		// The predecessor's old span covered the gap that now contains x, so
		// split it: everything the predecessor skipped past x's position stays
		// on x, the rest (plus x itself) stays on the predecessor.
		x.level[i].span = update[i].level[i].span - (rank[0] - rank[i])
		update[i].level[i].span = (rank[0] - rank[i]) + 1
	}
	// Levels above the new node just gained one more node underneath them.
	for i := level; i < zsl.level; i++ {
		update[i].level[i].span++
	}
Why a skip list beats a balanced tree here

Not asymptotics — both are O(log N) — but four practical properties. (1) No rotations: insert and delete are local pointer surgery, without the case analysis that makes red-black trees error-prone. (2) Level 0 is a sorted linked list with back pointers, so ZRANGE and ZREVRANGE are "find the start, then walk". (3) span is one integer per forward pointer; subtree sizes in a tree must be fixed by every rotation. (4) Range boundaries fall out of the same descent — firstInRange and lastInRange differ only in the comparison.

Re-scoring is delete + insert, and the dict must move with it

Position is a function of score, so ZADD on an existing member cannot patch in place — it deletes at the old score, inserts at the new one, then updates the dict. Miss the dict update and ZSCORE disagrees with ZRANGE forever; miss the delete and the member appears twice. Add also separates added from changed, so a re-add at an identical score returns 0 and leaves the command clean — which keeps it out of the AOF. And ZINCRBY rejects inf + -inf: a NaN score makes every comparison in less ill-defined.

Memory accounting

Eviction needs a number to act on, and the Go heap is not it — it includes connection buffers, the AOF buffer and allocator slack. So every mutation maintains a cached per-entry size and a per-shard atomic total, making MemoryUsed O(shards) instead of O(keyspace).

the cost model — approximate, but symmetricgo
// Per-entry overheads, in bytes. These are estimates of what the Go runtime
// actually spends: a map bucket slot, the Value header, a slice header, a list
// or skiplist node. They do not have to be exact -- eviction only needs a
// consistent, monotonic measure so that "delete keys until we are under the
// limit" terminates -- but they must be charged and refunded symmetrically,
// which VerifyMemoryAccounting checks.
const (
	entryOverhead    = 64
	sliceOverhead    = 24
	mapEntryOverhead = 48
	listNodeOverhead = 48
	zsetNodeOverhead = 96
)

func baseCost(key string) int64     { return entryOverhead + int64(len(key)) }
func stringCost(b []byte) int64     { return sliceOverhead + int64(len(b)) }
func zsetMemberCost(m string) int64 { return mapEntryOverhead + zsetNodeOverhead + 2*int64(len(m)) }

zsetMemberCost charges the member string twice, once for the dict entry and once for the skip list node — the honest answer for a structure that stores every member in two places, and worth knowing before you put ten million members in a leaderboard. Mutation sites then adjust by deltas: sh.grow(v, stringCost(v.str)-before) in IncrBy, sh.grow(v, -zsetMemberCost(m)) in ZRem.

Incremental accounting rots silently — so make it a test

One code path that charges on insert and forgets to refund on delete, and the counter drifts upward until eviction runs continuously on a nearly empty keyspace. Drift the other way and eviction never fires at all. Neither shows up as a failing assertion anywhere near the bug. The defence is a full recomputation, called after randomised workloads:

What to take away

  1. RESP2 is five type bytes, CRLF framing and no aggregate terminator — the declared count is the contract. Emit fewer elements than you declared and that connection is desynchronised permanently, with the symptom surfacing in unrelated code.
  2. Every length a client sends is an attack surface. Bound the element count (1 M), the payload length (512 MiB) and the header line (128 B) before allocating — the header cap is the forgotten one, because readLine loops past bufio.ErrBufferFull by design.
  3. Streaming comes free from the goroutine-per-connection model: "the command arrived in three TCP segments" is a blocking read inside bufio, not saved parser state.
  4. A protocol error is not a command error. Reply, flush, close — hence ProtocolError as a distinct type the connection loop tests for.
  5. Sharded locks buy multi-core parallelism and cost cross-key atomicity. Per-command atomicity survives because a command holds one shard lock throughout; DEL a b and MSET do not, and the fix is a fixed global lock order.
  6. Nothing owned by a shard may outlive its lock: Get copies, exportEntry deep-copies, and the three-index slice stops an append reaching bytes someone else owns.
  7. A sorted set is two structures in lockstep, and the skip list's edge over a balanced tree is engineering rather than complexity: no rotations, level 0 is already the range iterator, and one extra int per pointer buys O(log N) ZRANK.
